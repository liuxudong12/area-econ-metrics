# Day 13 操作手册：行级数据权限

> 目标：让**同一个接口**对不同的人返回不同的数据 ——
> 长沙市的管理员看到 11 个区县，张家界的管理员看到另外 11 个，谁也看不到对方的，
> 而代码里**一行 if 都不用加**。
>
> 今天所有数字都是实测的，第七节给了完整复现命令。

## 一、今天要解决什么问题

前 12 天做的都是同一件事的三个方面：

```
Day 1-4   把数据存进来、查出来        → 功能
Day 5-8   让它快起来                 → 性能
Day 9-12  让它稳下来（导入/导出）      → 稳定性
```

今天换一个维度：**安全**。

具体说，是一个真实项目里 100% 会遇到、而简历上的"CRUD 项目"从来不做的功能：

> 省厅的人打开大屏，看到全省 150 个区县的数据。
> 长沙市的人打开同一个大屏，只应该看到长沙的 11 个。
> 芙蓉区的人，只应该看到芙蓉区 1 个。
>
> 他们点的是**同一个按钮**、请求的是**同一个接口**、跑的是**同一段代码**。

### 为什么这件事非做不可

我把它拆成三层，从弱到强：

| 层次 | 做法 | 能挡住什么 |
|---|---|---|
| 界面控制 | 前端把菜单藏起来 | 只挡"不知道怎么用的人"。F12 删掉那行 div，接口照样能敲 |
| 接口鉴权 | 校验"你有没有权限访问这个接口" | 挡住"没登录的人"。但**有权限的人能看到全部数据** |
| **行级数据权限** | 校验"你能看到哪些行" | 挡住"登录了但只该看一部分的人" ← **今天做的** |

前两层是"门禁"，第三层是"每个人的文件柜只能开自己那格"。

**政企项目里，这一层是甲方验收的必查项。** 它不是锦上添花，是交付红线。
数据越权在等保测评里是直接扣分项，在真实事故里是"内部员工批量导出客户名单"的常见成因。

### 一句话总结今天的成果

> **5 个用户、同一个接口，看到 150 / 11 / 1 / 0 个区域；
> 48.96 万行的明细导出，长沙用户只能导出 35,904 行；
> 加权限后每条 SQL 多花 0.057ms（优化的，未优化时 0.92ms）；
> 故意写错的三种配置，全部被抓出来了。**

## 二、先说清楚"数据权限"到底是什么

用最土的话讲：

```
账号权限   →  你能不能进这个系统
功能权限   →  你进了系统能不能点"删除"这个按钮
数据权限   →  你能看到、能改的**具体是哪些行数据**
```

举个我们项目里的真实对应：

| 用户 | 角色 | 数据范围 | 打开大屏看到 |
|---|---|---|---|
| admin | 省厅管理员 | 全部 | 全省 150 个区县 |
| changsha | 长沙市管理员 | 辖区 4301 | 长沙 11 个区县 |
| yuelu | 长沙第2区管理员 | 辖区 430102 | 只有 430102 一个 |
| zhangjiajie | 张家界市管理员 | 辖区 4308 | 张家界 11 个区县 |
| viewer | 省厅只读（没配辖区） | 辖区为空 | **0 个** ← 这一行最关键 |

### 为什么用"编码前缀"而不是"等于"

区域编码是国家标准的分段编码，上级天然是下级的前缀：

```
430000  湖南省
  430100  长沙市
    430102  长沙第2区
    430103  长沙第3区
    ...
```

所以：

- 传 `43` → `region_code LIKE '43%'` → 全省
- 传 `4301` → `LIKE '4301%'` → 长沙市 + 它下面所有区县
- 传 `430102` → `LIKE '430102%'` → 就一个区

**一个字段、一个 `LIKE`，覆盖三种粒度。**

对比一下另一种做法：建一张"用户-区域"关联表，把长沙的 11 个编码一个个列进去。
代价是每新增一个区县，都得给所有地市管理员补一条记录；漏了就是"这个区看不到数据"。
用前缀就永远不会有这个问题。

> ⚠️ 前提：编码必须严格按 GB/T 2260 分段。自己瞎编的编码体系（比如 1、2、3 顺序编号）
> 用不了这招。这个取舍面试被问到要能说清楚。

## 三、三种做法，为什么选第三种

这是今天最重要的一个决策，面试必问。三种做法都写在代码注释里了，这里给对比：

### 做法 A：查全量，Java 里过滤

```java
List<Row> all = mapper.selectAll();              // 48.96 万行
List<Row> mine = all.stream()
        .filter(r -> r.getRegionCode().startsWith("4301"))
        .toList();                                // 3.59 万行
```

问题有三个，一个比一个严重：

| 问题 | 具体后果 |
|---|---|
| 13 倍的无用 I/O | 只为返回 3.59 万行，却把 48.96 万行全搬进内存 |
| 导出直接 OOM | Day 12 实测过：48.96 万行全量查峰值 **508MB**，256MB 堆下整个服务被打死 |
| 分页彻底失效 | 数据库给你 20 行，过滤完剩 3 行 —— 用户看到"每页只有 3 条" |

第三条最致命，因为它**不报错**。用户只会觉得"这系统分页做得真烂"。

### 做法 B：每个 Service 方法手动加条件

```java
wrapper.eq("region_code", user.getRegionCode());
```

看起来最简单。问题只有一个，但是致命的：**一定会漏。**

本项目现在有 7 条需要受约束的 SQL（统计 4 条 + 导出取数 1 条 + 导出计数 1 条 + 分页 1 条）。
将来加到 30 条，谁能保证每个人都记得加？

而且"漏了"这件事：
- 不报错，接口 200
- 数据看起来完整（只是多了别人家的）
- 代码评审时看不出（**缺的是"没有的东西"，人眼对缺失不敏感**）

### 做法 C：在 Mapper 层拦截 SQL，执行前改写 WHERE ✅

```sql
-- 改写前
WHERE f.deleted = 0 AND i.category = ? AND f.period_code IN (?,?)
-- 改写后
WHERE f.deleted = 0 AND i.category = ? AND f.period_code IN (?,?) AND f.region_code LIKE '4301%'
                                                                  ↑ 运行时自动加上
```

三个好处：

1. **数据库只扫该扫的行** —— 性能最好（长沙用户扫 3.59 万行，不是 48.96 万）
2. **权限逻辑只有一份** —— 改一处全局生效
3. **漏标记的风险可控** —— 用显式注解 + "找不到别名就抛异常"兜住

一句话总结这个选择：

> **过滤条件必须下推到数据库。**
> 因为只有数据库知道怎么用索引把它变快，
> 也因为应用层根本不该看到那些行。

```
      │
      ▼
```

### 5.1 第一步：sys_user 表

```sql
CREATE TABLE sys_user (
```

五个测试用户，覆盖五种必须验证的场景：

| id | username | data_scope | region_code | 用途 |
|---|---|---|---|---|
| 1 | admin | ALL | 430000 | 全量基准 |
| 2 | changsha | REGION | 4301 | 地市级 |

### 5.2 第二步：@DataScope 注解

文件：`security/DataScope.java`

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DataScope {
    String alias() default "";        // SQL 里的表别名，如 "f"
    String column() default "region_code";
}
```

用在 Mapper 方法上：

```java
@DataScope(alias = "f")
List<RegionMetricStatVO> selectCategorySummary(...);
```

#### 为什么是"显式标记"而不是"自动检测所有 SQL"

有两种设计思路：

- **自动**：拦截所有 SQL，只要 FROM 里出现 `fact_indicator_value` 就自动过滤
- **显式**（我们选的）：让开发者主动标记

选显式的三个理由：

1. **不是所有 SQL 都该被过滤**
   比如"补区域名称"那条 `SELECT * FROM dim_region WHERE region_code IN (...)`，
   它的入参已经是过滤后的结果，再加一遍纯属浪费。
   又比如"全省排名"时，分母要不要算别的市？业务上说不清 —— 这种必须让人决定。

2. **自动检测靠表名匹配，改表名就静默失效**
   有人把表改成 `fact_indicator_value_2025`，拦截器还在按老名字找 ——
   不报错，权限直接没了。这类"静默失效"是安全 bug 里最可怕的。

3. **显式标记本身就是一份清单**
   想知道"哪些接口受数据权限约束"，全局搜 `@DataScope` 就行。
   做安全评审时，这份清单能直接交上去。

代价也很明确：**漏标 = 漏权限**。所以第十节专门有个工具来抓漏网的。

#### alias 为什么必须有

因为 SQL 里有子查询。看 Day 6 的 TOP N 排行：

```sql
SELECT t.regionCode, RANK() OVER (...) FROM (
    SELECT f.region_code, SUM(...) FROM fact_indicator_value f
    WHERE f.deleted = 0 ...          ← 过滤条件必须加在**这一层**
    GROUP BY f.region_code
) t
ORDER BY t.totalValue DESC LIMIT 10
```

如果加到**外层**（别名 `t` 那一层），外层根本没有 `f`，MySQL 直接报
`Unknown column 'f.region_code' in 'where clause'`。

所以拦截器要按 alias 递归往下找，找到"FROM 里真的挂着别名 f 的那一层"。

### 5.3 第三步：ThreadLocal 上下文

文件：`security/DataScopeContext.java`、`security/LoginUser.java`

```java
public final class DataScopeContext {
    private static final ThreadLocal<LoginUser> HOLDER = new ThreadLocal<>();
    public static void set(LoginUser u) { HOLDER.set(u); }
    public static LoginUser get()        { return HOLDER.get(); }
    public static void clear()           { HOLDER.remove(); }
}
```

#### 为什么不用"参数一层层传下去"

那样每个方法签名都多一个 `currentUser`，而业务方法根本不关心这人是谁，
只是"顺手带过去"。这叫**参数污染**。

ThreadLocal 让"当前用户"像全局变量一样可取，但每个线程各有一份。

#### ⚠️ 这个类最大的风险：忘记清理

Tomcat 的线程是**复用**的。处理完请求 A，回头就处理请求 B。

如果 A 放进去没删，B 进来读到的还是 **A 的身份**。

后果：长沙的管理员发完请求，下一个请求（可能是张家界的人，甚至是匿名）
恰好落到同一个线程，就**顶着长沙的身份**查数据。

这叫"串号"，是 ThreadLocal 最经典的事故。而且它**偶发** ——
压测时线程不空闲，几乎复现不出来；线上用户一多就零星出现别人的数据。

所以规矩是：**set 和 clear 必须配对，clear 写在 finally 能保证执行的位置。**

#### LoginUser 为什么用 record

因为它在整条链路里**只读**。record 天然不可变。

如果给它 setter，只要有一处 `user.setRegionCode(null)`，
后面所有 SQL 就都不过滤了。**权限对象必须是不可变的**，这不是洁癖，是防守。

#### scopeKey()：三种语义收敛成一个方法

```java
ALL            → "ALL"
REGION + 4301  → "R4301"
REGION + null  → "NONE"
```

为什么要单独搞这个？因为缓存 key 里不能直接放 `regionCode`：
`null` 会变成字符串 `"null"`，更要命的是 **ALL 和 REGION+null 都可能拼出同一个串**，
而这两者的结果一个是全量、一个是零行，差着 48.96 万行。

### 5.4 第四步：身份拦截器

文件：`security/UserContextInterceptor.java`、`config/WebConfig.java`

```java
public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler) {
    DataScopeContext.clear();                       // 先清，防御上一轮的残留
    String raw = req.getHeader("X-User-Id");
    if (raw == null || raw.isBlank()) {
        throw new BizException(401, "缺少身份信息：...");
    }
    SysUser user = sysUserMapper.selectById(Long.parseLong(raw.trim()));
    if (user == null)          throw new BizException(401, "用户不存在");
    if (user.getStatus() != 1) throw new BizException(401, "用户已停用");

    DataScopeType scope = DataScopeType.parse(user.getDataScope());
    if (scope == null) {
        // 数据库里存了枚举里没有的值（有人手工改成了 'ALLOW'）
        throw new BizException(403, "用户的数据范围配置无效：" + user.getDataScope());
    }
    DataScopeContext.set(new LoginUser(..., scope, trimToNull(user.getRegionCode())));
    return true;
}

public void afterCompletion(..., Exception ex) {
    DataScopeContext.clear();                       // 无论成败都要清
}
```

#### 三个设计点

**① 清理为什么在 afterCompletion，不在 postHandle**

`postHandle` 只在 Controller **正常返回**后执行；抛异常时不执行。
也就是说"出错的那个请求"会把身份留在 ThreadLocal 里 ——
而恰恰是出错的请求更容易被重试、被并发。

`afterCompletion` 只要 `preHandle` 返回过 true 就一定执行，包括异常。

**② 枚举解析失败为什么抛 403 而不是默认 ALL**

配置错误的方向必须是"更严格"，不是"更宽松"。
返回 403 让人去修数据，比"悄悄给出全量数据"安全一万倍。

**③ ⚠️ X-User-Id 只是个教学替身，绝不能上生产**

请求头是客户端随便改的：用 Postman 把 `X-User-Id: 3` 改成 `1`，
立刻就是省厅管理员的权限。

真实项目的三种可靠来源：

| 方案 | 怎么保证不可伪造 | 要不要查库 |
|---|---|---|
| JWT | token 用服务端密钥签名，改一个字节就验签失败 | 不用（信息在 token 里） |
| Session | 服务端存，客户端只有一个随机 id | 不用 |
| OAuth2 / SSO | 交给统一认证中心 | 不用 |

**那为什么本项目还要每次查库？**

因为 `data_scope` / `region_code` 是**管理员随时能改**的，不能固化在 token 里
（改了要等 token 过期才生效，安全上是漏洞）。

折中方案：token 里只放 `userId`，每次请求按 userId 查一次用户信息 ——
这就是绝大多数企业系统的实际做法。

代价实测（第八节 E8）：**0.69ms**（含 HTTP 往返），纯查库约 0.3~0.5ms。

#### 拦截哪些、不拦哪些

```java
registry.addInterceptor(userContextInterceptor)
        .addPathPatterns("/api/**")                                  // 默认全部受保护
        .excludePathPatterns("/api/auth/users", "/api/auth/data-scope"); // 例外显式声明
```

**用"白名单"还是"黑名单"，结果完全不同：**

- ✗ 白名单（列出要拦的）：新增接口忘了加 → 那个接口没有身份
- ✓ 黑名单（默认全拦 + 排除少数）：新增接口**默认受保护**，放行必须显式加一行

这就是安全该有的默认值：**默认拒绝，例外显式声明。**
和"辖区为空就返回 0 行"是同一个原则。

### 5.5 第五步：SQL 改写拦截器（核心）

文件：`security/DataScopeInnerInterceptor.java`

#### 骨架

```java
@Override
public void beforeQuery(Executor executor, MappedStatement ms, Object parameter,
                        RowBounds rowBounds, ResultHandler resultHandler, BoundSql boundSql) {

    if (!enabled) return;                                  // 实验开关
    Optional<DataScope> ann = findAnnotation(ms.getId());
    if (ann.isEmpty()) return;                             // 没标 → 放行

    LoginUser user = DataScopeContext.get();
    if (user == null) throw new BizException(403, "当前线程没有用户身份...");  // ① 绝不放过
    if (user.isAllScope()) return;                          // ② 全量用户不改写

    // ③④⑤ 算条件 → 改写 → 写回
    String cacheKey = ms.getId() + '|' + user.scopeKey() + '|' + boundSql.getSql();
    String newSql = rewriteCache.get(cacheKey);
    if (newSql == null) {
        newSql = injectCondition(boundSql.getSql(), buildCondition(user, ann.get()),
                                 ms.getId(), ann.get());
        rewriteCache.put(cacheKey, newSql);
    }
    PluginUtils.mpBoundSql(boundSql).sql(newSql);
}
```

#### 关键点 1：用 AST 而不是拼字符串

**错误写法：**

```java
String newSql = boundSql.getSql() + " AND f.region_code LIKE '" + prefix + "%'";
```

遇到 `WHERE a = 1 OR b = 2`，会变成：

```sql
WHERE a = 1 OR b = 2 AND f.region_code LIKE '4301%'
              └────── 被 OR 短路了，权限过滤形同虚设 ──────┘
```

**越权，而且不报错。**

正确做法是解析成 AST，用 `AndExpression(oldWhere, newCondition)` 连起来 ——
`toString()` 出来天然带括号：

```sql
WHERE (a = 1 OR b = 2) AND f.region_code LIKE '4301%'
```

#### 关键点 2：递归找正确的层级

```java
private boolean injectInto(PlainSelect ps, Expression cond, DataScope ds) {
    FromItem from = ps.getFromItem();
    if (from instanceof Table table) {
        if (!aliasMatches(table, ds)) return false;
        Expression old = ps.getWhere();
        ps.setWhere(old == null ? cond : new AndExpression(old, cond));
        return true;
    }
    if (from instanceof ParenthesedSelect sub) {      // FROM ( SELECT ... ) t
        return injectInto((Select) sub, cond, ds);    // 递归下去
    }
    return false;
}
```

外层 `FROM ( SELECT ... ) t` 匹配不上 `f`，于是递归进子查询，在里面找到
`FROM fact_indicator_value f` 那一层，条件就加在那里。

**如果整棵 AST 都找不到这个别名 → 抛异常，不放过。**

因为那几乎一定是"XML 里改了别名、注解忘了同步"，静默跳过的后果是
这条 SQL 从此不受权限约束，而没有任何提示。

#### 关键点 3：为什么是 `PluginUtils.mpBoundSql().sql(...)` 而不是 `return new BoundSql(...)`

这是个坑。MyBatis-Plus 3.5.9 的 `InnerInterceptor.beforeQuery` **返回值是 void** ——
没有"返回一个新 BoundSql 让框架用"这个口子。

那 MP 自己怎么改 SQL？用 `PluginUtils.mpBoundSql(boundSql).sql(newSql)`：
它把原 BoundSql 包一层，通过 MetaObject 反射**直接写 sql 字段**。
分页插件加 LIMIT 走的就是这条路。我们照抄同一套。

#### 关键点 4：⚠️ 直接改对象，会不会影响别的请求

不会。`BoundSql` 虽然字段是 final，但它**不是共享单例**：

- `DynamicSqlSource.getBoundSql()` → 每次 new
- `RawSqlSource.getBoundSql()` → 每次 new

一次查询一个 BoundSql，改它只影响这一次。

**但反过来想**：如果哪天你把改写写到了 `MappedStatement.getSqlSource()` 上
（那是**共享**的），就会出现"长沙的管理员查完，全省其他人也只能看长沙"。
**改之前先问：这个对象是"每次新建"还是"大家共用"？**

#### 关键点 5：改写结果缓存

第一次实现时是每条 SQL 都解析一遍。实测 **0.92ms/条**。
一个导出请求 245 条 SQL，就是 225ms 纯花在"拆字符串再拼回去"上。

而这件事的结果**每次都一样** —— 因为改写结果只取决于：

1. 哪条 SQL（结构）→ `msId + SQL 文本`
2. 谁的权限范围 → `scopeKey`
3. 注解里的 alias → 固定挂在 msId 上

**参数值完全不影响改写结果**（我们只是往 WHERE 里 AND 一个条件，`?` 占位符一个都不动）。

所以加一层 `ConcurrentHashMap<msId|scopeKey|sql, newSql>`，
第二次开始就是一次 map 查找。

实测：**0.92ms → 0.057ms（16 倍），稳态 0.02ms/条，命中率 99.9%**。

> ⚠️ key 里为什么不能带参数**值**：那样用户随便传什么都能造一个新 key，
> 就是缓存最经典的"key 空间被用户输入撑爆"事故。
> 带 SQL **文本**是安全的，因为 `?` 占位符的个数是有限的（IN 列表长度）。

### 5.6 第六步：缓存 key（最容易漏）

文件：`service/impl/StatServiceImpl.java`

**这一步比 SQL 拦截器更重要，因为它更隐蔽。**

Day 7 给四个统计接口加了 Redis 缓存。缓存命中时，流程是：

```
请求 → 拼 key → 命中 Redis → 直接返回
             ↑
       根本不查库，SQL 压根没执行
```

而数据权限是靠"改写 SQL"实现的 —— **SQL 不执行，权限就不生效**。

所以必然发生（第七节 E7 实测复现）：

```
① admin 先请求 → 150 条 → 写进 stat:category-summary:工业:Y:2024,2025,2026
② changsha 请求同样参数 → 同一个 key → HIT → 拿到 150 条
③ 长沙管理员看到了全省数据。接口 200，日志正常，SQL 一次没跑。
```

修复就是给 key 加一段 `scopeKey()`：

```java
String key = StatCacheHelper.buildKey(
        "category-summary", category, periodType,
        StatCacheHelper.joinSorted(periodCodes), currentScopeKey());
```

```
stat:category-summary:工业:Y:2024,2025,2026:ALL
stat:category-summary:工业:Y:2024,2025,2026:R4301
stat:category-summary:工业:Y:2024,2025,2026:NONE
```

这就是 Day 7 那条铁律的第 13 天版本：

> **凡是会影响 SQL 结果的入参，一个都不能漏进 key。**
> Day 7 漏的是 `topN`，Day 13 要漏的就是"用户的数据范围"。

### 5.7 第七步：插件顺序

文件：`config/MybatisPlusConfig.java`

```java
interceptor.addInnerInterceptor(dataScopeInnerInterceptor);                       // ← 必须在前
interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));    // ← 必须在后
```

**`addInnerInterceptor` 的顺序 = 执行顺序，后一个拿到的是前一个的返回值。**

| 顺序 | 会发生什么 |
|---|---|
| ✓ 权限 → 分页 | ① 先改 WHERE ② 分页基于改写后的 SQL 去 COUNT、加 LIMIT → **total = 35904（正确）** |
| ✗ 分页 → 权限 | ① 先 COUNT 拿到 **489600（全量！）** ② 再在带 LIMIT 的 SQL 上加过滤 → **数据对，total 错** |

这个 bug 的形态很有意思：**数据没错，只有总数错**。
接口 200、数据合法，用户翻两页就发现不对了。

前 12 天没暴露，是因为所有统计都是手写 SQL、没用过分页插件。
Day 13 两个插件第一次同时存在，这个问题才浮出来。

## 六、五个必须处理的边界

这五条是这段代码的全部价值。每一条都对应第七节的一个实验。

| # | 情况 | 正确行为 | 写错的后果 |
|---|---|---|---|
| ① | ThreadLocal 里没用户 | 抛 403 | 不加条件 → 匿名看全量 |
| ② | data_scope = ALL | 原样放行 | 多一层无谓过滤 |
| ③ | data_scope = REGION 但辖区为 NULL | 加 `1 = 0`，返回 0 行 | **新员工入职即看全省** |
| ④ | SQL 里有子查询/窗口函数 | 改**正确的层级** | 报错，或改错层 |
| ⑤ | 找不到注解指定的别名 | 抛异常 | 静默失效，权限没了 |

### ③ 号边界单独讲：fail-closed

这是整段代码里最重要的几行。

```java
if (prefix == null || prefix.isBlank()) {
    log.warn("[数据权限] 用户 {} 的 data_scope=REGION 但未配置辖区，按'无可见数据'处理", user.username());
    return ALWAYS_FALSE;      // "1 = 0"
}
```

**如果写成"不加条件"会发生什么？**

真实项目里 `data_scope` 和 `region_code` 是管理员在后台表单里分开填的。
新建用户时只选了角色、忘了选辖区 → `region_code = NULL`。

如果代码写成：

```java
if (user.getRegionCode() != null) { 加上过滤条件 }   // ← 少了 else
```

那么这个人**能看全省数据**，而且系统一切正常：
接口 200、数据完整、日志无异常。

直到某天有人发现"新来的小王能看到别的市的数据"。

根因是**默认值选错了方向**：配置缺失时的默认行为应该是"最严格"，不是"最宽松"。

安全领域把这条叫做 fail-closed：

```
门锁坏了 → 打不开（fail-closed）✓
门锁坏了 → 谁都能进（fail-open）✗
```

```
  总处理=1550 真实解析=1550 累计耗时=1740.7ms 平均每条=0.921ms

  第1轮 500次 端到端平均 38.16ms/次 | 总处理=550  真实解析=1  命中率=99.8% 平均每条=0.123ms
  第2轮 500次 端到端平均 38.84ms/次 | 总处理=1050 真实解析=1  命中率=99.9% 平均每条=0.074ms
  第3轮 500次 端到端平均 39.77ms/次 | 总处理=1550 真实解析=1  命中率=99.9% 平均每条=0.057ms
```

看差值更准：从 550 次到 1550 次，累计耗时 67.9ms → 88.3ms，
即 **1000 次只花了 20.4ms = 0.02ms/条**。

**结论：改写摊到每条 SQL 上 0.02~0.06ms。**

对比一下：一次统计查询查库要 5~20ms。**改写占比 0.1%~1%。**

而换来的收益（实验 E4）：导出耗时从 19.66s 降到 1.65s，**快了 11.9 倍**。

> **这笔买卖的账**：花 0.05ms 换 11.9 倍，净赚 2000 倍。
> 而且安全价值没法用时间衡量。
>
> 面试时这么答：
> "改写本身 0.02 到 0.06 毫秒一条，因为加了改写结果缓存，JSqlParser 只解析第一次。
> 但它让数据库少扫了 93% 的行，导出反而快了 12 倍。"

## 八、踩坑记录

### 坑 1：MP 的 `beforeQuery` 返回值是 void

我第一版写的是：

```java
public BoundSql beforeQuery(...) { return new BoundSql(...); }   // 编译不过
```

因为 MyBatis-Plus 3.5.9 的 `InnerInterceptor.beforeQuery` 签名是 `void`。
MyBatis 原生 `Interceptor` 可以 `invocation.proceed()` 换参数，但 MP 的插件链不是那个模型。

解法：`PluginUtils.mpBoundSql(boundSql).sql(newSql)` —— 反射改原对象的字段（MP 自己的做法）。

### 坑 2：`additionalParameters` 丢了

如果改用 `new BoundSql(...)` 重建对象，一定要手动复制 `additionalParameters`：

```java
old.getAdditionalParameters().forEach(fresh::setAdditionalParameter);
```

因为 `<foreach>` 生成的 `__frch_pc_0`、`__frch_pc_1` 不在 `parameterObject` 里，
而在 `boundSql.additionalParameters` 里。

漏了会报 `Parameter '__frch_pc_0' not found` —— **报错位置在 JDBC 层，
看起来跟权限毫无关系**，非常难查。

（本项目最终没走这条路，但这个坑要知道。）

### 坑 3：别名匹配不上就静默失效

第一版实现里，找不到别名时 `return false`（跳过不改写）。
测试时发现 top-regions 的 `@DataScope(alias="f")` 没生效 —— 但接口 200、数据完整。

改成**抛异常**之后，问题立刻暴露出来。

> **安全相关的代码，"跳过"这个动作本身就是 bug。**
> 业务代码里"跳过"是容错，安全代码里"跳过"是放行。

### 坑 4：`1 = 0` 而不是 `FALSE`

MySQL 支持 `WHERE FALSE`，但 Oracle 没有 boolean 字面量。
写 `1 = 0` 跨库通用。这种细节面试时提一句，显得你真的踩过。

### 坑 5：`StatServiceImpl` 里 `LoginUser` 的 import 差点漏

`currentScopeKey()` 里用了 `LoginUser` 类型，要 `import com.liuxudong.areaecon.security.LoginUser;`。
编译期就报错，不算坑。但提醒一点：**这个 helper 方法是 Services 层唯一知道"权限"的地方**，
其余业务代码完全无感知 —— 这正是设计目标。

## 九、面试怎么讲

### 一句话版本

> "给统计和导出接口做了行级数据权限。做法是在 MyBatis 拦截器里用 JSqlParser 改写 SQL，
> 按用户辖区前缀动态 AND 一个 LIKE 条件，业务代码一行都不用改。
> 五个用户测下来分别是 150 / 11 / 1 / 11 / 0 个区域，导出从 48.96 万行收窄到 3.59 万行。
> 改写本身加了结果缓存之后是 0.02 毫秒一条。"

### 追问准备

**Q：为什么不在 Java 里过滤？**
A：三个原因。① 48.96 万行搬进内存只为返回 3.59 万，13 倍无用 I/O；② 导出场景会 OOM，
实测全量查峰值 508MB；③ 分页彻底失效 —— 数据库给 20 行，过滤完剩 3 行，而且不报错。

**Q：每个 Service 手动加条件不行吗？**
A：会漏。现在 8 条 SQL，将来 30 条，没人能保证都记得。而且"漏了"不报错、
数据看起来完整、代码评审也看不出（缺的是"没有的东西"）。
所以我用显式注解 + 一个扫描工具来把漏网的列出来。

**Q：性能影响多大？**
A：两项固定成本。① 每请求查一次用户表，约 0.4ms（因为 data_scope 是管理员随时能改的，
不能固化在 token 里）；② SQL 改写，加了结果缓存之后 0.02~0.06ms 一条。
换来的是数据库少扫 93% 的行，导出反而快了 12 倍。

**Q：怎么防止漏掉某个接口？**
A：三层。① 拦截器默认拦所有 `/api/**`，放行要显式声明；② SQL 层用 `@DataScope` 显式标记，
找不到别名直接抛异常而不是跳过；③ 有个扫描接口列出所有 Mapper 方法及标注状态，
SUSPECT 的每一条都要能说出"为什么不用标"。

**Q：配置漏了会怎样？**
A：我专门做了这个实验。如果 `data_scope=REGION` 但辖区是 NULL，
代码里写 `if (regionCode != null) 加条件` 就漏了 else —— 这个人能看到全省数据，
而且接口 200、日志正常。我用的是 fail-closed：辖区为空就拼 `1 = 0`，返回 0 行。
**默认值要往严格的方向选。**

**Q：缓存怎么办？**
A：这里有个坑。统计数据有 Redis 缓存，命中缓存时 SQL 根本不执行，
拦截器也就没机会改写它。所以缓存 key 里必须带上用户的权限指纹（ALL / R4301 / NONE）。
我实测过：去掉这一段，长沙用户会命中 admin 的缓存，139 个区域的越权数据直接返回。

**Q：多表 JOIN 和子查询怎么处理？**
A：用 JSqlParser 解析成 AST，按注解里的别名递归找"FROM 里真的挂着这个别名的那一层"。
比如 TOP N 那条 SQL 是 `FROM (SELECT ... FROM fact f) t`，条件必须加在子查询内部，
加到外层会报 Unknown column。找不到就抛异常，不猜。

## 十、已知漏洞（SUSPECT 清单的实际结论）

实验 E9 抓出 4 个 SUSPECT，逐条核对：

| 方法 | 是否真漏洞 | 结论 |
|---|---|---|
| `IndicatorMapper.selectCategories` | ❌ 不是 | 指标字典，全省共用，本来就不该按区域过滤 |
| `ImportErrorRowMapper.countByTaskId` | ✅ **是** | `import_error_row` 只按 `task_id` 关联，没按用户隔离 |
| `ImportErrorRowMapper.countByType` | ✅ **是** | 同上 |
| `ImportErrorRowMapper.selectPageByCursor` | ✅ **是** | 同上 |

### 具体是什么问题

Day 11 做的"导入错误明细"：用户上传一个坏 Excel，系统把出错的行记进
`import_error_row`，然后用户能下载错误报告。

问题：`async_task` 和 `import_error_row` **都没有 user_id 字段**。
所以只要知道 taskId，任何人（任何辖区）都能下载别人导入的错误明细。

```
GET /api/import/task/7/errors?scope=all
   ↑ 这个 7 是谁的任务？系统不检查
```

### 严重程度

中低。因为：① 错误明细里只有"用户自己上传的数据"的片段，不是全量业务库；
② 需要知道 taskId（自增数字，可以枚举）。

但**它确实是越权**，而且是最容易被忽视的那一类 ——
权限只做在"主表"上，忘了"从表/日志表"。

### 怎么修（留到以后，或面试时讲思路）

两个层次：

**最小改动**：给 `async_task` 加 `create_user_id`，`ImportController` 下载错误报告时校验
`task.createUserId == currentUser.id`，不是本人就 403。

**彻底一点**：`import_error_row` 也带上 `region_code`（从任务创建人的辖区快照），
然后给它标 `@DataScope`。这样和其他表走同一套机制。

> 为什么"快照"而不是关联查询？
> 因为用户的辖区会变（从长沙调去益阳）。历史任务应该按"当时"的辖区算，
> 而不是"现在"的。这是数据权限里一个容易被忽略的时间维度问题。

**这个"已知问题"本身就是面试素材** —— 它证明你的检查工具真的抓出了东西，
而不是做做样子。

## 十一、这套东西离生产还差什么

老实地列一遍，面试被追问"你们这个能上生产吗"时能答上来。

### 1. 身份认证（必须替换）

现在的 `X-User-Id` 请求头是客户端随便填的。生产必须换成：
JWT 验签 / Session / 企业 SSO。编码量约 1~2 天。

### 2. 只做了"读"，没做"写"

数据权限对写操作的形态是**"改/删之前先校验归属"**：

```java
// 伪代码
Row row = mapper.selectById(id);
if (!canSee(user, row.getRegionCode())) throw new BizException(403, "无权操作");
mapper.updateById(row);
```

⚠️ 而且这个校验必须在**同一个事务**里，且最好用 `UPDATE ... WHERE id = ? AND region_code LIKE ?`
这种"带条件的更新"—— 否则有"检查完、还没改，数据被改走了"的并发窗口（TOCTOU）。

本项目没有"修改既有业务数据"的接口（只有导入新增），所以这块没做。

### 3. 只有"行"，没有"列"和"字段"

真实政企项目常常还有**字段级脱敏**：同一个接口，"企业名称"所有人能看，
"联系电话"只有本辖区能看，"统一社会信用代码"只有省级能看。
那是另一套机制（序列化时按角色过滤字段）。

### 4. 多租户没考虑

如果系统要一套代码给多个客户用（SaaS），还要加 `tenant_id` 过滤。
那属于数据权限的另一个维度，和 region 是**并列**的，不是替代关系。

### 5. 拦截器的性能边界

现在的改写缓存 key 是 `msId|scopeKey|sql`。如果用户辖区有 1000 种组合，
就是 1000 倍的缓存条目（数量不大，但仍是有界的）。
真正超大规模时要考虑 LRU 而不是无界 ConcurrentHashMap。

### 6. 审计日志

"谁在什么时候查了哪些数据" —— 敏感数据访问必须留痕。
本项目只有 `export_log`（Day 12 做的），查库操作没有审计。

## 十四、今天的收获与明天

### 三条最值得记住的话

1. **过滤条件必须下推到数据库。**
   过滤越晚，代价越大：数据库只扫该扫的行是最省的。
   Java 里过滤会同时牺牲性能、内存和分页正确性。

2. **安全相关的默认值要往"严格"的方向选。**
   配置缺失 → 拒绝；枚举不认识 → 拒绝；找不到别名 → 抛异常。
   业务代码里"跳过"是容错，安全代码里"跳过"是放行。

3. **缓存和权限必须一起想。**
   缓存命中时 SQL 不执行，所有"改 SQL 做权限"的方案都会失效。
   key 里少一段 scope，前面所有工作全部白做。

### 明天（Day 14）建议

理由：

  游标 64.7×、导出内存 5×、数据权限导出 11.9×……），但它们是散的
- 面试官更想听的是"你怎么定位瓶颈、怎么验证、怎么避免自欺欺人"
