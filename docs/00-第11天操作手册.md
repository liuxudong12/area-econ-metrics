前 10 天解决的是"**怎么把数据导进去**"，今天解决的是"**导不进去的时候，怎么让用户自己修好**"。

具体四件事：

## 二、先看清改造前的痛点（这不是假设，是代码事实）

改造前，`FactImportListener` 里是这样写的（Day 10 版本，`git show 7171a6d` 可查）：

```java
// 第 66 行
private static final int MAX_ERRORS = 5;
...
// 第 235-236 行
if (errors.size() < MAX_ERRORS) {
    errors.add(withRow);   // 一条只是一个字符串
}
```

也就是说，**一个 1 万行、3000 行有错的文件，用户只能看到 5 条错误**，剩下的 2995 行要靠他自己在 Excel 里肉眼找。

而且这 5 条还得塞进 `async_task.error_msg`（`VARCHAR(1000)`）。一条错误信息 60 多个字符，十几个就撑爆了。

用户拿到的提示长这样：

```
导入失败：共 2989 行数据不合法，本次一行都未写入。
示例：第 6 行：周期类型只能是 Y/Q/M，实际是：月；第 8 行：…；第 22 行：…（共 2989 行有误，仅列出前 5 条）
```

用户看完能做什么？只能说：**放弃**。

> **一句话总结**：数据结构的上限，决定了产品能力的上限。
> 你把错误存成 `List<String>`，那你最多只能做个"提示框"；
> 你把错误存成一张表，才能做个"错误报告"。

## 三、闭环长什么样

```
   ┌──────────────┐
   │ ① 下载模板    │  GET /api/import/template
   │  5 列 + 示例  │  周期编码列已设文本格式，输入 2027-01 不会变日期
   └──────┬───────┘
          ↓ 用户填写
   ┌──────────────┐
   │ ② 上传        │  POST /api/import/async
   └──────┬───────┘
          ↓ 后台解析 + 校验
     ┌────┴─────┐
     │ 全部通过？ │
     └────┬─────┘
      是  │        否
     ┌────↓────┐  ┌─────────────────────────────────────┐
     │ 写库成功 │  │ ③ 错误明细落库（独立事务，先删后插） │
     │ SUCCESS  │  │    任务标 FAILED，但明细留着          │
     └─────────┘  └──────────────┬──────────────────────┘
                                 ↓
                  ┌──────────────────────────────┐
                  │ ④ 看统计：哪类错误最多        │  GET .../error-summary
                  │   周期类型非法 2629 行 87.96% │
                  └──────────────┬───────────────┘
                                 ↓
                  ┌──────────────────────────────┐
                  │ ⑤ 下载错误报告                │  GET .../errors?scope=error|all
                  │   scope=error：只有错误行     │
                  │   scope=all  ：全部行 + 标注  │
                  └──────────────┬───────────────┘
                                 ↓ 用户在同一份 Excel 里改
                  ┌──────────────────────────────┐
                  │ ⑥ 原样重传（多余的 3 列被忽略）│
                  └──────────────┬───────────────┘
                                 ↓
                            导入成功 10000 行
```

**⑥ 那一步是今天最有价值的地方**：用户下载的文件和模板列不一样（多了 3 列），但直接传上去就能用。因为 EasyExcel 是**按表头名绑定**的，找不到对应 `@ExcelProperty` 的列会被自动忽略，不报错。

## 四、三个技术点，是今天真正要讲的东西

### 技术点 1：错误明细绝对不能和主数据同事务

#### 是什么

导入失败时，业务数据要回滚（一行都不写），但**错误明细必须留下来**。这两件事必须在两个事务里。

#### 为什么

看下面这段"看起来很正常"的代码：

```java
@Transactional
public void importFile(File f) {
    List<Row> rows = parse(f);
    List<Error> errors = validate(rows);
    if (!errors.isEmpty()) {
        errorMapper.insertBatch(errors);   // 写错误明细
        throw new BizException("有错误");   // 抛异常 → 事务回滚
    }
    factMapper.insertBatch(rows);
}
```

跑起来会发生什么？

```
开事务 → 写 2989 条错误明细 → 抛 BizException → Spring 回滚整个事务
       → 错误明细被 UNDO 掉了
```

用户点"下载错误报告"，得到一张**空表**。然后他会以为系统坏了。

#### 怎么办

把"写错误明细"抽出来，让它自己开一个事务、**先提交**，再让异常往上抛：

```java
// ImportServiceImpl.java · persistErrors 方法
transactionTemplate.executeWithoutResult(status -> {
    importErrorRowMapper.delete(...);          // 清上一轮
    for (int from = 0; from < total; from += ERROR_BATCH) {
        importErrorRowMapper.insertBatch(chunk);  // 分批写
    }
});   // ← 这里提交。提交完之后，外面怎么回滚都动不到它
```

#### 怎么验证

实验数据：任务最终状态是 `FAILED`（业务数据 0 行），但 `import_error_row` 里有 **2989 条**记录，能正常下载成 Excel。

```sql
SELECT status, success_rows, error_rows FROM async_task WHERE id=1;
-- FAILED | 0 | 2989        ← 业务没写，但错误记下来了

SELECT COUNT(*) FROM import_error_row WHERE task_id=1;
-- 2989
```

> **记住这句话**：任务失败要回滚业务数据，但**失败的原因不能回滚**。否则用户永远不知道错在哪。
> 这和 Day 10 那条"任务状态更新不能和业务数据同事务"是同一个道理的两面。

### 技术点 2：描述错误的表，不能假设错误数据是合法的

#### 是什么

`import_error_row.indicator_value` 这一列，用的是 `VARCHAR(64)`，**不是** `DECIMAL(20,4)`。

#### 为什么

先想清楚一个问题：**什么样的行会成为错误行？**

答案是：**不符合我们表结构的行**。具体来说：

| 用户填的 | 为什么会错 |
|---|---|
| `abc` | 根本不是数字 |
| `12,000` | 带了千分位 |
| `1.5万` | 中文字符 |
| `-33001` | 是数字，但业务上不允许负数 |

如果我们把这一列建成 `DECIMAL(20,4)`，那么"插入一条错误记录"这个动作**本身就会失败**：

```
ERROR 1366: Incorrect decimal value: 'abc' for column 'indicator_value'
```

于是出现一个荒谬的循环：**为了记录错误，程序自己又报了一个错。**

#### 怎么办

错误表的所有字段都按字符串存，并在写入前统一截断到列宽：

```java
// FactImportListener.java
private static final int CODE_MAX = 64;
private static final int TYPE_MAX = 32;
private static final int MSG_MAX = 500;
...
e.setIndicatorValue(truncate(row.getIndicatorValue().toPlainString(), CODE_MAX));
```

> 同理，`region_code` 也用 `VARCHAR(64)` 而不是主表的 `VARCHAR(32)` ——
> 因为用户可能在那一格填 200 个字符。**错误数据不遵守任何约定**，包括长度约定。
> 所以代码里还要再截断一次（双保险）。

#### 怎么验证

实测里 30 行 `BAD_NUMBER` 类型，`indicator_value` 存的就是字符串 `abc`：

```sql
SELECT row_num, indicator_value, error_msg FROM import_error_row
WHERE task_id=1 AND error_type='BAD_NUMBER' LIMIT 1;
-- 106 | abc | 第 106 行的「指标值」填了「abc」，无法识别为数字
```

### 技术点 3：Excel 会把 `2027-01` 自动变成日期

#### 是什么

用户在模板的"周期编码"格子里输入 `2027-01`，一按回车，格子变成 `2027/1/1`。

#### 为什么

Excel 的单元格有"类型"。默认是"常规"，Excel 看到 `2027-01` 会认为你想表达一个日期，于是：
1. 把值**转换**成一个日期序列号（比如 46023）
2. 把**显示格式**改成日期

关键点：**转换发生在用户输入的那一刻，跟我们的程序没有任何关系**。我们读到的已经是日期值了，再怎么处理也恢复不出原来的字符串。

结果是：数据库里存的是 `2027-01`，用户传上来的是 `2027/1/1`，对不上。而唯一索引 `uk_fact` 不会拦（字符串不同），于是**脏数据静默入库**，等统计报表查不出来才发现。

#### 怎么办

在用户输入**之前**就把格子标成"文本"：

```java
// TextColumnStyleHandler.java
CellStyle textStyle = workbook.createCellStyle();
textStyle.setDataFormat(workbook.createDataFormat().getFormat("@"));  // "@" = 文本
for (Integer col : textColumns) {
    writeSheetHolder.getSheet().setDefaultColumnStyle(col, textStyle);
}
```

模板里设了三列：`区域编码`(0)、`指标编码`(1)、`周期编码`(2)。

> 为什么区域编码也要设文本？因为如果有 `043102` 这种前导 0 的编码，
> 数字格式会把 0 吃掉变成 `43102`。**所有"看起来像数字但其实是编码"的列，都必须是文本。**

#### 怎么验证（这里有个我自己的弯路）

一开始我担心两件事：
- 列默认格式管不到**用户新增的行**
- 也管不到**示例行那几个已存在的单元格**

于是我额外写了个 `CellWriteHandler`，逐个单元格设样式。实测发现：**它被 EasyExcel 内置的样式覆盖了，而且根本不需要。**

证据（解压 xlsx 看 `xl/worksheets/sheet1.xml`）：

```xml
<!-- 列定义：style=1，对应 numFmtId=49（文本） -->
<cols><col min="1" max="1" style="1" .../>
      <col min="2" max="2" style="1" .../>
      <col min="3" max="3" style="1" .../></cols>

<!-- 示例行：t="inlineStr" 说明值本身是字符串类型 -->
<row r="2">
  <c r="C2" s="3" t="inlineStr"><is><t>2027-01</t></is></c>
</row>
```

`t="inlineStr"` 才是关键：**程序写进去的值本身就是字符串，不是"数字+日期格式"**。Excel 打开看到的是字符串，压根不会转换。所以示例行即使显示格式是 General，也永远是 `2027-01`。

**真正需要解决的只有一件**：用户之后**新增的行** —— 那些格子现在还不存在，用的是列的默认格式。这才是 `setDefaultColumnStyle` 的唯一作用。

于是我删掉了那层无效的 `CellWriteHandler`。

> **这条值得单独记住**：先把问题验证清楚，再决定要不要写那层代码。
> 我如果一开始就去实测，能省掉半小时。

### 实验 B：错误明细落库耗时

| 条数 | 批次数（500/批） | 耗时 |
|---|---|---|
| 2989 条 | 6 批 | **412 ms** |
| 100 条（截断实验） | 1 批 | **53 ms** |

日志原文：

```
[导入-错误明细] 已落库 taskId=1 条数=2989 批次数=6 耗时=412ms
[导入-错误明细] 已落库 taskId=1 条数=100  批次数=1 耗时=53ms
```

> 为什么 2989 条要分 6 批而不是 1 条 SQL 塞完？
> 因为错误行多一个 `error_msg`（最长 500 字符），500 行一条 SQL 可能到 300KB。
> 单条 SQL 太大，MySQL 解析成本高，而且一旦失败整批全废。
> 这和 Day 9 的"500 行一批"是同一个理由。

### 实验 C：两个导出接口的耗时

| 接口 | 导出行数 | 文件大小 | 三次耗时 |
|---|---|---|---|
| `?scope=error` | 2,989 | 142 KB | 307.6 / 184.3 / 154.1 ms |
| `?scope=all` | 10,000 | 413 KB | 414.6 / 277.8 / 282.0 ms |

> 第一次总比后面慢（307 → 154）：JIT 预热 + 类加载。
> 这和 Day 7 讲过的"新 JVM 要先预热"是同一件事，**报数字时要说明是第几次**。

**为什么 `scope=all` 慢一倍多**：它要**重新解析一遍原始文件**（1 万行），而 `scope=error` 只是从数据库里查 2989 条。

### 实验 E：闭环验证（今天最重要的一组数据）

#### E1：如果只给用户"错误行"，会发生什么

用户下载 `scope=error` 的报告（2989 行），把错误全部改正，重传。

| 观察点 | 结果 |
|---|---|
| 任务状态 | **SUCCESS** |
| `success_rows` | **2989** |
| 数据库里 2027 年的实际行数 | **2928** |
| 应该是多少 | **10000** |
| **丢失** | **7072 行** |

> 2928 而不是 2989：因为 `EMPTY_REQUIRED` 那 106 行区域编码被清空，修正时统一填了 `430000`，
> 有 61 行和已有组合撞上，被 upsert **覆盖**了（不是失败，是覆盖）。

**这就是最坑的体验**：系统显示"导入成功，2989 行"，用户以为搞定了。
实际上原文件里 **7000 多行正确的数据从来没进过库** —— 因为它们跟着第一批一起回滚了，
而错误报告里根本没有它们。

#### E2：给"全部数据 + 标注"，结果完全不同

用户下载 `scope=all` 的报告（10000 行，前 3 列是 Excel行号/错误类型/错误原因），改完重传。

| 观察点 | 结果 |
|---|---|
| 任务状态 | **SUCCESS** |
| `success_rows` | **10000** |
| 数据库里 2027 年的行数 | **10000** |
| `fact_indicator_value` 总数 | **499,600** = 489,600 + 10,000 ✅ |

**这一组对比就是 `scope=all` 存在的全部理由。**

#### 顺带验证：多出来的 3 列会被忽略

E2 的文件表头是：

```
Excel行号 | 错误类型 | 错误原因 | 区域编码 | 指标编码 | 周期编码 | 周期类型 | 指标值
```

`FactImportRow` 只认后 5 个表头。前 3 个找不到对应的 `@ExcelProperty`，被 EasyExcel **静默忽略**，不报错 —— 所以用户改完可以直接传，不用删列。

> ⚠️ 代价：用户如果**改动了后 5 个表头的任何一个字**，就会绑定失败、字段全 null，
> 然后报"区域编码不能为空"。所以模板说明里要明确写"请勿修改表头"。

| `truncated` | **true** | 前端要提示"仅记录前 100 条" |
| 下载文件行数 | **100** | |
| 各类型百分比之和 | **100.00%** | 分母用的是 `recordedRows` |

### 实验 G：重试不会让错误明细翻倍

| 时点 | 明细条数 | id 范围 |
|---|---|---|
| 首次失败后 | 100 | 1 ~ 100 |
| 手动重试（再失败一次）后 | **100** | 101 ~ 200 |

条数没变，但 id 变了 —— 说明走的是"**先 DELETE 再 INSERT**"，不是累加。

> 为什么不做 upsert（像 `fact` 表那样）？
> 因为错误明细的语义是"**当前这一轮的快照**"，不是流水账。
> 整批替换最简单，也不会让用户看到重复行后怀疑"是不是导了两遍"。

## 七、踩坑记录（6 个）

### 坑 1：`getCellData().getData()` 返回 null，错误消息里是「」

**现象**：错误明细里 `indicator_value` 字段正确存了 `abc`，但 `error_msg` 里是：

```
第 106 行的「指标值」填了「」，无法识别为数字
```

**原因**：`onException` 分支里，EasyExcel **还没把值转成目标类型**，所以 `getCellData().getData()` 返回 null。

**修法**：回到原始单元格按列索引取文本（`cellMap` 里存的是原文）：

```java
String badText = rawTextByIndex(context, e.getColumnIndex());
if (badText == null) {
    Object raw = e.getCellData() == null ? null : e.getCellData().getData();
    badText = raw == null ? "" : String.valueOf(raw);
}
```

> **教训**：异常分支里拿不到"正常路径"的数据，是很常见的事。
> 凡是"出错时还要展示原值"的需求，都要准备一条独立的取值路径。

---

### 坑 2：百分比的分母选错

**现象**：截断到 100 条时，各类百分比是 `2.74% / 0.43% / 0.10% / 0.07%`，加起来只有 **3.34%**。

**原因**：分母用了 `errorRows`（2989），但分子加起来只有 100。

**修法**：分母改成 `recordedRows`（已记录明细条数），各类占比正好 100%：

```
周期类型非法  82 行  82.00%
指标值为负    13 行  13.00%
数值格式错误   3 行   3.00%
必填项为空     2 行   2.00%
百分比之和 = 100.00%
```

> 语义要说清楚：这是"**在已记录的 100 条明细里**各类占多少"，不是"全部 2989 行里各类占多少"。
> 截断时前端要额外提示一句，用户才不会误解。

---

### 坑 3：同一句话说了三遍

**现象**：

```
导入失败：共 2989 行数据不合法，本次一行都未写入：第 6 行…；第 8 行…；第 22 行……（共 2989 行有误，
可下载错误报告查看全部明细）（共 2989 行数据有问题，已生成错误报告，可下载后修改重传）
```

三个地方都在说"2989 行"和"可以下载"。

**原因**：`errorSummary()`、`BizException` 消息、`buildResult()` 三层各拼了一遍。

**修法**：划分信息层次 —— **数量由上层说一次，中间层只举例，最下层只给动作**：

```
导入失败：共 2989 行数据不合法，本次一行都未写入。
示例：第 6 行：周期类型只能是 Y/Q/M，实际填的是「月」；第 8 行：…；第 22 行：…
（已生成错误报告，可下载后修改重传）
```

> 这类问题不影响功能，但**非常影响专业感**。面试官如果看到这种文案，会觉得"这人没自己用过"。

---

### 坑 4：`ReadListener` 没有 `invokeHeadMap` 方法

**现象**：编译报错"方法不会覆盖或实现超类型的方法"。

**原因**：`com.alibaba.excel.read.listener.ReadListener` 接口里**没有** `invokeHeadMap`，
它在 `AnalysisEventListener` 抽象类里（有默认空实现）。

**修法**：把 `implements ReadListener<FactImportRow>` 改成 `extends AnalysisEventListener<FactImportRow>`。

---

### 坑 5：`getCellMap()` 返回的是 `Map<Integer, Cell>` 不是 `CellData`

**现象**：编译报"不兼容的类型"。

**原因**：`readRowHolder().getCellMap()` 的返回类型是 `Map<Integer, Cell>`，
`Cell` 是接口，`CellData` 是实现类。`getStringValue()` 这些方法在 `CellData` 上，不在接口上。

**修法**：

```java
Cell cell = cells.get(idx);
if (!(cell instanceof CellData cd)) {   // 用 instanceof 模式匹配，顺带判空
    return null;
}
```

> 用 `instanceof` 而不是直接强转，是因为万一 EasyExcel 以后换了实现，这里会返回 null 而不是 `ClassCastException`。
> 错误处理路径上的代码，**宁可降级也不要崩**。

---

### 坑 6：`error_msg` 装不下第 6 条错误

**现象**：改造前，明明 `MAX_ERRORS = 5`，但有时候只显示了 2~3 条。

**原因**：`async_task.error_msg` 是 `VARCHAR(1000)`，一条错误信息 60~200 字符。
`truncate(msg, 950)` 会从中间截断，后面的错误就没了。

**修法**：今天直接换掉了存储方式（明细表），`error_msg` 只留"前 3 条 + 省略号"，永远写不满。

> 更普遍的教训：**字段长度不是"够不够用"的问题，是"上限在哪"的问题**。
> 只要一个字段要存"数量不定"的东西，就该考虑换表。

## 八、自测题（7 道，带答案）

### 题 1：为什么错误明细必须用独立事务？不用会怎样？

<details>
<summary>展开答案</summary>

因为导入失败时业务数据要回滚，而错误明细是"失败的原因"，必须留下来。
如果共用一个事务，抛 `BizException` 后整个事务回滚，**错误明细被 UNDO 掉**，
用户点"下载错误报告"得到空表，会以为系统坏了。

实现上就是用一个独立的 `TransactionTemplate`，**先提交，再让异常往上抛**。

</details>

---

### 题 2：`import_error_row.indicator_value` 为什么是 `VARCHAR` 而不是 `DECIMAL`？

<details>
<summary>展开答案</summary>

因为**这一行之所以成为错误行，很可能就是因为这一列填了非数字**（`abc`、`12,000`、`1.5万`）。
如果建成 `DECIMAL`，"插入一条错误记录"这个动作本身就会失败 —— 为了记录错误，程序自己又报了个错。

原则：**描述错误的模型，不能假设错误数据符合 schema。**

</details>

---

### 题 3：`uk_fact` 唯一索引不含 `deleted`，这对错误处理有什么影响？

<details>
<summary>展开答案</summary>

这是 Day 10 的坑，今天仍然有效：
一行被逻辑删除（`deleted=1`）后，唯一键仍然占位。用 upsert 重导入时如果不显式写
`deleted = 0`，这行**永远不会复活**，而且不报错、查询也查不到 —— 静默 bug。

所以 `insertBatch` 的 `ON DUPLICATE KEY UPDATE` 里必须带上 `deleted = 0`。

</details>

---

### 题 4：为什么 `scope=all` 要重新解析原始文件，而不是从错误表里拼？

<details>
<summary>展开答案</summary>

因为错误表**只存了错误行**。正确行的数据只在原文件里。

用户改完重传时必须带上那些正确行（它们跟着第一批一起回滚了，从没进过库）。
所以必须重新读一遍上传时落盘的那个文件（`async_task.file_path`）。

实验 E1 证明了不这么做的后果：只导 2989 行，**7072 行永久丢失**，而系统显示 "SUCCESS"。

</details>

---

### 题 5：`scope=all` 为什么用 `Map<Integer,String>` 读，不用 `FactImportRow`？

<details>
<summary>展开答案</summary>

因为 `FactImportRow` 会做类型转换：指标值那列填了 `abc` 会抛 `ExcelDataConvertException`。
而我们要导出**恰恰是这些行**。

`Map<Integer,String>` 模式下每一格都是字符串，**不做任何转换，永远不会失败** ——
正好是我们需要的"用户当初填的原文"。

</details>

---

### 题 6：游标分页（`WHERE id > ? ORDER BY id LIMIT ?`）比 `LIMIT offset, size` 好在哪？

<details>
<summary>展开答案</summary>

- `LIMIT offset, size`：offset 越大越慢。MySQL 要先**扫描并丢弃** offset 行，
  第 1 万页要扫 9999×N 行。
- 游标法：`WHERE id > lastId` 始终是主键范围扫描，**每页耗时几乎恒定**。

前提是结果必须 `ORDER BY id` —— 游标分页的"不重不漏"完全依赖这个顺序。
不排序的话 MySQL 返回顺序不保证，可能漏行或读重复。

</details>

---

### 题 7：流式下载接口里，如果写到一半抛异常怎么办？

<details>
<summary>展开答案</summary>

**没办法。** 响应头已经发出去了（`Content-Type`、`Content-Disposition`），
甚至 body 已经写了一部分，这时**不可能再改成 JSON 错误响应**。

所以设计原则是：**所有能提前校验的，全部放在写响应头之前**。
`downloadErrors` 里先做 `getErrorSummary(taskId)`（校验任务存在、有没有错误行、scope 是否合法），
全部通过后才 `setDownloadHeaders` + 开始写流。

剩下的运行时异常（比如原文件被清理了）只能记日志 —— 用户拿到一个不完整的文件。
真实项目里的做法是：**下载前先确认资源还在**，或者把文件存到对象存储（不会被人为清理）。

</details>

## 九、面试话术（8 条）

### 1. "你这个导入功能，用户上传错了怎么办？"

> 我做了个闭环：用户先下模板，填完上传；如果有错，系统把所有错误行**全量落库**
> （不是只提示前几条），并提供一个"错误报告"下载 —— 里面是原始数据加上
> 行号、错误类型、错误原因三列。用户在同一个 Excel 里改完直接重传，
> 多余的列会被自动忽略，不用删。
>
> 关键是我提供了两种导出范围：只导错误行，或者导全部行带标注。
> 实测过：如果只给错误行，用户改完重传，**那些原本正确的行就永久丢了** ——
> 它们的错误原因列是空的，在报告里根本不存在。而全量导出就没有这个问题。

### 2. "错误明细为什么要单独建表，不能写在任务的 error_msg 字段里？"

> 两个原因。一是**容量**：`error_msg` 是 `VARCHAR(1000)`，一条错误信息 60 多个字符，
> 十几个就撑满了，所以原来只能存 5 条 —— 3000 行错误的文件，用户只能看到 5 条。
>
> 二是**结构**：存成字符串就没法按类型聚合。我建了表之后，可以 `GROUP BY error_type`
> 告诉用户"3000 行错误里 87.96% 是周期类型填错了，你改那一列就行"。
> 这句话比"有 3000 行错了"有用得多。

### 3. "写错误明细和写业务数据，事务怎么处理的？"

> 分开的。业务数据要能回滚（一行都不写），但错误明细**不能回滚** —— 它是失败的原因。
> 如果共用一个事务，抛异常之后明细被 UNDO 掉，用户点下载得到空表。
>
> 所以我用一个独立的 `TransactionTemplate`，**先提交，再让异常往上抛**。
> 提交之后外面怎么回滚都动不到它。

### 4. "用户填的 `2027-01` 传上来变成 `2027/1/1` 了，你怎么解决的？"

> 这是 Excel 的自动日期识别：输入 `2027-01` 时 Excel 认为你想表达日期，
> 会转成日期序列号并把格式也改掉。**转换发生在用户输入那一刻，程序无能为力。**
>
> 唯一解法是在用户输入前把格子标成文本 —— 用 `setDefaultColumnStyle` 设列默认格式为 `@`。
> 这里有个细节：必须设**列**级而不是单元格级，因为用户要往下新增几十行，
> 那些单元格现在还不存在；列默认格式对之后新增的单元格生效。
>
> 我实测验证过：解压 xlsx 看 XML，列定义是 `numFmtId=49`（文本），
> 示例行的值是 `t="inlineStr"`（字符串类型）。两个都对，所以用户怎么填都不会被转。

### 5. "错误报告导出，数据量大怎么办？"

> 用**游标分页 + 边查边写**。不是"先全查出来再写"，而是每次查 1000 条、写一次、再查下一千条，
> 内存里永远只有 1000 条对象，跟总数无关。
>
> 游标分页用 `WHERE id > lastId ORDER BY id LIMIT 1000`，而不是 `LIMIT offset, size` ——
> 后者 offset 越大越慢，因为 MySQL 要先扫并丢弃 offset 行。

### 6. "为什么写错误明细时字段全用 String？"

> 因为**错误数据的本质就是"不符合模型"**。指标值那列填了 `abc`，才能成为错误行；
> 如果建表时写成 `DECIMAL`，插这条错误记录本身就会失败 —— 记录错误的动作自己报错了。
>
> 同理 `region_code` 也用 `VARCHAR(64)` 而不是主表的 32，因为用户可能在那一格填 200 个字符。
> 错误数据不遵守任何约定，包括长度约定。代码里还要再截断一次做双保险。

### 7. "文件下载的中文文件名怎么处理的？"

> HTTP 头只能是 ASCII，直接写中文会被 ISO-8859-1 编码成乱码。
> 用 `URLEncoder.encode(name, UTF_8)`，并且把空格转成 `%20`（URLEncoder 默认输出 `+`）。
>
> 响应头写两层兼容：`filename="..."` 给老浏览器，`filename*=UTF-8''...` 是 RFC 5987 标准写法。
> 另外加 `Access-Control-Expose-Headers: Content-Disposition` ——
> 前后端分离时，跨域读不到这个头，前端就拿不到真文件名。

### 8. "这个功能里你觉得最难的是什么？"

> 不是技术，是**发现"只给错误行"是个坑**。
>
> 我一开始觉得只导错误行就够了 —— 文件小、聚焦。但写完测试的时候想了一下：
> 用户改完这 3000 行，重传上去，那原本正确的 7000 行呢？它们跟着第一批一起回滚了，
> 从来没进过库，而错误报告里根本没有它们。
>
> 于是我造了两份文件做对比实验：只改错误行的版本，系统显示 "SUCCESS 2989 行"，
> 但库里只有 2928 行，少了 7072 行；全量版本导进去正好 10000 行。
>
> 这个坑很隐蔽 —— **系统显示成功，用户以为搞定了，数据却少了一大半**。
> 所以后来我把 `scope=all` 做成了必选项之一，默认还是 `error`（快），
> 但任务详情里会明确提示"要改完整体重传，请下载全部数据"。
