# 01 · 建模设计

## 要解决的问题

政府/园区的大屏要展示的经济指标有几百个：GDP、一产增加值、规上工业增加值、一般公共预算收入、
固定资产投资增速……如果**每个指标建一张表**，会发生什么？

- 表数量爆炸，几百张表
- 每加一个指标就要建表、写 Mapper、写接口、改前端
- 大屏要同时查 20 个指标，就要 join 20 张表
- 维护成本随时间无限增长

**这个项目的核心设计，就是用一套「编码体系」把这几百张表压成一张事实表。**

## 三张维表 + 一张事实表

```
dim_region（区域）  ─┐
dim_indicator（指标）─┼──→  fact_indicator_value（指标值）
dim_period（周期）   ─┘        三者的组合 = 一条数据
```

**事实表只存"谁、什么指标、什么时候、值多少"，指标是什么、属于哪个分类、单位是什么，全部放在维表里。**

## 指标编码体系（这是最值得讲的一点）

```
1              综合经济
├── 1-1        GDP
│   ├── 1-1-1  第一产业增加值
│   ├── 1-1-2  第二产业增加值
│   └── 1-1-3  第三产业增加值
└── 1-2        GDP增速

2              工业
├── 2-1        规模以上工业增加值
├── 2-2        规上工业企业数
└── 2-3        工业用电量
```

编码的规律是 **`父编码-序号`**，所以：

- **层级关系直接体现在字符串里** → 查"工业分类下所有指标"就是 `WHERE indicator_code LIKE '2-%'`，
  或者按 `parent_code = '2'` 查一层子节点
- **加新指标不用改表结构** → 只要往 `dim_indicator` 插一行，前端自动能展示
- **大屏聚合不用 join 多张表** → 一个 `WHERE category = '工业'` 就够了

对比一下：如果按"一指标一表"建模，新增一个指标是一条 DDL；这里是**一条 INSERT**。
这就是统一建模的价值，也是面试时你应该讲出来的那句话。

## 周期维表的必要性

为什么不用字符串直接存 `2026Q1`，还要单独建 `dim_period`？

| 问题 | 只有字符串 | 有周期维表 |
|---|---|---|
| 按时间排序 | `ORDER BY period_code` 对 `2026Q10` 会排错 | `ORDER BY period_index` 正确 |
| 取"最近 12 期" | 要写复杂的字符串处理 | `WHERE period_index > ?` 简单 |
| 算同比/环比 | 要解析字符串 | 直接按 `period_year`、`period_index` 位移 |
| 筛选某年所有季 | 字符串模糊匹配 | `WHERE period_type='Q' AND period_year=2026` |

**结论：把"时间"当维度处理，而不是当字符串处理。** 这是数据仓库的常规做法，也是你区别于
"只会写 CRUD" 的证明。

## 三个典型查询场景

### 场景 1 · 明细查询（走唯一索引，很快）
```sql
SELECT indicator_value FROM fact_indicator_value
WHERE region_code = '431300' AND indicator_code = '1-1' AND period_code = '2026Q1';
```
命中 `uk_fact(region_code, indicator_code, period_code)`。

### 场景 2 · 大屏聚合（第 6-8 天的优化对象）
```sql
SELECT f.region_code, f.period_code, SUM(f.indicator_value) AS total
FROM fact_indicator_value f
JOIN dim_indicator i ON i.indicator_code = f.indicator_code
WHERE f.period_type = 'Y'
  AND i.category = '工业'
  AND f.period_code IN ('2024','2025','2026')
GROUP BY f.region_code, f.period_code;
```
**`period_type` 不在 `uk_fact` 的最左前缀里 → 全表扫描。** 这是要优化的目标。

### 场景 3 · 缺失周期补值
大屏要展示 2021–2026 连续 6 年，但某区县的 2023 年数据缺失。
如果直接跳过，折线图会断。做法是**用上一期的值补齐**：

```sql
-- 思路：先用窗口函数找每个"区域+指标"下最近一个非空值
SELECT region_code, indicator_code, period_code,
       COALESCE(indicator_value,
                LAG(indicator_value) OVER (
                  PARTITION BY region_code, indicator_code
                  ORDER BY period_code
                )) AS filled_value
FROM fact_indicator_value
WHERE region_code = '431300' AND indicator_code = '1-1';
```

> 这是简历里可以单独写一条的技术点：**用窗口函数实现缺失周期自动沿用上期值，避免前端手动补数。**

## 你需要自己想清楚的问题

做完这块之前，先把这四个问题想明白（面试会问）：

1. 为什么事实表用 `UK(region_code, indicator_code, period_code)` 而不是给 `id` 加唯一约束？
2. 如果某个指标是"累计值"（比如 1-6 月累计），而另一个是"当期值"，同一张表能放吗？怎么区分？
3. 大屏要"按分类汇总"，但事实表里没有 `category` 字段——怎么查？有没有更好的设计？
4. 指标编码用 `1-1-1` 这种字符串有什么缺点？如果用整数编码（如 10101）会更好吗？
