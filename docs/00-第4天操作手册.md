## 二、为什么要灌 49 万行？

**因为数据太少，"慢查询"根本不会显形。**

如果 `fact_indicator_value` 只有几百行，全表扫描也就 0.1 毫秒——你根本看不出索引优化前后的差别。

数据量是这么算出来的：

```
行数 = 区域数 × 叶子指标数 × 周期数
     = 150      × 12          × 272
     = 489,600
```

| 维度 | 怎么来的 |
|---|---|
| **区域 150** | 湖南省 + 14 个地级市 + 13 个市各 10 个区县（娄底已有 5 个真实区县） |
| **指标 12** | 只给"叶子指标"赋值（`1-1-1`、`2-1` 这种最末端的具体指标）；`1 综合经济`、`2 工业` 是汇总节点，不给值 |
| **周期 272** | 2011–2026 共 16 年 × （16 个年 + 64 个季 + 192 个月） |

> **为什么要给"叶子指标"过滤条件？**
> 用的是 `NOT EXISTS (SELECT 1 FROM dim_indicator c WHERE c.parent_code = i.indicator_code)`——
> 翻译成人话："找出那些没有被别人当作上级的指标"。
> 这就是维度建模里的标准做法，面试问到可以讲。

**实际生成结果**（实测）：

```
区域数 150 / 指标数 18 / 周期数 272 / 指标值行数 489,600
耗时 6.6 秒
表大小：数据 39.6 MB + 索引 27.6 MB
```

> ⚠️ **脚本可以重复执行**：全部用 `INSERT IGNORE`，重跑不会报错也不会重复插。
> 如果你以后把数据删了，重新跑一遍就回来了。
>
> ⚠️ **这会让 Day 2 手册里的"期望 7 条区域"变成 150 条**——那是正常的，
> 因为我们是"新增"区域，没有删掉原来那 7 条。

**另外记得执行一次 `ANALYZE TABLE fact_indicator_value;`** —— 让优化器知道真实的行数。
不刷新的话它还以为是 10 万行，执行计划可能选错。

## 三、今天的新知识：手写 SQL

### 3.1 什么时候需要手写？

| 场景 | 方案 |
|---|---|
| 单表增删改查 | `BaseMapper` / `lambdaQuery()`，**一行 SQL 都不用写** |
| 多表 JOIN + GROUP BY 聚合 | **必须手写** |

### 3.2 手写 SQL 的两种写法

| 写法 | 适合 | 例子 |
|---|---|---|
| **注解** `@Select("...")` | 短 SQL、无动态条件 | `IndicatorMapper.selectCategories()` |
| **XML** `<select>` | 长 SQL、有 `if` / `foreach` 等动态条件 | `FactIndicatorValueMapper.selectCategorySummary()` |

两种混用在同一个项目里**是正常的**，不是"不统一"。判断标准就一条：**短就注解，长就 XML。**

### 3.3 XML 是怎么被找到的？（这是第一大坑）

靠两个东西，缺一不可：

1. `application.yml` 里配了 `mapper-locations`，指向 `resources/mapper` 下的 xml
2. XML 里的 `namespace` **必须一字不差**等于 Mapper 接口的全限定名

少任何一个，启动就报：

```
Invalid bound statement (not found): com.liuxudong.areaecon.mapper.FactIndicatorValueMapper.xxx
```

### 3.4 `<foreach>` —— 把 Java 的 List 拼成 SQL 的 IN

```xml
AND f.period_code IN
<foreach collection="periodCodes" item="pc" open="(" separator="," close=")">
    #{pc}
</foreach>
```

Java 传 `["2024","2025","2026"]`，最终拼出来是 `AND f.period_code IN ( ? , ? , ? )`。

**注意是 `#{}` 不是 `${}`**——`#{}` 会变成 `?` 做参数绑定（防 SQL 注入），
`${}` 是字符串硬拼（有注入风险，只在拼表名/字段名时才用）。

### 3.5 ⚠️ 手写 SQL 必须自己加逻辑删除条件

这是**今天最容易出线上事故的一点**：

```sql
WHERE f.deleted = 0 AND i.deleted = 0 AND r.deleted = 0
```

MyBatis-Plus 的 `@TableLogic` **只能管它自动生成的单表 SQL**，你手写的多表 SQL 它管不了。
忘了加 = 把已删除的数据也算进统计里 = "报表数字对不上"。

> 你以前修过的那些"统计数量和清单不一致"，很多就是这类问题。

### 3.6 VO 为什么不能复用实体？

聚合结果"长不成一张表的样子"：

```
区域编码    区域名称   汇总值
430100     长沙市     123456.7890
```

数据库里没有这张表，它是 `SUM()` 算出来的临时结构。所以要用专门的 VO 接。

**字段名必须和 SQL 里的别名对上**，对不上就是 `null`——而且**不报错**，最难查。

## 四、今天最重要的发现：索引不是"有没有"，而是"能不能用上"

### 4.1 两个接口，一个快一个慢

| 接口 | 做什么 | EXPLAIN |
|---|---|---|
| `/api/stat/category-summary` | 按**区域**汇总 | `type=ref, key=uk_fact, rows=317` |
| `/api/stat/trend` | 按**周期**汇总 | `type=**ALL**, key=NULL, rows=**487354**` |

**两条 SQL 的表结构、JOIN 完全一样，唯一区别是：一个按区域分组，一个按周期分组。**

- 按**区域** → 查询里必然出现 `region_code` → 而 `uk_fact` 索引的**最左列正好是 `region_code`** → 索引能用上 → 只扫 1,668 行
- 按**周期** → 查询里**从头到尾没有 `region_code`** → 最左列缺失，B+ 树找不到入口 → **全表扫描 48 万行**

### 4.2 实测数字（这条是简历素材，请记牢）

用 `performance_schema` 读 MySQL 自己记录的执行耗时（不含网络开销），每条跑 10 次：

| 查询 | 平均耗时 | 扫描行数 | 用的索引 |
|---|---|---|---|
| 三表 join（按区域）/category-summary | **38.5 ms** | 1,668 | uk_fact |
| 两表 join（按周期）/trend | **122.9 ms** | 489,618 | **无（全表）** |
| 单表汇总（完全不筛区域） | **526.5 ms** | 489,600 | **无（全表）** |

端到端（含 HTTP）实测：

| 请求 | 耗时 |
|---|---|
| `/api/stat/category-summary` | 48 ~ 74 ms |
| `/api/stat/trend`（年，3 期） | **128 ~ 154 ms** |
| `/api/stat/trend`（月，12 期） | **182 ms** |

### 5.3 亲眼看它慢（最重要的一步）

启动服务，调用 `/api/stat/trend`，**看着浏览器转 150 毫秒**。
然后去控制台看它打印的 SQL，把那条 SQL 复制到 Navicat / 命令行里执行：

```sql
EXPLAIN SELECT f.period_code, SUM(f.indicator_value)
FROM fact_indicator_value f
JOIN dim_indicator i ON i.indicator_code = f.indicator_code
WHERE f.deleted=0 AND i.deleted=0 AND i.category='工业'
  AND f.period_type='Y' AND f.period_code IN ('2024','2025','2026')
GROUP BY f.period_code;
```

**看到 `type` 那一列是 `ALL`、`rows` 是 `487354`，你就亲眼见到"全表扫描"了。**

## 六、今天踩到的一个坑（真实发生）

**现象**：编译报错 `非法字符: '\u2461'`、`需要 class、interface、enum 或 record`。

**原因**：我在 Java 注释里写了配置项的通配路径：

```java
/**
 * ① application.yml 里的 mapper-locations: classpath*:/mapper/**   ← 注意这里
 *    /*.xml
 */
```

`**` 后面紧跟 `/` 和 `*`，其中的 **`*/` 组合正好是"注释结束符"**。
编译器一看：注释到这儿就结束了。后面那几行注释文字立刻变成"代码"，于是报出一堆看不懂的错。

**教训**：
- 在 `/* */` 或 `/** */` 注释里，**不要出现 `*/` 这个组合**，哪怕它只是路径的一部分；
- 遇到 `非法字符` / `需要 class、interface...` 这种"驴唇不对马嘴"的报错，
  **第一反应先往上找有没有注释提前结束了**。
