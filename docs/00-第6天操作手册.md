# 第 6 天 · 第二种优化思路：把维表挪到聚合之后

> 目标：把 `/api/stat/category-summary` 从 **43 ms** 压到 **10 ms** 以内；
> 再新增两个大屏接口（TOP N 排行、同比）。
>
> 成果：**DB 耗时 43.38 ms → 10.57 ms（4.1 倍）**，
> 而**平均扫描行数反而从 1,668 涨到了 5,568（多了 3.3 倍）**。
>
> 今天最有价值的不是那 4 倍提速，而是上面这句话——它会让你彻底搞懂
> "扫描行数"和"耗时"不是一回事。完整可复现的实验在 `sql/05-JOIN结构优化实验.sql`。

---

## 一、先看结果

| 指标 | 改造前 | 改造后 | 变化 |
|---|---|---|---|
| DB 平均耗时 | **43.38 ms** | **10.57 ms** | **快 4.1 倍** |
| 平均扫描行数 | 1,668 | 5,568 | **反而多了 3.3 倍** |
| 执行计划 | 600 次索引点查 + 1,350 次回表 | 1 次顺序范围扫描 | 从"随机翻 600 次"到"顺序扫 1 遍" |
| 端到端（HTTP） | Day 4 记录 48 ~ 74 ms | **30.14 ms** | —— |
| 返回条数 | 150 条 | 150 条 | 一致 |
| 前五名金额 | 67757.3316 / 63711.3076 / 63282.0554 … | 完全相同 | **已逐行校验** |

**今天没有加任何索引。** 表上还是 Day 5 的那两个（`uk_fact` + `idx_tpi`），
改的只是 SQL 的写法。

> 这一点很重要。Day 5 你学会了"加索引"，今天要学会"改 SQL"。
> **只会加索引的人，遇到"索引已经加满了还是慢"就会卡住。**

## 二、体检：43ms 到底花在哪

### 2.1 先认识一个新工具：`EXPLAIN ANALYZE`

`EXPLAIN` 只是**预估**（"我打算这么干"），`EXPLAIN ANALYZE` 是**真跑一次**然后告诉你
每个步骤实际花了多久（"我刚才这么干，这是账单"）。MySQL 8.0.18 以上才有。

```sql
EXPLAIN ANALYZE
SELECT f.region_code, r.region_name, SUM(f.indicator_value) AS totalValue
FROM fact_indicator_value f
         JOIN dim_indicator i ON i.indicator_code = f.indicator_code
         JOIN dim_region r ON r.region_code = f.region_code
WHERE f.deleted = 0 AND i.deleted = 0 AND r.deleted = 0
  AND f.period_type = 'Y' AND i.category = '工业'
  AND f.period_code IN ('2024','2025','2026')
GROUP BY f.region_code, r.region_name
ORDER BY totalValue DESC;
```

输出是一棵树（缩进表示层级，**从最里面往外读**）：

```
-> Sort: totalValue DESC                              (actual time=44.3..44.3 rows=150)
    -> Table scan on <temporary>                      (actual time=44..44.1 rows=150)
        -> Aggregate using temporary table            (actual time=44..44 rows=150)
            -> Nested loop inner join                 (actual time=0.273..42.8 rows=1350)  ← ★ 瓶颈
                -> Inner hash join (no condition)     rows=600
                    -> Table scan on r  (dim_region, 150 行)
                    -> Hash -> Table scan on i (dim_indicator, 18 行)
                -> Index lookup on f using uk_fact     (actual time=0.07..0.0708 rows=2.25 loops=600)
```

### 2.2 怎么读这三行数字

| 读法 | 含义 |
|---|---|
| `actual time=A..B` | A = 返回第一行花多久；B = **全部处理完**花多久。**盯 B。** |
| `rows=N` | 这个节点实际处理了多少行 |
| `loops=N` | **这个节点被执行了几次** ← 今天的关键 |

### 2.3 结论

把账单翻译成人话：

```
排序          44.3 ms   ← 只是最后一步，被上面拖累了
聚合          44 ms     ← 也很快，但它在等下面
★ 嵌套循环     42.8 ms   ← 42.8ms 全花在这
   └─ 600 次索引查找，每次约 0.07ms
```

**聚合和排序加起来只花了 2 毫秒，42 毫秒全耗在那 600 次索引查找上。**
而且别忘了：查出 1,350 行明细后，每一行还要**回表去 `dim_region` 换区域名字**——
那是 1,350 次随机 I/O。

## 三、四种写法，横着比一遍

| 方案 | 写法 | DB 耗时 | 相对基线 | 说明 |
|---|---|---|---|---|
| **A** | JOIN `dim_region` + `dim_indicator` | **44.3 ms** | 1.0× | 基线（原版） |
| **B** | 强制走 `idx_tpi` 索引 | **48.8 ms** | 0.9×（**更慢**） | 证明换索引没用 |
| **C** | **去掉 `dim_region` 的 JOIN** | **9.52 ms** | **4.6×** | ★ 今天采用的方案 |
| **E** | 两个维表都不 JOIN | **6.11 ms** | **7.2×** | 极限，但牺牲可维护性 |

### 方案 B 为什么更慢？——这次"失败"很值钱

方案 B 是拿 Day 5 加的 `idx_tpi` 索引硬套上去。结果 **48.8ms，比原版还慢**。

```
走 uk_fact：600 次点查 × 每次扫 302 行 → 1350 次回表        44.3 ms
走 idx_tpi：顺序扫 5,400 行 → 1,350 次回表查 dim_region     48.8 ms
```

两条路都卡在"1,350 次回表"上。所以：

> **这次的瓶颈不是"没索引"，是"要随机访问太多次"。换索引治不了这个病。**

**面试时一定要讲这个失败的尝试**："我先怀疑是索引没用好，试了强制走 `idx_tpi`，
结果反而更慢，这才意识到问题不在索引，在 JOIN 的执行顺序。"——
主动说出排除过程，比一上来就答对更能证明你真在做分析。

## 四、原理：先聚合，还是先 JOIN？

### 4.1 用一个比喻

想象你要统计**全校 150 个班的平均分**，手上有一叠 1,350 张成绩单（每张写了班级号）。

- **改造前（先 JOIN 再聚合）**：
  先拿着每张成绩单跑一趟教务处查"班级号 → 班级名称"，**1,350 趟**，
  查到名字后再按班级把分数加起来，压成 150 行。
  → 白跑了 1,200 趟。

- **改造后（先聚合再补名）**：
  先按班级号把分加起来，压成 150 行，**然后只查 150 次班级名**。
  → 少跑 1,200 趟。

**聚合天生会砍掉 90% 的行，那就应该让它先发生。** 这就是全部的道理。

### 4.2 落到 SQL 上

```sql
-- ✗ 改造前：dim_region 写在 FROM 里，MySQL 只能在"聚合前"就去关联它
FROM fact_indicator_value f
    JOIN dim_indicator i ON ...
    JOIN dim_region   r ON ...          ← 1350 行各查一次名字
GROUP BY f.region_code, r.region_name

-- ✓ 改造后：SQL 只管算数，不碰区域表
FROM fact_indicator_value f
    JOIN dim_indicator i ON ...
GROUP BY f.region_code                  ← 先压成 150 行
-- 区域名字由 Java 侧"一次查 150 个"补上（1 次 IN 查询）
```

### 4.3 顺带搞明白：为什么 `dim_indicator` 反而留着？

因为它只有 **18 行**，MySQL 用 hash join 扫它 **0.05 毫秒**，留着不影响性能，
但少一次应用层的查询。**优化的原则是"哪里慢改哪里"，不是"JOIN 越少越好"。**

## 五、⚠️ 今天最重要的发现：扫描行数变多了，反而更快

这是 `performance_schema` 读出来的真实数据（各跑 80 次）：

| 版本 | 平均耗时 | 平均扫描行数 |
|---|---|---|
| 改造前（三表 JOIN） | **43.38 ms** | **1,668** |
| 改造后（两表 JOIN） | **10.57 ms** | **5,568** |

**改造后扫描的行数是改造前的 3.3 倍，耗时却只有 1/4。**

### 为什么？——两种 I/O 的价钱完全不一样

| | 改造前 | 改造后 |
|---|---|---|
| 访问方式 | 600 次**点查**（每次跳到一个位置） | 1 次**范围扫描**（顺着索引往下读） |
| I/O 类型 | **随机 I/O**（要转盘、要寻道，慢） | **顺序 I/O**（连着读，快） |
| 一次能读多少 | 一行 | 一整段 |

打个比方：

> 随机 I/O 像**在图书馆里按索书号跑 600 个不同的书架各抽一本书**；
> 顺序 I/O 像**从一个书架上把一整排书全抱下来**。
> 后者一次抱 5,500 本，也比前者来回跑 600 趟快。

### 所以要记住这句

> **"扫描行数少" ≠ "快"。** 决定快慢的还有：是随机访问还是顺序访问、
> 要不要回表、有没有排序、数据在不在内存里。`rows` 只是一个参考值。

**面试时主动说出这个反例**，比背"`rows` 越小越好"高不止一个档次。

## 六、改造落地的四个细节（每一个都是考点）

### 6.1 区域名字改由 Java 侧补：`StatServiceImpl` 里发生了什么

```java
// ① SQL 只算 region_code + 总值
List<RegionMetricStatVO> rows = mapper.selectCategorySummary(category, periodType, periodCodes);

// ② 一次性把这批结果的区域名捞回来（1 次查询，不是 150 次）
Map<String, String> nameMap = loadRegionNameMap(
        rows.stream().map(RegionMetricStatVO::getRegionCode).toList());

// ③ 逐行补名字；补不到的丢掉
```

### 6.2 ⚠️ 最容易翻车的地方：**边界语义**

改造前那句 `JOIN dim_region ... AND r.deleted = 0`，除了"取名字"，
还**默默承担了一个业务规则**：**被删除的区域不能出现在统计结果里。**

去掉这个 JOIN 之后，这个规则就没人管了。所以 Java 侧补名字时，
**`nameMap` 里找不到对应区域的记录会被丢弃**，这样才和原语义等价。

> **一句话记住**：改写 SQL 时一定要问自己——
> "原来那些 JOIN / WHERE，除了过滤数据，还偷偷承担了什么语义？"
> 忘了这条，接口返回的条数会莫名其妙多出来几条，而且**不报错**，
> 只有用户会发现。你之前在 SPIMS 修的"统计数量和清单对不上"，多半就是这一类。

### 6.3 为什么不用 for 循环逐个查名字？——**N+1 问题**

```java
// ❌ 150 个区域 = 150 次数据库往返
for (RegionMetricStatVO row : rows) {
    row.setRegionName(regionMapper.selectNameByCode(row.getRegionCode()));
}

// ✓ 1 次查询搞定
regionService.listByCodes(codes);
```

这就是面试常问的 **N+1 查询问题**。识别方法极其简单：

> **看到 for 循环里写数据库查询，就要停下来想：能不能批量？**

这是"你项目里怎么优化性能"的第三个标准答案（前两个是索引、缓存）。

### 6.4 什么样的重复代码**不**该抽成公共方法

补名字这段逻辑现在出现了 **3 次**（三个接口各一遍），看着很重复。
但我**故意没抽**——因为三个方法的 VO 类型不同
（`RegionMetricStatVO` / `RegionRankVO` / `RegionYoyVO`），
要抽就得引入 `BiConsumer` 这类函数式参数，读起来反而更绕。

> **经验法则：重复 3 次的代码，如果抽出来之后变得**更难读**，那就先别抽。**
> "三行原则"是用来提醒你**留意**重复的，不是让你无脑抽取的。

## 七、新接口一：TOP N 区域排行（窗口函数）

### 7.1 请求与返回

```
GET /api/stat/top-regions?category=工业&periodType=Y&periodCodes=2024,2025,2026&topN=5
```

```json
[{"regionCode":"430806","regionName":"张家界第6区","totalValue":67757.3316,"rankNo":1,"share":1.03},
 {"regionCode":"430905","regionName":"益阳第5区","totalValue":63711.3076,"rankNo":2,"share":0.97},
 {"regionCode":"430102","regionName":"长沙第2区","totalValue":63282.0554,"rankNo":3,"share":0.97}]
```

### 7.2 核心：窗口函数（Window Function）

```sql
SELECT t.regionCode, t.totalValue,
       RANK() OVER (ORDER BY t.totalValue DESC)                 AS rankNo,
       ROUND(t.totalValue / SUM(t.totalValue) OVER () * 100, 2) AS share
FROM ( ...按区域分组的子查询... ) t
ORDER BY t.totalValue DESC
LIMIT #{topN}
```

**`OVER ()` 括号里什么都不写 = 把整个结果集当成一个窗口来算。**

### 7.3 窗口函数 vs `GROUP BY`（面试必问，必须分清）

| | `GROUP BY` | 窗口函数 |
|---|---|---|
| 对行数的影响 | **把多行压成一行**（150 行 → 150 个区域，明细没了） | **不改行数**，只给每行**多挂一列**结果 |
| 能同时看明细和汇总吗 | 不能 | **能** |
| 典型场景 | 汇总表 | 排行榜、占比、环比、开窗累计 |

一句话：**`GROUP BY` 是"合并"，窗口函数是"旁挂"。**

### 7.4 `RANK` / `DENSE_RANK` / `ROW_NUMBER` 三兄弟

假设三个区域的值是 **100 / 100 / 90**：

| 函数 | 结果 | 规则 |
|---|---|---|
| `ROW_NUMBER()` | 1, 2, 3 | 硬编号，值相同也分先后 |
| `RANK()` | **1, 1, 3** | 并列占位，后面**跳号** ← 我们用的这个 |
| `DENSE_RANK()` | **1, 1, 2** | 并列占位，后面**不跳号** |

排行榜的直觉是"并列第 1，下一名是第 3"，所以选 `RANK()`。

### 7.5 为什么外面要套一层子查询 `t`？

MySQL 的执行顺序是：

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY
```

`SELECT` 里算出来的聚合别名（`SUM(...) AS totalValue`）**在同一层的窗口函数里引用不到**。
所以先让子查询把"每个区域的总值"算出来，外层把 `t` 当普通表再做窗口计算。

> 经验：**窗口函数套在聚合结果之上时，套子查询最省心。**

### 7.6 一个容易有的错觉：`LIMIT` 不会让数据库少干活

```
LIMIT 是在**最后**才生效的。
150 个区域该聚合还得全聚合完、该排序还得全排完，只是最后只吐 5 行出来。
```

所以"加个 `LIMIT` 就变快"是错觉。真要让数据库少干活，得在 `WHERE` 上做文章。

## 八、新接口二：同比增长（条件聚合）

### 8.1 请求与返回

```
# 年同比：2025 vs 2024
GET /api/stat/yoy?category=工业&periodType=Y&basePeriod=2024&currentPeriod=2025

# 月环比：2026-03 vs 2026-02  ← 同一个接口，换参数就是环比
GET /api/stat/yoy?category=工业&periodType=M&basePeriod=2026-02&currentPeriod=2026-03
```

```json
[{"regionCode":"430102","regionName":"长沙第2区",
  "currentValue":16589.9550,"baseValue":18201.2779,
  "growth":-1611.3229,"growthRate":-8.85}]
```

### 8.2 同比和环比是同一件事

| 口径 | 基期 | 当期 |
|---|---|---|
| 同比 (YoY) | 去年同期（2024） | 今年（2025） |
| 环比 (MoM) | 上一个周期（2026-02） | 本期（2026-03） |

**代码一模一样，只是传进来的两个周期不同。**
所以只做一个接口，参数化即可 —— **别为"同比""环比"写两个接口。**

### 8.3 核心技术：条件聚合（Conditional Aggregation）

```sql
SELECT f.region_code AS regionCode,
       SUM(CASE WHEN f.period_code = #{currentPeriod} THEN f.indicator_value ELSE 0 END) AS currentValue,
       SUM(CASE WHEN f.period_code = #{basePeriod}    THEN f.indicator_value ELSE 0 END) AS baseValue
FROM ...
GROUP BY f.region_code
```

拆开看它在干嘛：

```
SUM(   CASE WHEN 周期 = 当期  THEN 值  ELSE 0  END   )
↑      └──────── 只挑出"这一档"的值，别的都当 0 ──────┘
└─ 然后把这批值加起来
```

**一次扫表，同时算出多个口径** —— 数据统计里最常用的手法之一。

**为什么不查两次库？** 两个值来自同一批数据、同一个 `WHERE`。
分两次查 = 两倍 I/O + 回到 Java 还得按 `region_code` 两边拼接（一边有一边没有时很容易对不齐）。

**⚠️ `ELSE 0` 千万别省。** 不写的话 `CASE` 返回 `NULL`，你就分不清
"这个区域当期真的是 0"和"当期压根没数据"。写 `ELSE 0` 是在**声明口径**。

### 8.4 整个项目最容易写错的三行：`BigDecimal`

```java
BigDecimal growth = current.subtract(base);          // 增长额：安全

BigDecimal growthRate = null;
if (base.compareTo(BigDecimal.ZERO) != 0) {          // 必须判除零
    growthRate = growth.multiply(HUNDRED)
                       .divide(base, 2, RoundingMode.HALF_UP);   // 三个参数一个都不能少
}
```

#### 死规矩一：`divide()` 必须给精度和舍入方式

```java
a.divide(b)                          // ❌ 遇到除不尽的数（如 100/3）直接抛异常
a.divide(b, 2, RoundingMode.HALF_UP) // ✓ 保留 2 位，四舍五入
```

抛的是 `ArithmeticException: Non-terminating decimal expansion; no exact representable decimal result`。
注意它是**抛异常**，不是返回近似值 —— 所以这行代码平时不报错，**只在特定数据下爆炸**，
是最典型的"埋雷"。

#### 死规矩二：舍入用 `HALF_UP`，别用默认的 `HALF_EVEN`

`HALF_EVEN` 是"银行家舍入"（逢 5 取偶）：`2.5 → 2`、`3.5 → 4`。
它在金融结算里是有道理的，但**报表上会让人觉得"算错了"**。

#### 死规矩三：比较大小用 `compareTo`，绝不用 `==` / `equals`

```java
base == BigDecimal.ZERO              // ❌ 比较的是对象地址，永远是 false
base.equals(BigDecimal.ZERO)         // ❌ "1.0" 和 "1.00" 会返回 false（scale 不同）
base.compareTo(BigDecimal.ZERO) == 0 // ✓ 值相等就是相等
```

#### 关于除零：返回 `null` 而不是 `0`

基期为 0 时，增长率**不是 0%，而是"没法算"**。
去年没有数据、今年有 100 万，这是"从无到有"，写成 0% 是严重误导。
所以返回 `null`，前端显示成 `--`。

> **在统计数据里，"0" 和"空"必须严格区分开。**

## 九、参数校验：fail fast（让错误在最靠近源头的地方暴露）

今天顺手把校验加固了一层，四条规则：

| 校验 | 触发 | 返回 |
|---|---|---|
| `periodType` 白名单 | 传 `X` / `y` / `年` | `periodType 只能是 Y（年）/ Q（季）/ M（月），本次传入：X` |
| `topN` 上限 100 | 传 `1000` | `topN 最大 100，本次传入 1000` |
| 基期 ≠ 当期 | 两个周期相同 | `基期和当期不能是同一个周期，否则增长率恒为 0，没有意义` |
| 解析后非空 | `periodCodes=,,,` | `periodCodes 解析后为空，请检查格式，如 2024,2025,2026` |

### 9.1 为什么 `periodType` 要做白名单？

因为它只有一个字符，写错太容易了。传 `"y"` 进 SQL 就是 `period_type = 'y'`——
**不报错，返回空数组**。调用方看到空数据，第一反应是"没数据啊"，
而不是"我参数写错了"，能 debug 半天。

### 9.2 为什么 `topN` 超限要报错，而不是"自动截断成 100"？

**因为静默改用户的参数是更坏的行为。** 前端传 500 以为拿到 500 条，实际只有 100 条，
这种 bug 最难查。宁可让他立刻看到错误。

### 9.3 为什么"基期=当期"要拦？

算出来增长率永远是 0%，**看起来完全正常，但毫无意义**。
这类"不报错但结果没意义"的参数最危险。

> **统一原则：宁可报错，也不要静默返回一个看起来对、其实错的结果。**
> 这叫 **fail fast** —— 让错误在最靠近源头的地方暴露。

### 9.4 校验要校验"处理之后"的结果

```java
List<String> codes = Arrays.stream(periodCodes.split(","))
        .map(String::trim).filter(s -> !s.isEmpty()).toList();
if (codes.isEmpty()) {   // ← 校验的是 split+filter 之后的结果
    throw new BizException("periodCodes 解析后为空…");
}
```

用户传 `",,,"`，原始输入非空，但解析完是空列表，拿去拼 SQL 会变成非法的 `IN ()`。
**校验必须落在"真正要用的那个值"上。**

## 十、今天怎么测的（方法可以复用）

### 10.1 `EXPLAIN ANALYZE` —— 排查慢查询的第一工具

```sql
EXPLAIN ANALYZE <你的 SQL>;
```

看得懂三件事就够：**哪个节点最慢**（看 `actual time` 的第二个数字）、
**执行了几次**（`loops`）、**处理了多少行**（`rows`）。

### 10.2 `performance_schema` —— 拿"不含网络开销"的纯 DB 耗时

Day 5 手册里介绍过。今天补一个技巧：**结构不同的 SQL 会被归成不同的 digest**，
所以可以直接对比两条 SQL：

```sql
SELECT ROUND(AVG_TIMER_WAIT/1000000000, 2) AS 平均ms,
       COUNT_STAR                           AS 执行次数,
       SUM_ROWS_EXAMINED DIV COUNT_STAR     AS 平均扫描行数,
       CASE WHEN DIGEST_TEXT LIKE '%dim_region%'
            THEN '改造前' ELSE '改造后' END  AS 版本
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT LIKE '%fact_indicator_value%'
ORDER BY AVG_TIMER_WAIT DESC;
```

### 10.3 端到端测量（含 HTTP）

```bash
for i in $(seq 1 40); do
  curl -s -o /dev/null -w "%{time_total}\n" "<你的 URL>"
done | tail -n 30 | awk '{s+=$1} END {print "平均 " s/NR*1000 " ms"}'
```

**取 40 次、丢掉前 10 次**：前几次包含 JVM 类加载和 JIT 编译，
不丢掉的话平均会被严重拉高（这叫"预热"）。

### 10.4 DB 侧快，端到端慢？——这是正常的，也是下一步的方向

```
DB 侧     10.57 ms
端到端    30.14 ms
────────────────────
差值      约 20 ms：Tomcat 收请求 → Spring MVC 路由 → MyBatis 映射 150 行
                    → 打 SQL 日志（application.yml 里开着 StdOutImpl！）
                    → JSON 序列化 → 网络回包
```

> ★ **优化到后面，瓶颈会从"数据库"转移到"应用层"。**
> 当你发现 SQL 只剩 10ms、接口却还要 30ms 时，就该换方向了 ——
> **Day 7 的 Redis 缓存，省掉的正是这 20ms 里的大头。**

## 十一、面试怎么讲（背这三句）

**① 讲问题（有数字、有证据）**

> "大屏聚合接口响应 43 毫秒。我用 `EXPLAIN ANALYZE` 看了真实执行计划，
> 发现聚合和排序只花 2 毫秒，42 毫秒全耗在一个嵌套循环上——
> MySQL 选了 600 次索引点查，而且查出 1350 行后还要逐行回表去区域维表换名称。"

**② 讲原因（有原理）**

> "根因是**关联的顺序**：SQL 里 JOIN 了区域维表，MySQL 只能在聚合**之前**就去关联，
> 导致 1350 行明细各查一次区域名。但聚合本来会把结果压成 150 行——
> 那这个关联就该放到聚合**之后**。"

**③ 讲方案和结果（有取舍、有反直觉的发现）**

> "我先把区域维表从 SQL 里去掉，改成在应用层用一次 `IN` 查询批量补名称，
> 耗时从 43 毫秒降到 10.6 毫秒。
> 有意思的是，**改造后扫描的行数反而从 1668 涨到了 5568**——
> 因为原来走的是 600 次随机点查，现在是一次顺序范围扫描，随机 I/O 比顺序 I/O 贵得多。
> 所以我没有只盯着 `rows` 这个指标。
> 我还试过把两个维表全去掉，能到 6 毫秒，但要在应用层拼 SQL 参数、可维护性下降，
> 权衡后没用——43 毫秒压到 10 毫秒，对一个大屏读接口已经足够了。"

**这三句话里有 8 个数字，每一个你都能当场打开 `sql/05-JOIN结构优化实验.sql` 给面试官看。**
