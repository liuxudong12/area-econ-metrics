## 一、先建立一个概念：为什么要分四层？

Day1 的 `/ping` 直接 `return "pong"`，不需要数据库。今天开始要碰数据库了，代码就得**分层**。

```
浏览器
  │  HTTP 请求  /api/region/list
  ▼
Controller   ← 只干两件事：接参数、返回结果。不碰 SQL。
  │
  ▼
Service      ← 业务逻辑写在这。比如"查区域要过滤掉已删除的"。事务也加在这。
  │
  ▼
Mapper       ← 只跟数据库打交道，一个方法对应一条/一组 SQL。
  │
  ▼
MySQL
```

**打比方**：Controller 是前台接待，Service 是业务员，Mapper 是仓库管理员。
前台不直接进仓库拿货，仓库管理员也不管客户要干什么。**每一层只做自己的事**，这就是"分层"。

为什么这么麻烦？因为：
- 改 SQL 不用碰 Controller（**改动扩散小**）
- 同一段业务逻辑可以被多个接口复用（**复用**）
- `@Transactional` 只有加在 Service 上才生效（**这是硬性技术原因**，加在 Controller 上不生效）

**面试被问"你项目怎么分层的"，答这条链路 + 上面三个理由，就够了。**

## 五、最值得看的三段代码

### 1）`Result.java` —— 为什么接口要包一层

所有接口都返回 `{code, message, data}` 这个固定形状。前端永远读这三个字段，不用为每个接口写不同解析逻辑。

```java
public static <T> Result<T> ok(T data) { ... }     // code = 0
public static <T> Result<T> fail(String message) { ... }  // code = 500
```

> **面试可能问**：成功为什么用 0，不用 200？
> 答：0 是**业务成功码**，和 HTTP 的 200 是两回事。HTTP 200 只代表"请求到达了服务器"，
> 业务是否成功要看 code。分开之后，HTTP 层负责"通信"，业务层负责"结果"，互不干扰。

### 2）`Region.java` —— 两个注解 + 一个"自动带条件"

```java
@Data
@TableName("dim_region")        // 告诉框架：这个类对应 dim_region 表
public class Region {
    @TableId(type = IdType.AUTO) // 主键，数据库自增
    private Long id;
    private String regionCode;   // 自动对应 region_code（下划线转驼峰）
    ...
    @TableLogic
    private Integer deleted;     // 逻辑删除
}
```

`@TableLogic` 是今天最值得记住的一个注解。加了它之后：
- 调 `deleteById(1)` → 实际执行的是 `UPDATE dim_region SET deleted=1 WHERE id=1`（**不是物理删除**）
- 调 `selectList(...)` → 自动变成 `SELECT ... WHERE deleted=0`

**作者实测的 SQL 日志，你可以自己核对：**

```
SELECT id,region_code,... FROM dim_region WHERE deleted=0 ORDER BY region_level ASC,sort ASC
                                                  ↑ 这个条件你一行都没写，框架自动加的
```

> **面试常问**：为什么用逻辑删除？
> 答：① 数据可追溯、可恢复，误删能救；② 关联数据不会变成孤儿；
> 注意点：查询必须带 `deleted=0`（所以靠框架统一处理最保险）；
> 另外**唯一索引要把 deleted 考虑进去**，否则"删掉的数据"会挡住"新插入的同样数据"。

### 3）`RegionServiceImpl.java` —— lambdaQuery() 是重点

对比两种写法：

```java
// ❌ 传统写法：字段名是字符串，写错了编译不报错，上线才炸
qw.eq("region_level", level).orderByAsc("sort");

// ✅ lambda 写法：字段名是方法引用，写错编译不过
lambdaQuery()
    .eq(Region::getRegionLevel, level)
    .orderByAsc(Region::getSort)
    .list();
```

还有个**非常实用的小技巧**——条件里的第一个参数当"开关"：

```java
.eq(level != null, Region::getRegionLevel, level)
```

意思是：`level` 不为空才拼这个条件，为空就跳过。
这样"查全部"和"按层级查"**共用一个方法**，不用写 if-else 两套。
（你在 SPIMS 里写的那些"组合查询"接口，本质上就是这个模式。）

> `.one()` 表示只取一条；查出多条会抛异常。区域编码有唯一索引，所以安全。

### 加分验收：去控制台数 SQL

访问第 3 条（分页）后，控制台应该出现 **2 条 SQL**：

```sql
SELECT COUNT(*) AS total FROM dim_region WHERE deleted = 0            -- 第①条：拿总数
SELECT id,region_code,... FROM dim_region WHERE deleted=0 ORDER BY ... LIMIT ?   -- 第②条：拿数据
```

**看到这两条，说明你理解了分页的本质。**（面试问"分页怎么实现的"，
答"插件先把 SQL 改写成 COUNT 查总数，再拼 LIMIT 查数据，所以一次分页实际是两条 SQL"，
这个回答比"用了 PageHelper" 强得多。）

## 七、可能遇到的报错（对照表）

| 报错 | 原因 | 怎么办 |
|---|---|---|
| `NoClassDefFoundError: net/sf/jsqlparser/...` | 没加 `mybatis-plus-jsqlparser` 依赖 | 检查 pom.xml，然后刷新 Maven |
| `Invalid bound statement (not found): ...RegionMapper.selectList` | Mapper 没被扫描到 | 检查 `MybatisPlusConfig` 上的 `@MapperScan("com.liuxudong.areaecon.mapper")` 包名是否写对 |
| `Unknown column 'xxx' in 'field list'` | 实体属性名和表字段对不上 | 核对名字（下划线→驼峰），或给属性加 `@TableField("字段名")` |
| `Communications link failure` | MySQL 服务没起 / 端口不对 | `net start MySQL`，确认 3306 在听 |
| `Access denied for user 'root'` | 密码不对 | `application.yml` 里密码应为 `Root@1234` |
| `Table 'area_econ.dim_region' doesn't exist` | 建表脚本没执行 | 重跑 `sql/schema.sql` |
| 返回 `data: []`（空数组） | 表建好了但没插数据 | 检查 `dim_region` 是否有 7 行 |
| 浏览器 404 | 包名放错位置了 | Controller 必须在 `com.liuxudong.areaecon` **及子包**下 |
