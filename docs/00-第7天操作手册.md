## 一、为什么 Day 7 该上缓存了

先回顾一下前两天的天花板：

| 时间 | 做了什么 | `/category-summary` |
|---|---|---|
| Day 4 | 原始版本（三表 JOIN） | 43.38 ms |
| Day 6 | 去掉 `dim_region` 的 JOIN，先聚合后补名 | **10.57 ms** |

**SQL 侧已经没什么可榨的了。** 但接口端到端的耗时是这样的：

```
HTTP 解析 → Tomcat 线程 → Spring MVC 分发 → 连接池借连接
→ MyBatis 映射参数 → 执行 SQL(10ms) → ResultSet 转 Java 对象
→ Java 补区域名（又一次查库）→ Jackson 序列化 JSON → 写回响应
```

Day 6 的对照实验其实已经暴露了这一点：**SQL 是 10.57 ms，端到端却是 30 ms**。中间那 20 ms 分散在框架和 I/O 上，你再怎么优化索引也动不了它们。

**唯一能让这 20 ms 也消失的办法，是根本不走这条路 —— 也就是缓存。**

而缓存对这个业务天生合适：

> 大屏挂在值班室墙上，100 个人看的是**同一条 URL**。
> 参数就是 `工业 + 年 + 2024,2025,2026`，结果在 10 分钟内不可能变。
> 第一次查库，后面 99 次完全一样 —— 不缓存就是把这套流程重复跑 99 遍。

## 二、缓存的核心就三段式（背下来）

所有缓存代码，无论什么框架、什么语言，骨架都是这三步：

```
1. 拼 key → 查 Redis
2. 命中 → 直接返回
   未命中 → 查数据库
3. 把查库结果写回 Redis（设 TTL）→ 返回
```

`@Cacheable` 注解、Spring Cache、MyBatis 二级缓存……**全都只是这三步的封装**。面试官问"`@Cacheable` 底层是什么"，标准答案就是"AOP 动态代理 + 一个拦截器，拦截器里执行的就是这三段式"。你要是只会背注解，这一问就露馅了。

所以我们手写。代码在 `cache/StatCacheHelper.java`，核心方法就一个：

```java
public <T> List<T> getList(String key, Class<T> elementType, Supplier<List<T>> loader)
```

- `key`：缓存键
- `elementType`：列表里元素是什么类型（反序列化要用）
- `loader`：**"怎么查库"**，用 lambda 传进来，**只有未命中时才会被执行**

用起来的业务代码就变成这样，短得几乎看不见缓存的痕迹：

```java
@Override
public List<RegionMetricStatVO> categorySummary(String category, String periodType, List<String> periodCodes) {
    String key = StatCacheHelper.buildKey(
            "category-summary", category, periodType, StatCacheHelper.joinSorted(periodCodes));
    return cache.getList(key, RegionMetricStatVO.class,
            () -> loadCategorySummary(category, periodType, periodCodes));
}
```

> **改造手法值得单独记一句**：把每个方法一劈两半 ——
> `public` 方法只管缓存，原来那段查库逻辑**一行不改**地搬进 `private` 方法。
> 这样"加缓存"这个动作对原有业务是**零风险**的，也对调用方完全透明（接口签名没动）。

## 三、坑 ①：序列化 —— 默认的 RedisTemplate 存进去的东西人看不懂

这是今天第一个必须搞懂的坑。

如果你直接 `new RedisTemplate()` 或者用 Spring 默认给的那个，它用的是 **JDK 序列化**（`JdkSerializationRedisSerializer`）。后果是你在 `redis-cli` 里 `GET` 出来的东西长这样：

```
"\xac\xed\x00\x05t\x00\x11stat:category-sum-\xac\xed\x00\x05sr\x00..."
```

一堆二进制乱码。**后果有三个：**

| 后果 | 说明 |
|---|---|
| ① 看不懂 | 线上出问题时你打不开缓存看内容，只能盲猜。这是最要命的 |
| ② 跨语言不通 | 你存的 Java 二进制，隔壁的 Python / Go 服务读不了 |
| ③ 改类就炸 | 给 VO 加个字段，反序列化老数据直接抛异常（`serialVersionUID` 不匹配） |

**解决办法**：用 `StringRedisTemplate`（key 和 value 都按字符串处理），再用 Jackson 自己把对象转成 **JSON 字符串** 存进去。

好处：`redis-cli` 里一眼读懂、任何语言都能读、加字段不影响老数据。代价：多写两行转换代码。

实测存进去的内容（可以直接看到了）：

```json
[{"regionCode":"430806","regionName":"张家界第6区","totalValue":2217905.9398}, ...]
```

> **一句话记忆**：
> `RedisTemplate` = 二进制，省事但不可观测；
> `StringRedisTemplate` + JSON = 可读、跨语言、可演进。
> **生产项目一律选后者。**

## 四、坑 ②：key 怎么设计（三条规则，每条都有实测证据）

key 设计错了，缓存不但不生效，还会**返回错误的数据**——而且不报错。

### 规则 1：凡影响结果的入参，一个都不能漏

今天的 `top-regions` 接口有个 `topN` 参数。如果 key 里不带它：

```
先请求 topN=5  → 缓存了 5 条
再请求 topN=10 → 直接返回那 5 条   ← 用户要 10 个，只给 5 个，还不报错
```

**实测证据**（用命中计数验证）：

```
查 topN=5   → hit 差值 = 0  （未命中，生成了新 key ✓）
再查 topN=10 → hit 差值 = 1 （命中了 topN=10 自己的缓存 ✓）
```

Redis 里确实多出一个 key：

```
stat:top-regions:工业:Y:2024,2025,2026:5
stat:top-regions:工业:Y:2024,2025,2026:10
```

> **缓存串数据的头号原因就是"key 少带了参数"。**
> 自检方法：把 SQL 里所有会变的输入列出来，一个个对，看 key 里有没有。

### 规则 2：顺序无关的参数要排序（否则缓存利用率砍半）

`periodCodes=2024,2025,2026` 和 `periodCodes=2025,2024,2026` 查出来的结果**完全一样**。如果不排序，就会生成两个 key，缓存白存一份。

所以 `joinSorted()` 会**去重 + 排序**再拼接：`["2025","2024"]` → `"2024,2025"`。

**实测证据**：

```
传 periodCodes=2025,2024,2026（故意打乱顺序）
hit: 240 → 241   差值 = 1   ← 命中了已有的 2024,2025,2026 缓存 ✓
```

### 规则 3：角色不同的参数**绝对不能**排序（这条最反直觉）

`/yoy` 接口有两个周期参数：`basePeriod`（基期，做分母）和 `currentPeriod`（当期，做分子）。

**它们不能像上面那样排序、去重、当成集合。** 因为：

```
(基期=2024, 当期=2025) → 增长 +20%
(基期=2025, 当期=2024) → 增长 -16.7%     ← 完全不同的结果
```

如果偷懒写成 `joinSorted(List.of(basePeriod, currentPeriod))`，这两个会被拼成同一个 key，第二个请求会命中第一个的缓存 —— **增长率直接算反，接口还不报错**。

**实测证据**：

```
查 base=2024 current=2025 → hit 差值 = 1（命中 ✓）
查 base=2025 current=2024 → hit 差值 = 0（未命中，生成新 key ✓）
```

Redis 里是两个不同的 key：

```
stat:yoy:工业:Y:2024:2025
stat:yoy:工业:Y:2024... → 实际为 stat:yoy:工业:Y:2025:2024
```

> **判断标准就一句话**：
> **把两个值交换一下，SQL 的结果会不会变？**
> 会变 → 是"角色"，固定位置拼，不许排序。
> 不变 → 是"集合"，排序去重后拼。

### 补充：为什么 key 用 `:` 分隔？

这是 Redis 社区约定（Spring Data Redis 的 `RedisCache` 也默认用它）。

好处：`redis-cli` 的图形客户端（如 Another Redis Desktop）会把冒号渲染成**树形目录**：

```
stat
└── category-summary
    ├── 工业:Y:2024,2025,2026
    └── 不存在的分类:Y:2024
```

一眼就能看出 key 的组织结构。同时它也方便做"按前缀批量删"（Day 8 会用到）。

## 五、TTL：为什么必须有，以及为什么要"抖一下"

**TTL（Time To Live）= 这个 key 多久后自动消失。**

为什么缓存必须设 TTL？设想两种极端：

- **不设 TTL**：一旦数据变了，缓存永远脏，除非有人手动删 —— 迟早出事
- **TTL 设太长**（比如 24 小时）：数据更新后，用户有 24 小时看到的是旧数据
- **TTL 设太短**（比如 5 秒）：基本每次都过期，等于没缓存

我们用 **600 秒（10 分钟）**。理由：大屏数据是"小时级"更新的，10 分钟内看到旧数据业务上可以接受。

### 但光有 TTL 还不够，要加随机抖动

设想 1000 个 key 是同一时刻写入、TTL 都是整齐的 600 秒 —— 它们会在**同一秒集体过期**。那一秒所有请求同时穿到数据库，数据库瞬间被打垮。这叫 **缓存雪崩**。

解决办法：**在基础 TTL 之上加一个随机数**。

```java
private long ttlWithJitter() {
    return DEFAULT_TTL_SECONDS + ThreadLocalRandom.current().nextLong(TTL_JITTER_SECONDS + 1);
    //     600 + 0~60 秒随机
}
```

**实测证据**（连删 5 次，每次都看回填后的 TTL）：

```
第 1 次回填后 TTL = 658 秒
第 2 次回填后 TTL = 642 秒
第 3 次回填后 TTL = 626 秒
第 4 次回填后 TTL = 604 秒
第 5 次回填后 TTL = 623 秒
```

**每次都不一样 —— 抖动生效了。** 这样 1000 个 key 的过期时间会散落在 600~660 秒之间，压力就被摊平了。

> 面试话术：**"我给 TTL 加了随机抖动，把'集体过期'摊成 60 秒的窗口，避免雪崩。"**
> 就这么一句话，比背"雪崩的三种解决方案"实在得多，因为你是真做了。

## 六、空值缓存：防穿透，顺手就做了

**缓存穿透**：一直查一个**数据库里根本不存在**的东西。

```
攻击者/前端 bug 疯狂请求 category=乱码
→ 缓存里没有（因为从没存过）
→ 每次都穿到数据库
→ 缓存形同虚设
```

**解法：查库结果是空的时候，"空"这个结论也要缓存起来。**

我们的实现里，空结果写一个**空字符串哨兵**，TTL 只给 60 秒：

```java
if (data == null || data.isEmpty()) {
    redis.opsForValue().set(key, NULL_SENTINEL, Duration.ofSeconds(NULL_TTL_SECONDS)); // 60 秒
}
```

### 这里有个**必须分清**的区别（很多人写错）

```java
redis.get(key) == null      // key 不存在 —— 从未缓存过，或已过期  → 要查库
redis.get(key).isEmpty()    // key 存在，值是"特意缓存的空结果"  → 直接返回空
```

这两件事完全不同。分不清就会把空值缓存写坏：要么空结果没缓存住（照样穿透），要么把"没缓存"误判成"空结果"（返回错误的空数据）。

### 为什么空值的 TTL 要比正常数据短得多？

因为**"空"这个结论可能很快就不成立了**。比如运维刚导入了一批新分类的数据，10 分钟的空缓存会让用户以为"数据没进去"。

正常数据 600 秒、空数据 60 秒 —— **用不同的 TTL 表达"我对这个结论有多确信"**。

**实测证据**：

```
第 1 次请求 category=不存在的分类  → {"code":0,"data":[]}
  key 是否存在：1        （存在 ✓）
  key 的值长度：0        （空字符串哨兵 ✓）
  key 的 TTL  ：60 秒    （比正常数据的 600 短得多 ✓）
第 2 次请求 → 直接返回空，完全不查库
```

|---|---|---|---|

| `/trend` | 16.8 ms | **4.67 ms** | **3.6×** |

| `/yoy` | 25.2 ms | **6.48 ms** | **3.9×** |

### `/category-summary` 的精细数据

```
MISS（每次先删 key 再请求，5 次）：30.8 / 28.5 / 24.5 / 25.1 / 27.2 ms
HIT （连打 30 次）：平均 5.15 ms | 最小 2.48 ms | 最大 26.95 ms
```

### 最硬的一条证据：**缓存命中时，数据库访问次数 = 0**

方法：清空 MySQL 的 SQL 统计账本（`performance_schema.events_statements_summary_by_digest`），
然后连打 50 次请求（全部 HIT），再查账本：

```
总SQL条数             2
碰过 fact 表的SQL条数  0     ← 关键
碰过 dim  表的SQL条数  0     ← 关键
```

**50 次请求，一条 SQL 都没发出去。** 这比任何"快了 X 倍"都更有说服力 —— 因为它证明的不是"变快了"，而是**"数据库根本没参与"**。

### 缓存层自身的耗时：0.68 ms

服务日志里 HIT 的真实打点：

```
[缓存] HIT  key=stat:top-regions:工业:Y:2024,2025,2026:10 条数=10 耗时=0.6804ms
```

也就是说：读 Redis + JSON 反序列化的开销只有 **0.68 ms**。
端到端那 4.5 ms 里剩下的部分，是 Tomcat + Spring MVC + curl 客户端的固定开销。

### 累计命中率

```
hit=240 miss=17 命中率=93.4%
```

> **注意这个数字的真实含义**：命中率不是越高越好。
> 如果一开始就 100%，说明缓存压根没被写进去过（因为你总要 miss 一次才能填进去）。
> 有 miss、且随时间收敛到 90%+，才是**健康**的。

### ⚠️ 环境坑：Windows 下 redis-cli 传中文 key 会失败

**这个问题今天真实踩到了**，浪费了一轮测试。表现是：

```bash
K="stat:category-summary:工业:Y:2024,2025,2026"
redis-cli exists "$K"    → 返回 0     ← 明明 scan 里能看见这个 key！
```

原因：Git Bash 用 UTF-8 传参数，但 Windows 原生 exe 按 ANSI(GBK) 解析，`工业` 这三个字节被解错了。

**正确姿势 —— 用 stdin 传参（`-x`）：**

```bash
printf '%s' "$K" | redis-cli -x exists     → 返回 1  ✓
printf '%s' "$K" | redis-cli -x ttl        → 返回 624 ✓
printf '%s' "$K" | redis-cli -x del        → 删掉 ✓
printf '%s' "$K" | redis-cli -x strlen     → 0（空值哨兵）✓
```

**排查手法**（通用）：

```bash
redis-cli exists "key"            # 命令行传参
printf '%s' "key" | redis-cli -x exists   # stdin 传参
```

两个结果不一致 → 就是编码问题，不是 Redis 的问题。

> 顺带说：这只是**本地命令行工具**的问题。
> Java 代码走 TCP 直接发 UTF-8 字节，**完全不受影响**——所以服务端一切正常。

## 九、缓存三大问题：今天解决了两个

面试必问"缓存穿透、击穿、雪崩"，今天已经顺手做了两个：

| 问题 | 是什么 | 今天怎么解决的 |
|---|---|---|
| **穿透** | 查不存在的数据，每次都打库 | ✅ **空值缓存**（空结果也存，TTL 短） |
| **雪崩** | 大量 key 同时过期，数据库被打垮 | ✅ **TTL 随机抖动**（600 + 0~60 秒） |
| **击穿** | **某个热点 key** 过期瞬间，几百个请求同时查库重建 | ⏳ **Day 8 做**（互斥锁 / 逻辑过期） |

**穿透 vs 击穿的区别**（容易混）：

- 穿透：查的是**不存在**的数据 → 缓存永远不命中 → 靠**缓存空值**挡
- 击穿：查的是**存在且很热**的数据，只是**刚好过期了那一瞬间** → 靠**加锁**让别人等

## 十、今天的自测题

**Q1. 为什么用 Redis 之后，`/category-summary` 的 MISS 还要 23ms？为什么不能降下来？**

<details>
<summary>点开看答案</summary>

因为 MISS 走的就是**没缓存的完整路径**：HTTP + Spring MVC + 连接池 + SQL(10.5ms)
+ Java 补区域名（又一次查库）+ JSON 序列化。

缓存不会让这条路变快 —— 它的价值是**让后续请求绕开这条路**。
所以你看数据的时候要看两个数：
- **MISS**：证明"缓存没有让事情变慢"（23.3ms vs 原来的 30.1ms，甚至还快了一点，因为不再每次重建对象）
- **HIT**：证明"缓存真的省掉了什么"（5.37ms，且数据库零访问）

**面试时两个数都要报，只报 HIT 会显得不诚实。**
</details>

**Q2. 缓存命中率 93.4%，是越高越好吗？**

<details>
<summary>点开看答案</summary>

不一定。命中率要结合**场景**看：

- 如果业务是"每次参数都不同"（比如按身份证号查），命中率天然就低，**这很正常**，不该硬凑；
- 如果命中率一开始就是 100%，反而**有问题**——说明你可能压根没写进缓存，或者 TTL 设得太长导致数据不更新；
- 真正的判断标准是：**"这段时间内，相同的 key 被请求了多少次？"** 这个比例才是命中率的理论上限。

另外命中率要按 key 维度观察：**少数热点 key 贡献了大部分命中**。整体 93% 可能掩盖了"长尾 key 全部 miss"的情况。
</details>

**Q3. 为什么 `hasKey()` 不能用来判断缓存是否存在？**

<details>
<summary>点开看答案</summary>

因为 `hasKey()` 和 `get()` 是**两次**独立的 Redis 请求（两次网络往返）。

假设有人在这两次请求之间把 key 删了 —— 你 `hasKey()` 得到 true，`get()` 返回 null，
代码就炸了。这叫 **TOCTOU（Time-of-check to time-of-use）竞态**。

正确做法：**只做一次 `get()`，用返回值判断**：
- 返回 null → 没缓存
- 返回非 null 且为空串 → 缓存了空结果
- 返回非 null 且有内容 → 命中

我们的 `StatCacheHelper` 就是这么写的，一次请求解决。
</details>

**Q4. 如果 Redis 挂了，这个接口会怎样？**

<details>
<summary>点开看答案</summary>

**会降级到直接查库，接口仍然返回正确结果 —— 而且这是实测过的。**

代码里有两处保护：

1. **读缓存**：`get()` 外面包了 `try-catch (RuntimeException)`，失败就记一笔 WARN、
   把结果当"未命中"处理，继续查库；
2. **回填**：同样包了 `try-catch`，失败只记日志，照常返回数据库结果。

### 实测证据

让应用去连一个**不存在的 Redis 端口**（`--spring.data.redis.port=6399`），
四个接口的表现：

```
① /category-summary → HTTP 200  耗时 42.7 ms  （数据完整正确）
② /trend            → HTTP 200  耗时 42.7 ms
③ /yoy              → HTTP 200  耗时 33.3 ms
④ /top-regions      → HTTP 200  耗时 22.9 ms
```

耗时涨回 MISS 水平（22~43ms）—— 因为每次都老老实实查库了。**但接口没挂。**

服务日志：

```
WARN [缓存] 读取失败，降级为直接查库。key=stat:category-summary:工业:Y:2024,2025,2026 原因=Unable to connect to Redis
WARN [缓存] 回填失败，本次直接返回数据库结果（不影响业务）。key=stat:yoy:工业:Y:2024:2025 原因=Unable to connect to Redis
```

### 为什么这条比"快了 X 倍"更值得讲

**缓存设计的第一原则：缓存是锦上添花，不是必需品。**

缓存挂掉时，系统的正确行为是**"变慢"**（退化成每次查库），而不是**"报错"**。
很多线上事故就是把 Redis 当成了强依赖 —— 缓存一抖，整个服务全 500。

> 可以这样讲给面试官：
> **"我特意把 Redis 停掉测过一次：四个接口全部正常返回，只是耗时退回到查库的水平。
> 因为我给缓存读和写都加了降级，缓存失败只记日志、不影响业务。"**

**知道有这回事但没做的**：如果 Redis 持续不可用，每次请求都会白等一次超时 + 刷一条 WARN 日志。
生产做法是加**熔断开关**（连续失败 N 次后，直接跳过缓存 30 秒再试探），
可以用 Resilience4j 的 `CircuitBreaker`，也可以自己用计数器实现。
</details>

**Q4-补. 那读缓存那一步的 `try-catch` 是本来就有，还是后来补的？**

<details>
<summary>点开看答案</summary>

**是后来补的 —— 而且这是今天最有价值的一段过程。**

第一版代码里，回填有保护、**读缓存那一步漏了**。写自测题的时候才发现：
"如果这里 Redis 挂了会怎样？" —— 答案是会抛异常 → 接口 500。

**这个自查习惯比代码本身重要。** 具体怎么自查：

> 每一段调用了**外部依赖**（Redis / HTTP / MQ / 文件）的代码，都问一句
> **"它挂了会怎样？"** 然后决定是"往上抛"还是"就地降级"。
>
> 判断标准：
> - 这个依赖是**核心链路**（比如数据库）→ 挂了就该报错，让上游知道
> - 这个依赖是**加速器**（比如缓存）→ 挂了必须降级，绝不能拖垮业务
</details>


**Q5. 为什么 `StatCacheHelper.getList` 要传 `elementType`（如 `RegionMetricStatVO.class`）？**

<details>
<summary>点开看答案</summary>

因为 **JSON 是"无类型"的**。

反序列化 `[{"regionCode":"..."}]` 时，Jackson 只知道"这是个数组，元素是对象"，但它
**不知道这些对象该变成什么 Java 类**。你不告诉它，它只能给你 `List<LinkedHashMap>` ——
编译期就报错了。

所以我们传 `RegionMetricStatVO.class`，再构造出 `JavaType`：

```java
objectMapper.getTypeFactory().constructCollectionType(List.class, elementType)
```

这就是**泛型擦除**带来的代价：运行时 `<T>` 已经不存在了，必须由调用方显式传类型。
</details>

**Q6. 今天缓存加在 Service 层而不是 Controller 层，为什么？**

<details>
<summary>点开看答案</summary>

三个理由：

1. **职责**：Controller 管"接参数、转结果"，不该管数据从哪来；
2. **复用**：同一个查询可能被多个 Controller 调用（大屏、报表导出、定时预热），
   只有加在 Service 才能覆盖全部入口；
3. **兜底**：加在 Service 意味着**没有别的入口能绕过缓存**。

一句话：**缓存是数据访问策略，属于数据层的事。**
</details>

## 十二、两个配置上的坑（顺手记下来）

### 坑 1：`spring.redis` → `spring.data.redis`

| 版本 | 配置路径 |
|---|---|
| Spring Boot 2.x | `spring.redis.host` |
| Spring Boot 3.x | `spring.**data**.redis.host` |

写成老路径**不报错**，只是配置完全不生效，然后连到默认的 `localhost:6379`。
本地刚好也是 localhost:6379，所以你**根本发现不了** —— 但一上服务器就崩。

> 通用教训：**Spring Boot 大版本升级时，配置项改名是最容易被忽略的破坏性变更。**

### 坑 2：连接池配置需要 `commons-pool2` 才生效

`application.yml` 里写：

```yaml
spring.data.redis.lettuce.pool.max-active: 16
```

**如果 pom 里没有 `org.apache.commons:commons-pool2`，这段配置会被静默忽略**（不报错！），
Lettuce 走它默认的"全应用复用一条连接"模式。

**判断标准**：启动日志里如果完全没有 pool 相关的内容，大概率就是没生效。
所以 pom 里那个 `commons-pool2` 依赖是**必须加的**，不是可选的。
