# 第 8 天操作手册 · Redis 缓存（写通路 + 击穿防护）

> 昨天做完了"读"：4 个统计接口全部接上缓存，命中时数据库压力直接归零。
> 但缓存只进不出，就会变成**谎言的放大器** —— 数据改了，用户还在看 10 分钟前的旧数字。
>
> 今天做两件事：
> **① 让缓存能失效**（数据变更 → 清缓存，而且要清得对、清得准）；
> **② 扛住并发**（热点 key 过期的一瞬间，别让数据库被同一个查询打几十下）。

---

## 一、先想清楚一个问题：谁该负责清缓存？

答案很简单，但很多人做错：**改数据的那个人负责清。**

为什么？因为只有他**确切知道**"什么时间、改了什么"。让统计侧去猜（比如定时轮询维表）既慢又不可靠。

本项目里，改动会影响到统计结果的只有一处：**`dim_region` 的增删改**。

```
dim_region 改了名字
   → /category-summary 返回的 regionName 是错的
   → /top-regions      返回的 regionName 是错的
   → /yoy              返回的 regionName 是错的
```

所以清缓存的动作写在 `RegionServiceImpl` 里，不在 `StatServiceImpl` 里。

> **面试可能会问**："区域服务凭什么管统计缓存？这不是耦合吗？"
> 答：这不是耦合，是**归属**。数据的所有者天然知道它什么时候变了。
> 真正的解耦方案是**订阅 binlog**（Canal / Debezium），应用完全不感知，
> 由独立进程监听数据库变更日志去删缓存 —— 那是"规模上来以后"的方案（见第七节）。

## 二、清缓存最容易踩的坑：在事务里面清

这是今天**最重要**的一段，也是缓存一致性的核心事故场景。先看错误写法会发生什么：

```java
@Transactional
public void updateRegion(...) {
    updateById(update);      // ① 数据库已改，但事务没提交
    cache.evictAllStat();    // ② 缓存删了
}                            // ③ 方法结束，事务才提交
```

看起来没问题？把时序展开，灾难就出来了：

```
时间 →
更新线程:  [① UPDATE 执行完，未提交]──[② 删缓存]──────────────[③ 提交]
读线程:                          [缓存空→查库→读到【旧值】]→[把旧值写回缓存]
                                                              ↑
                                        结果：缓存里躺着旧值，还要躺 600 秒
```

**根因一句话**：`删缓存` 和 `事务提交` 之间存在一个时间窗，读线程可以挤进这个窗口，
把**还没提交的旧值**重新灌回缓存。这叫"缓存回填脏数据"，比"忘删缓存"更难查 ——
因为缓存明明被删过，日志里还有记录。

### 正确做法：`afterCommit`

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {          // ← 事务真正提交之后才执行
        cache.evictAllStat();
    }
});
```

用在本项目里就是 `RegionServiceImpl.evictStatCacheAfterCommit(...)`。

两个细节值得记住：

1. `isSynchronizationActive()` 先判断"当前有没有事务"。正常走 Controller 一定有；
   万一这个方法被别的非事务方法直接调用，就没有事务，此时立刻删是对的。
2. **`afterCommit` 里抛异常不会回滚业务**（此时已经提交完了）。这正是我们想要的：
   删缓存失败最多让脏数据撑到 TTL 到期，绝不能让"改数据成功"变成"改数据失败"。

## 三、"先删缓存"还是"后删缓存"？别背结论，讲清失败场景

这是缓存一致性的必考题。标准答法不是给个结论，而是**说清两条路各自怎么坏**：

| 顺序 | 出问题的场景 | 后果 |
|---|---|---|
| **先删缓存 → 再更新库** | 删完、库还没更新时，读线程查库拿到旧值并回填 | 脏数据躺到 TTL 到期，窗口大（更新库在事务里要几十毫秒） |
| **先更新库 → 再删缓存**（本项目采用） | 读线程恰好在"提交后、删缓存前"读了旧缓存 | 下一次请求前缓存就被删了，窗口极小 |

Facebook 那篇 *Scaling Memcache at Facebook* 推荐的就是**后删**，本项目一致。

### 那网上说的"延迟双删"呢？

```
更新库 → 删缓存 → 睡 500ms → 再删一次
```

第二次删是为了把"这期间别人回填的旧值"再清一次，主要用来兜**主从延迟**
（写主库、读从库，从库还没同步完就被读到旧值）。

但要清楚它的毛病：**"睡"这个动作很脏** —— 阻塞线程、时间靠猜、睡多久没有理论依据。
所以它是补丁，不是方案。真实项目里更常见的组合是：

- 缓存只放"变不动的字典数据"（区域、指标这类维表，本项目正好是这种）；
- 或者订阅 binlog 异步失效；
- **接受"最终一致 + 窗口尽量小"，而不是追求强一致。**

> 谁跟你说"我用 Redis 给业务数据做到了强一致"，基本可以判定他没真做过。
> 缓存和强一致天生矛盾，能做的是把不一致窗口压到毫秒级、并且有兜底 TTL。

## 四、批量删缓存：为什么绝对不能用 `KEYS`

数据一变，需要删的不是一个 key，而是"这一类" key：

```
stat:category-summary:工业:Y:2024,2025,2026
stat:trend:工业:Y:2024,2025,2026
stat:top-regions:工业:Y:2024,2025,2026:10
stat:yoy:工业:Y:2024:2025
...
```

看着像 `KEYS stat:*` 一行搞定？**千万别。**

> Redis 是**单线程**的。`KEYS` 会一次性遍历整个库的所有 key，
> 遍历期间**其它所有命令全部阻塞**。库里有几百万 key 时，
> 一条 `KEYS` 能让 Redis 卡住几百毫秒到几秒，全站接口跟着抖。
> 这是"一个命令搞垮 Redis"的最经典案例，很多公司直接在配置里禁掉它。

正确做法是 `SCAN`：**游标式分批扫描**，每次只扫一小批（本项目 500 个），
扫完把游标还给你，你拿着游标继续扫，直到游标回到 `0`。

```java
try (Cursor<String> cursor = redis.scan(
        ScanOptions.scanOptions().match("stat:*").count(500).build())) {
    // 边扫边分批删，每批 500 个
}
```

`SCAN` 的代价是**不保证快照一致**（扫描期间新增/删除的 key 可能漏掉或多出）。
但对"删缓存"完全够用 —— 漏掉的那一条本来就会自己过期。

### 一个容易被忽略的设计点：锁的 key 不能放在 `stat:` 下面

```java
private static final String LOCK_PREFIX = "lock:stat:";   // ✅
// 如果写成 "stat:lock:"，一次 evictAllStat() 会把别人正持有的锁删掉，互斥直接失效
```

**命名空间隔离**是 key 设计里最容易漏、又最容易埋坑的一条。

## 五、清多少？"全清"还是"精准清"？

本项目的选择是**全清**（`evictAllStat`），理由：区域名变了会影响所有含这个区域的统计结果，
而这些 key 里**没有 region_code**（region_code 是查询结果的列，不是入参），
想把"受影响的 key 组合"枚举出来不现实。

但"全清"不等于"每次都清"。**能判断的时候一定要判断**：

```java
boolean nameChanged = !Objects.equals(old.getRegionName(), reqVO.getRegionName());
boolean codeChanged = !Objects.equals(old.getRegionCode(), reqVO.getRegionCode());
if (nameChanged || codeChanged) {
    evictStatCacheAfterCommit(...);
} else {
    log.info("[一致性] 区域 id={} 的修改不影响统计字段，跳过清缓存", id);
}
```

因为统计只用到区域的两个字段：`region_code`（关联）和 `region_name`（显示）。
只改 `sort` / `parentCode` / `regionLevel`，统计结果**一模一样**，缓存不用动。

为什么值得较真？因为"清缓存"不是免费的：清完之后下一次请求必然未命中、
还要抢锁、还要查库。**清得太随意，缓存就变成了"永远在失效"，等于没做。**

> 一句话原则：**失效范围按"哪些查询结果真的变了"来定，不能一律清空。**

### 三种写操作的处理（本项目实测过）

| 操作 | 是否清 | 原因 |
|---|---|---|
| 新增区域 | 清 | 多数时候可以省（新区域在 fact 表没数据），但存在边界：以前逻辑删除过、现在用同一个 code 建回来，历史数据会立刻重新出现在统计里 |
| 修改区域 | **看字段** | 名称/编码变了才清，只改 sort 不清 |
| 删除区域 | 必清 | 结果集本身变了（150 条变 149 条，那个区域整条消失） |

## 六、缓存击穿：三个"穿"要分清

| 名字 | 是什么 | 解法 | 本项目 |
|---|---|---|---|
| 穿透 | 查**根本不存在**的数据，缓存永远不可能命中 | 缓存空值 | Day 7 已做 |
| 击穿 | **一个热点 key 过期瞬间**，并发同时冲去查库 | 互斥锁 | **今天做** |
| 雪崩 | **大批 key 同时过期**（或 Redis 挂了） | TTL 抖动 + 高可用 | Day 7 已做 |

### 击穿到底怎么发生的

```
key 刚好过期，此刻 50 个请求同时进来：
  50 个线程都执行"查缓存" → 都是 null → 50 个都去查库
查库只要 20ms，但已经足够 50 个请求挤进"缓存已删、数据未回填"这个窗口
```

### 锁要加对，三个要点缺一不可

1. **必须是 SETNX**（`setIfAbsent`）—— "不存在才写入"，天然互斥；
2. **必须带过期时间** —— 否则持锁线程一崩，锁永远留着，所有人卡死（死锁）；
3. **释放时必须比对 value + Lua** —— 只删"自己那把锁"，且比对和删除要原子。

第 3 点展开讲，因为它最容易写错：

```
A 抢到锁 → A 卡住超过 10 秒 → 锁 TTL 到期自动释放 → B 抢到锁
→ A 醒来执行 del → 把 B 的锁删了 → C 又能抢到锁 → 互斥彻底失效
```

所以解锁要写成 Lua：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

### 抢不到锁的线程干什么？—— 等，但**有时间上限**

```java
if (lockState == LOCK_BUSY) {
    String waited = waitForCache(key);   // 每 50ms 看一次，最多 20 次（约 1 秒）
    if (waited != null) return decode(waited, ...);   // 别人填好了，直接读
    // 1 秒还没好 → 自己查库（降级，绝不死等）
}
```

为什么不等到底？因为**可用性优先于最优解**。持锁线程可能卡住了，
不能让其余 49 个请求陪它一起挂。

### 抢到锁后还要再查一次缓存（double-check）

从"第 1 步查缓存"到"真的抢到锁"之间已经过了几毫秒，这期间别人可能已经填好了。
再查一次能挡掉一批重复查库。

## 七、实测数据

### ① 击穿防护 A/B 对照（50 并发打同一个冷 key）

用 `tools/cache-stampede-test.py`（多线程 + Barrier，所有线程卡在同一起跑线）。
**关键指标不是耗时，而是"数据库被执行了几次"**（用 `performance_schema` 账本统计）。

| 组 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| **A：防击穿开启** | **1 次** | **1 次** | **1 次** |
| B：防击穿关闭 | 50 次 | 39 次 | 38 次 |

应用侧计数（A 组三轮累计）：`抢锁失败(去等待)=138 等待超时降级=0` ——
说明 138 个请求确实去排队等别人回填了，而不是各自查库。

> 为什么 B 组后面两轮是 39/38 而不是 50？因为部分请求到达时，
> 第一个线程已经把缓存填好了 —— 它们"捡了便宜"。真实压测里这个数字取决于并发度。
> 所以看**量级**（50 vs 1），不要纠结精确值。

### ② 耗时对照（顺便暴露一个真相）

| 场景 | 平均耗时 |
|---|---|
| 50 并发，全部命中缓存 | 26.6 ms |
| 50 并发，冷 key + 防击穿开启 | 57.8 ~ 72.9 ms |
| 50 并发，冷 key + 防击穿关闭 | 89.4 ~ 105.9 ms |

**注意 A 组（加锁）反而比 B 组（不加锁）更快**，但这不是普遍规律 ——
本地 MySQL 太快（10ms），B 组 50 个并发查库把连接池和 CPU 挤爆了才慢下来。
换成生产上数据库几十毫秒 + 连接池只有 10 个，差距会更大。

**更诚实的说法**：互斥锁的收益是**保护数据库**，不是降低自己的延迟。
等待方每 50ms 才醒一次，单个请求看是"多等了几十毫秒"。
面试时把这句话说出来，比只说"我提升了性能"可信得多。

### ③ 一致性验证（改区域名 → 缓存自动失效）

| 步骤 | 结果 |
|---|---|
| 请求 `/category-summary`，缓存里是 `张家界第6区` | ✓ |
| `PUT /api/region` 改名成 `张家界第6区-改名验证` | 返回成功，日志出现 `[一致性] 事务已提交，开始清理统计缓存` |
| 立刻 `SCAN` 看 Redis | **空了**（缓存被删干净） |
| 再请求接口 | 返回 `张家界第6区-改名验证` ✓ |
| 只改 `sort`（不影响统计） | 缓存 key 数 **1 → 1 不变**，日志 `跳过清缓存` ✓ |

### ④ Redis 挂了还能不能活（今天修了一个真 bug）

第一版代码有个隐患：Redis 读缓存已经抛异常了，代码还去**抢锁**、抢不到再**等 1 秒**。
结果 Redis 一挂，每个请求白白多花 1 秒 —— 没报错，但慢了 50 倍。

修法：读缓存失败就把 `redisHealthy` 置 false，后面**既不抢锁也不等待**，直接查库。

| 场景 | 修复前 | 修复后（实测） |
|---|---|---|
| Redis 不可用时 `/trend` | 约 1000 ms/次 | **平均 23 ms，最大 30 ms** |

用 `--spring.data.redis.port=6399`（指向一个不存在的端口）验证，
日志里每个请求只有一条 `[缓存] 读取失败，降级为直接查库`，
**没有** `抢锁异常` —— 证明抢锁真的被跳过了。数据完全正确。

> 这条经验很值钱：**降级路径本身也要测。**
> 大部分人只测"Redis 正常时快不快"，不测"Redis 挂了会不会更糟"。
> 而线上事故恰恰发生在后者。

| 坑 | 现象 | 原因 / 解法 |
|---|---|---|
| 用 `xargs -P 50` 跑 50 个 curl | 墙钟 8.4 秒、抢锁失败 **0** 次，看起来"没有并发问题" | 每个请求都 fork 一个进程，实际是排队发出去的。**必须用线程池 + Barrier** |

## 九、今天的自测题（先自己想，再点开答案）

**Q1. 为什么删缓存必须放在事务提交之后？用时序讲清楚在事务里删会发生什么。**

<details>
<summary>点开看答案</summary>

在事务内删缓存后，读线程会挤进"缓存已删、事务未提交"的窗口，查库读到**旧值**并回填；
等事务提交时，缓存里已经是旧值了，还要躺到 TTL 到期（600 秒）。
这比"忘删缓存"更难查，因为缓存确实被删过。

正确做法：`TransactionSynchronizationManager.registerSynchronization(...)` 的 `afterCommit`。
</details>

**Q2. 为什么不能用 `KEYS stat:*` 批量删缓存？**

<details>
<summary>点开看答案</summary>

Redis 单线程，`KEYS` 会一次性遍历全库并**阻塞所有其它命令**，key 多时能让 Redis 卡住几秒。
用 `SCAN` 分批游标扫描，每次 500 个，边扫边删。代价是不保证快照一致，但删缓存场景够用。
</details>

**Q3. 互斥锁的三个必备要素是什么？少一个会怎样？**

<details>
<summary>点开看答案</summary>

① SETNX（互斥）；② 过期时间（防死锁：持锁线程崩了锁不会永远留着）；
③ 释放时比对 value + Lua 原子删除（防误删别人的锁）。

少 ②：进程崩了锁永久占用，该 key 再也加载不出来。
少 ③：A 超时后 B 抢到锁，A 醒来把 B 的锁删了，互斥失效，退化成没有锁。
</details>

**Q4. 抢锁失败后为什么是"等一会儿再看缓存"，而不是"直接查库"？**

<details>
<summary>点开看答案</summary>

因为抢锁失败说明**已经有人在查了**，我再查就是纯重复劳动，击穿防护的意义正是"只让 1 个人查"。
等他回填好，我读缓存连数据库往返都省了。

但要设上限（本项目 1 秒），超时就自己查库 —— 可用性优先，不能让请求陪一个卡住的线程一起挂。
</details>

**Q5. 什么情况下"更新数据"不需要清缓存？举一个本项目的例子。**

<details>
<summary>点开看答案</summary>

**当改的字段不参与任何查询结果时。**

本项目：区域只改 `sort`（排序字段），而统计结果只用 `region_code` 和 `region_name`，
所以统计结果完全不变 → 不清，日志打 `跳过清缓存`。实测缓存 key 数 1 → 1 不变。

反例：改了 `region_name`，所有含这个区域的统计结果全错 → 必须清。
</details>

**Q6. Redis 挂掉时，加了防击穿锁的接口会不会变慢？为什么？**

<details>
<summary>点开看答案</summary>

**会，如果没做额外处理**：读缓存失败后去抢锁（又失败），然后进入"等 1 秒"的循环，
每个请求白白多 1 秒。

所以必须区分"抢锁失败"的两种语义：
- `LOCK_BUSY`（别人在查）→ 应该等；
- `LOCK_ERROR`（Redis 不可用）→ **不能等**，直接查库。

修复后实测：Redis 不可用时 23ms（修复前约 1000ms）。
**教训：降级路径本身也要测。**
</details>

**Q7. 面试官说"我用 Redis 保证了缓存和数据库强一致"，你怎么看？**

<details>
<summary>点开看答案</summary>

这话基本不成立。缓存和强一致天生矛盾：删缓存与事务提交之间永远存在时间窗，
分布式环境下还叠加主从延迟、并发回填。

工程上的目标是**最终一致 + 窗口尽量小**：后删缓存（Cache Aside）、
afterCommit、TTL 兜底、必要时订阅 binlog 异步失效。

如果有人真需要强一致，正确做法是那不叫缓存 —— 那是把 Redis 当主存储用（另有一套代价）。
</details>

## 十一、面试怎么讲（把两天连成一条线）

> "我给统计接口做了缓存，然后用两步保证它不是一个只进不出的黑洞。
>
> **读**：手写三段式（拼 key → 查缓存 → 未命中查库回填），
> 用 `StringRedisTemplate` + JSON 而不是 JDK 序列化，这样 `redis-cli` 里能直接看懂缓存内容。
> 空结果也缓存 60 秒防穿透，TTL 加 0~60 秒随机抖动防雪崩。
> 实测命中时数据库 **0 次访问**，四个接口从 20 多毫秒降到 4~6 毫秒。
>
> **写**：区域表变更后清缓存，但删除动作注册在事务的 `afterCommit` 里 ——
> 因为在事务内删，读线程会把未提交的旧值回填回缓存，脏数据要躺到 TTL 到期。
> 而且我做的是**按字段精准失效**：只改 sort 这种不参与查询结果的字段就不清，
> 只在名称/编码变化时才清，避免缓存永远在失效。
>
> **并发**：热点 key 过期瞬间 50 个并发会同时查库。我用 SETNX + 过期时间做互斥锁，
> 解锁用 Lua 比对 token 防误删。实测 50 并发打冷 key，数据库执行次数从 **50 次降到 1 次**。
> 抢不到锁的线程不是死等，最多等 1 秒就降级自己查库。
>
> 最后还做了一件事：把 Redis 指到一个不存在的端口验证降级，
> 结果发现第一版会白等 1 秒 —— 修完之后是 23 毫秒。**降级路径也得测。**"
