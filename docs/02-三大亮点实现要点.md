# 亮点一 · 慢查询排查与索引优化

## 目标

拿到你自己测出来的「优化前 → 优化后」真实数字。数字是多少不重要，**真实**才重要。

## 操作步骤

**1. 先灌数据（没有数据量就看不出慢）**

往 `fact_indicator_value` 灌 10 万行以上。两种做法，推荐第二种：

- 写一个 MySQL 存储过程循环插入
- **写一个 Java 批量插入工具类**（`insertBatch`，每 1000 条一批）— 推荐，
  这样你还多一个"批量写入"的代码可以讲

灌数据的逻辑：遍历 `dim_region` × `dim_indicator` 的叶子节点 × `dim_period`，
每个组合生成一个随机值。

**2. 测优化前的耗时**

先把 MySQL 的慢查询开关打开，方便观察：

```sql
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
```

跑这条聚合查询，记录耗时：

```sql
SELECT f.region_code, f.period_code, SUM(f.indicator_value) AS total
FROM fact_indicator_value f
JOIN dim_indicator i ON i.indicator_code = f.indicator_code
WHERE f.period_type = 'Y'
  AND i.category = '工业'
  AND f.period_code IN ('2024','2025','2026')
GROUP BY f.region_code, f.period_code;
```

**3. 看执行计划**

```sql
EXPLAIN <上面那条 SQL>;
```

记下这四个字段：

| 字段 | 优化前 | 优化后 |
|---|---|---|
| `type` | | |
| `key` | | |
| `rows` | | |
| `Extra` | | |

> `type` 是访问类型，从差到好：`ALL`（全表扫描）→ `index` → `range` → `ref` → `const`。
> 看到 `ALL` 就说明没走索引。

**4. 加索引，重写 SQL，再测一次**

```sql
ALTER TABLE fact_indicator_value
  ADD INDEX idx_type_period_indicator (period_type, period_code, indicator_code, region_code);
```

重新 `EXPLAIN` + 计时，填进上面的表。

**5. 记录到 `README.md` 的记录区**

# 亮点二 · 大屏聚合接口 + Redis 缓存

## 目标

拿到「加缓存前 → 加缓存后」的耗时对比。

## 操作步骤

**1. 先做同步版本**

大屏接口直接查库，记录耗时（用 `System.currentTimeMillis()` 打日志，或者 StopWatch）。

**2. 设计缓存**

```
Key 结构：  econ:dashboard:{regionCode}:{periodType}:{periods}:{categories}
例子：      econ:dashboard:431300:Y:2024,2025,2026:综合经济,工业

Value：   聚合结果的 JSON
TTL：     10 分钟
```

**3. 实现"查缓存 → miss 查库 → 回填"**

```
1. 拼 key
2. 查 Redis
3. 命中 → 直接返回，日志记 "cache hit"
4. 未命中 → 查库 → 写入 Redis 并设 TTL → 返回，日志记 "cache miss"
```

**4. 数据变更时删缓存**

`fact_indicator_value` 有任何新增/修改/删除，就删除该区域相关的缓存 key。

> 简单做法：用 `SCAN` 匹配前缀删除（别用 `KEYS`，会阻塞 Redis）。
> 生产做法：维护一张"区域 → key"的映射，或者用延迟双删。

**5. 测前后对比**

连续请求同一参数 10 次，记录第一次（miss）和后续（hit）的耗时，填进 README 记录区。

---

## 决策点

1. **为什么是"删除缓存"而不是"更新缓存"？**
   （提示：并发下两个写请求的更新顺序问题）
2. **缓存怎么防穿透？** 查一个不存在的区域，每次都打到库上怎么办？
3. **缓存怎么防击穿？** 某个热点 key 过期瞬间，几百个请求同时查库怎么办？
4. **缓存怎么防雪崩？** 一堆 key 同时过期怎么办？
5. **为什么 key 用 `:` 分隔？** 这样设计有什么好处？
6. **`SCAN` 和 `KEYS` 有什么区别？为什么不能用 `KEYS`？**

# 亮点三 · Excel 异步导入 + 失败重试 + 幂等

> **这是三条里最值钱的。** 因为它同时考了并发、幂等、状态机、容错四件事，
> 大部分应届生答不上来。

## 目标

把同步的 Excel 导入改成异步任务，做到：**不重复、不丢失、失败可重试、状态可查。**

## 操作步骤

**1. 先做同步版本，并测出它的慢**

上传 1 万行 Excel，记录接口耗时（会很长，这就说明为什么需要异步）。

**2. 改成异步（同步接口只负责"接单"）**

```
POST /indicator-value/import
  1. 接收文件，存到本地/OSS
  2. 计算文件 MD5
  3. 用 MD5 作为 biz_key 查 async_task 表
     ├── 已存在且 SUCCESS  → 直接返回"该文件已导入成功"，不重复执行   ← 幂等
     ├── 已存在且 PENDING/RUNNING → 返回"任务执行中，请稍候"
     └── 不存在 → 插入任务记录（状态 PENDING）→ 提交到线程池 → 立即返回 taskId
```

**3. 线程池怎么配**

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4,                                  // 核心线程数
    8,                                  // 最大线程数
    60, TimeUnit.SECONDS,               // 空闲存活时间
    new LinkedBlockingQueue<>(100),     // 任务队列
    new ThreadFactory() { ... },        // 给线程起有意义的名字
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝策略
);
```

**4. 状态机**

```
PENDING ──提交──→ RUNNING ──成功──→ SUCCESS
                     │
                     └─失败─→ 还有重试次数？
                                ├── 有 → 计算 next_retry_time，回到 PENDING
                                └── 没有 → FAILED
```

**5. 指数退避重试**

```
第 1 次失败 → 等 1 秒重试
第 2 次失败 → 等 2 秒重试
第 3 次失败 → 等 4 秒重试
第 4 次失败 → status = FAILED，记录 error_msg
```

**6. 幂等怎么保证（两道防线）**

- **第一道**：业务层先查 `biz_key` 是否存在，存在就返回已有任务
- **第二道**：`async_task` 表的 `uk_biz_key` 唯一索引——并发情况下插入重复会抛异常，
  捕获后返回已有任务。**这是兜底，不能只靠第一道。**

**7. 怎么保证不丢**

**先把任务落库，再提交到线程池。** 顺序反了就会丢——线程池提交成功但数据库没记，
服务重启后这个任务就消失了。

**8. 服务重启时正在执行的任务怎么办（进阶）**

启动时扫描 `status = 'RUNNING'` 且 `update_time` 超过 10 分钟的任务，重新入队。

---

## 决策点（每一条都是必考题）

1. **为什么用线程池，不用 MQ？**
   想清楚两者的适用边界，别背答案。
2. **幂等键为什么选"文件 MD5"？**
   如果换成"区域 + 周期 + 指标"行不行？各有什么问题？
   （提示：同一份文件改了内容，MD5 会变；但如果只是数据更新，你可能希望它还是同一个任务）
3. **重试为什么必须指数退避？** 一直用 1 秒间隔重试会发生什么？
4. **失败重试会不会重复写入数据？** 靠什么保证？
   （提示：`uk_fact` 唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE` 或先删后插）
5. **`CallerRunsPolicy` 是什么意思？为什么选它，不用 `DiscardPolicy`？**
6. **如果任务执行到一半服务挂了，这条数据是成功还是失败？** 怎么查、怎么补救？
7. **线程池的核心线程数设 4 怎么定出来的？**
   （提示：这个任务是 IO 密集型还是 CPU 密集型？）

**面试时你可以这么说：**

> "大屏聚合查询原本是全表扫描，`EXPLAIN` 显示 `type=ALL`、扫描了 48 万行。
> 我分析了查询条件，发现 `period_type` 不在原索引的最左前缀里，
> 于是建了 `(period_type, period_code, indicator_code)` 的联合索引，
> 优化后 `type` 变成 `range`，扫描行数降到 5,418，接口耗时从 133 毫秒降到 9.7 毫秒。
>
> 后来我又优化了另一个按区域聚合的接口。它走的是索引、扫描行数也不多，
> 但还是要 43 毫秒。用 `EXPLAIN ANALYZE` 看真实执行计划才发现，
> 时间全花在 600 次索引点查和 1,350 次回表上——根因是 SQL 里 JOIN 了区域维表，
> 让关联发生在聚合**之前**。我把维表关联挪到聚合之后（改到应用层批量补名称），
> 耗时降到 10.6 毫秒。有意思的是改造后扫描行数从 1,668 涨到了 5,568，
> 但因为从随机点查变成了顺序范围扫描，实际反而更快——这让我意识到
> 不能只盯 `rows` 一个指标，I/O 的类型同样关键。
>
> 另外我给这四个聚合接口都加了 Redis 缓存。理由很直接：大屏是典型的读多写少场景，
> 挂在值班室墙上，100 个人看的是同一条 URL、同一组参数，10 分钟内结果不会变，
> 不缓存就等于把同一套查询重复跑 100 遍。
>
> 实现上我没有用 `@Cacheable`，而是手写了一个「查缓存 → miss 查库回填」的通用组件，
> 原因是那几个缓存设计细节我要自己控制：用 `StringRedisTemplate` + JSON 存放，
> 而不是默认的 JDK 序列化，这样 `redis-cli` 里能直接读懂缓存内容；
> key 里把**所有影响结果的参数**都拼进去（包括容易被漏掉的 `topN`）；
> 对"语义不同"的参数（比如同比的基期和当期）按固定位置拼、不做排序，
> 因为调换它们结果就完全不同。
>
> 另外顺手做了两件防坑的事：一是**空值缓存**，查库结果是空的时候也把"空"缓存起来
> （TTL 只给 60 秒），防止有人一直查不存在的数据把请求全打到数据库上；
> 二是 **TTL 随机抖动**，基础 600 秒再加 0~60 秒随机，避免一批 key 同时过期把数据库打穿。
>
> 实测下来：未命中（查库）23.3 ms，命中 5.37 ms，其中缓存层自身只占 0.68 ms。
> 我还用 `performance_schema` 做了个验证：连打 50 次命中请求，
> 数据库侧 `fact_indicator_value` 相关的 SQL 条数是 **0** ——
> 缓存不是"让查询变快"，而是"让数据库根本不参与"，这两件事的差别挺大的。
>
> 顺便说一句，这四个接口的优化是分层的：先用索引把单次查询从 133 ms 压到 9.7 ms，
> 再用缓存把后续 99 次请求变成不查库。**索引解决"查得快"，缓存解决"不用查"，
> 是接力关系，不是二选一**——索引让未命中的那一次也不慢，缓存让之后的请求不碰数据库。

### 亮点三的面试话术（Excel 异步导入）

> "第三个问题是我做的数据导入。最初是同步接口，1 万行大概要 5 秒，
> 而且用户会重复点击，网关卡超时之后还会自动重试，数据就重复了。
>
> 我先做了两件事定位问题：一是把逐行 INSERT 改成每 500 行批量插入，
> 5.09 秒降到 0.65 秒，快了 7.8 倍——原因是网络往返从 1 万次降到 22 次，
> 而且索引维护和事务开销也同步减少；
> 二是把同步改成异步，接口只做"存文件 + 算 MD5 + 落任务表 + 投递线程池"四件事，
> 56 毫秒就返回一个 taskId，用户拿 taskId 轮询状态。
>
> **异步没有让导入变快，它只是把等待从请求线程挪到了后台线程**——
> 这样 Tomcat 线程不会被一个 5 秒的请求占住，30 个人同时导入也不会把服务拖垮。
>
> 异步带来的新问题是"任务不能只在内存里"。第一版我直接把任务丢进线程池，
> 后来意识到服务一重启（发版、OOM）队列里的任务就全丢了，
> 而用户已经拿到"提交成功"的提示，他永远不知道数据没导进去。
> 所以我加了 `async_task` 表，任务状态、行数、失败原因全部落库，
> 服务重启后 `GET /task/{id}` 依然能查到 —— 这个我实测验证过。
>
> 幂等做了两道防线。第一道是用文件的 MD5 当 `biz_key`，
> 上传前先查有没有同 MD5 的任务，有就直接返回已有的 taskId。
> 用 MD5 而不是文件名，是因为文件名可以改——用户把文件另存为"副本"再传，
> 文件名变了但 MD5 没变，照样能拦住。
> 第二道是 `async_task.biz_key` 上的唯一索引。因为"查"和"插"之间有时间窗口，
> 两个请求可能同时查到"不存在"，然后都去插入。我用 10 个线程压过同一个文件，
> 日志显示 1 个建任务成功、9 个撞唯一索引被拦下，最终数据库里只有 1 条任务记录，
> 业务数据也只导入了 1 遍。
>
> 线程池这块我特意没有用 `CallerRunsPolicy`。它的语义是队列满了让提交任务的线程自己去跑，
> 在后台程序里没问题，但在 Web 里提交任务的就是 Tomcat 线程 ——
> 等于异步接口又变回同步，而且连 Tomcat 线程也被占住了。
> 所以我用 `AbortPolicy`，队列满就拒绝，把任务标成 FAILED 并返回"系统繁忙"，
> 不留一条永远 PENDING 的僵尸任务。
>
> 还有一个细节：我把"解析校验"和"写库"分开了。
> 边解析边写的话，如果第 8000 行出错，前面 7999 行已经进库了；
> 异步版是分批提交的，事务兜不住。所以改成全部校验通过才开始写，
> 语义就是"要么全对，要么一行不写"。实测三种非法数据（表头写错、值填成文字、负数），
> 全部是 `success_rows=0`，库里一行脏数据都没留。"
>
> 但缓存只进不出会变成谎言的放大器，所以我接着做了**失效**和**防击穿**两件事。
>
> 失效这块，区域维表变动后要清统计缓存，删缓存的动作我注册在事务的 `afterCommit` 里。
> 因为如果在事务里面删，会出现这个时序：更新库（未提交）→ 删缓存 → 读线程查库读到旧值
> → 把旧值回填进缓存 → 事务提交。结果是缓存里躺着旧值，还要躺 600 秒，
> 而且日志里明明有"删缓存"的记录，排查时非常迷惑。
> 另外我做的是**按字段精准失效**：区域只改 `sort` 这种不参与查询结果的字段就不清，
> 只有名称或编码变了才清 —— 否则缓存永远在失效，等于没做。
>
> 防击穿是用 SETNX + 过期时间做互斥锁，解锁用 Lua 脚本比对 token，防止误删别人的锁。
> 抢不到锁的线程不是死等，最多等 1 秒就降级自己查库。
> 实测 50 个并发打同一个冷 key（用线程池 + Barrier 保证同时出发），
> 关掉防护时数据库执行了 50 / 39 / 38 次，开启后稳定是 **1 次**。
>
