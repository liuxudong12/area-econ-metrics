## 二、EXPLAIN 怎么看（只需盯 4 个字段）

`EXPLAIN` 是"让 MySQL 告诉你它打算怎么执行这条 SQL"。字段很多，**新手只需要看 4 个**：

| 字段 | 看什么 | 我们的例子 |
|---|---|---|
| **type** | **怎么访问表的**，最重要 | `ALL` → `range` |
| **key** | **实际用了哪个索引** | `NULL` → `idx_tpi` |
| **rows** | 预计要扫描多少行 | 487354 → 5400 |
| **Extra** | 补充信息 | `Using index condition` / `Using filesort` 等 |

### `type` 的好坏排序（从好到坏，背下来）

```
system > const > eq_ref > ref > range > index > ALL
```

| type | 含义 | 什么时候出现 |
|---|---|---|
| `const` | 按主键/唯一索引查，最多一行 | `WHERE id = 5` |
| `eq_ref` | 关联查询时用主键/唯一索引匹配 | JOIN 主键 |
| **`ref`** | 用非唯一索引等值查找 | `WHERE category = '工业'` |
| **`range`** | 用索引做范围扫描 | `BETWEEN`、`IN`、`>` |
| `index` | 扫整个索引树（比全表略好） | 覆盖索引但没过滤条件 |
| **`ALL`** | **全表扫描，看到它基本就是要优化** | 索引没用上 |

> **看到 `type=ALL` 且 `rows` 很大，就是明确的优化信号。**
> 我们的优化前就是 `type=ALL, key=NULL, rows=487354`——教科书级的反面案例。

### `Extra` 里几个高频词

| Extra | 意思 | 要不要管 |
|---|---|---|
| `Using index` | **覆盖索引**，只读索引不回表 | 👍 好 |
| `Using index condition` | 索引下推（ICP），在索引层就过滤掉部分数据 | 👍 好 |
| `Using where` | 拿到数据后再过滤 | 正常 |
| `Using join buffer (hash join)` | 没用上索引，走哈希连接 | ⚠️ 常常说明有优化空间 |
| `Using temporary` | 用了临时表（常见于 GROUP BY） | 少量数据无所谓 |
| **`Using filesort`** | **额外做了一次排序**，无法用索引顺序 | ⚠️ 数据量大时是问题 |

> ⚠️ **`Using filesort` 不一定慢** —— 名字里的 "file" 是历史遗留，小数据量时它就在内存里排。
> 别看到就慌。

## 三、为什么慢：最左前缀原则

### 3.1 先用一个比喻记住

把 `uk_fact (region_code, indicator_code, period_code)` 想成一本**电话簿**：

- 它先按 **区域** 排序，同区域内按 **指标** 排序，同指标内再按 **周期** 排序。

现在你要找"**周期 = 2024** 的所有记录"，但**不告诉区域**。

结果就是：你只能**从第一页翻到最后一页**——因为整本书是按区域分段的，你不知道"2024"在每段里的哪个位置。

**这就是全表扫描。**

反过来，如果查询里给了 `region_code`（"先查娄底市那一段"），你就能直接翻到娄底市那一段，再在里面找——**快得多**。

### 3.2 落到 B+ 树上

索引是一棵 B+ 树，**只有从最左列开始，才能找到入口一路往下定位**。

```
uk_fact (region_code, indicator_code, period_code)
          ↑ 最左列

查询里出现 region_code  →  能定位 → type=ref   → 扫 1,668 行
查询里没有 region_code  →  找不到入口 → type=ALL → 扫 489,618 行
```

**最左前缀原则**一句话总结：

> 联合索引 `(a, b, c)` 能被用在 `WHERE a=?`、`WHERE a=? AND b=?`、`WHERE a=? AND b=? AND c=?` 上；
> 但**不能**用在只给 `b` 或只给 `c` 的查询上。

### 3.3 这条规律在真实项目里的样子

同一个表、同一个 JOIN，**只因为 group by 的字段不同**，性能差 3 倍：

| 接口 | 分组字段 | 查询里有没有 region_code | EXPLAIN |
|---|---|---|---|
| `/category-summary` | 按**区域** | 有 ✅ | `type=ref, key=uk_fact, rows=1668` |
| `/trend` | 按**周期** | 没有 ❌ | `type=ALL, key=NULL, rows=487354` |

> **这句话请记住**：
> **"表上有索引" ≠ "查询能用上索引"。索引能不能用，取决于你的 WHERE / JOIN / GROUP BY
> 里有没有它的最左列。**

## 四、索引怎么设计：三条实操规则

我们的目标 SQL 的过滤条件：

```sql
WHERE period_type = 'Y'                        -- 等值
  AND period_code IN ('2024','2025','2026')    -- 范围（多个区间）
  AND indicator_code IN (...)                  -- 等值（JOIN 带过来的）
GROUP BY period_code
```

设计的索引：

```sql
ALTER TABLE fact_indicator_value
  ADD INDEX idx_tpi (period_type, period_code, indicator_code);
```

**列顺序的三条规则**（按优先级）：

| 规则 | 说明 | 本例 |
|---|---|---|
| ① **等值条件放最左** | 等值能大幅缩小范围 | `period_type` 放第一 |
| ② **范围条件跟在等值后面** | 一旦遇到范围，**后面的列就不能再用于定位了** | `period_code` 放第二 |
| ③ **区分度高的放前面** | 区分度 = 不同值的个数 / 总行数 | 都还行 |

> **③ 的反面案例**：`deleted` 这一列**只有一个值（全是 0）**，区分度＝0，**不要单独建索引**。
> 这就是为什么我们没有把 `deleted` 放在索引最左边。

## 五、我试了两种方案，为什么选慢的那个

| 方案 | 索引 | 耗时 | 索引体积 |
|---|---|---|---|
| A | `(period_type, period_code, indicator_code)` | **9.14 ms** | +15.5 MB |
| B | `(period_type, period_code, indicator_code, deleted, indicator_value)` | **4.95 ms** | +21.6 MB |

方案 B 更快，因为它是一个**覆盖索引**——SQL 用到的列全在索引里，**完全不用回表**。

### 什么是"回表"？

```
走索引找到主键 id   →   再拿 id 去聚簇索引把整行数据取回来
                       ↑ 这一步就叫"回表"
```

- **A**：先在索引里定位到 5,418 条，再逐条回表取 `indicator_value` → 9.14 ms
- **B**：`indicator_value` 也在索引里 → 一个回表都不用 → 4.95 ms（`Extra: Using index`）

### 那为什么还选 A？

**因为多花 6 MB 索引空间，只换来 4 毫秒。**

对一个每天被调几百次的接口来说，4 毫秒没人在意；但每次写入都要多维护一份更大的索引、磁盘也多占 6 MB。

> ★ **这段"取舍"本身才是加分项。**
> 面试时主动说"我试过覆盖索引，能再快一倍，但权衡后没选，因为收益抵不上索引膨胀"——
> 证明的是**你会权衡**，而不是背了答案。

## 六、索引的代价（这部分一定要懂，否则会滥用）

索引不是越多越好。每一个索引都有三份成本：

| 成本 | 说明 |
|---|---|
| **写变慢** | 每次 INSERT / UPDATE / DELETE 都要**同步维护所有索引**。索引越多，写越慢 |
| **占空间** | 本例：加一个索引，27.6 MB → 43.1 MB |
| **优化器负担** | 可选索引变多，选错执行计划的概率上升 |

**什么时候不要加索引**：

| 情况 | 原因 |
|---|---|
| 表很小（几百行以内） | 全表扫比走索引还快。比如 `dim_indicator` 只有 18 行，加索引毫无意义 |
| 列区分度极低 | 比如 `deleted`（全是 0）、`gender`（男女各半）——过滤不掉多少数据 |
| 频繁更新的列 | 维护成本高 |
| 已经能被别的联合索引覆盖 | 联合索引 `(a,b,c)` 已经能当 `(a)` 和 `(a,b)` 用，不用再单独建 |

> **面试常问**："索引越多越好吗？"
> 答：不是。索引能加速读，但会拖慢写、占空间。要按**实际慢查询**来建，
> 并注意联合索引的最左前缀能不能复用，避免建重复索引。

## 七、怎么测的（方法可以复用到别的项目）

### 7.1 测量方法

mysql 命令行客户端在**管道/非终端**环境下会自动切换成 batch 模式，**不打印 `N rows in set (X sec)`**，
所以抓不到耗时。可靠的做法是直接读 MySQL 自己记录的执行统计：

```sql
-- ① 清空统计
TRUNCATE TABLE performance_schema.events_statements_summary_by_digest;

-- ② 把同一条 SQL 跑 10 次（同一个连接内，避免连接开销干扰）

-- ③ 读结果
SELECT ROUND(AVG_TIMER_WAIT/1000000000, 2) AS 平均ms,
       SUM_ROWS_EXAMINED DIV COUNT_STAR AS 扫描行数
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT LIKE '%fact_indicator_value%';
```

`TIMER_WAIT` 单位是皮秒，除以 10 亿就是毫秒。

> ⚠️ **一个坑**：`DIGEST_TEXT` 会把 SQL 里的**字面量归一化成 `?`**。
> 所以 `LIMIT 0,10` 和 `LIMIT 50000,10` 会归成同一条 digest，**没法用这个方法区分**。
> 但对比"两条结构不同的 SQL"（比如优化前 / 优化后）是完全没问题的。

### 7.2 EXPLAIN 的正确用法（我踩的坑）

```bash
# ❌ 这样写不出来（SQL 末尾的分号会把 \G 截断）
mysql -e "EXPLAIN SELECT ... ;\G"

# ✅ 去掉分号再拼 \G
mysql -e "EXPLAIN SELECT ... \G"

# ✅ 或者用普通格式，第六列就是 key、第十列是 rows
mysql -e "EXPLAIN SELECT ..." | awk -F'\t' '{print $4, $6, $10}'
```

### 7.3 加索引后必须做的两件事

1. **验证结果一致**：同一组参数，优化前后的返回值必须完全相同
2. **刷新统计信息**：`ANALYZE TABLE fact_indicator_value;`
   不然优化器还按旧行数估算，可能选错执行计划，也会让你测的数字不准
