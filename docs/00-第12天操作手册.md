# Day 12 操作手册：数据导出

> 目标：把一个 48.96 万行的表，在 **256MB 堆**里完整导出成 Excel，
> 而且导出的时候，在线功能不受影响。
>
> 今天的数字全是实测的，每条命令都在第十三节给了复现步骤。

---

## 一、今天要解决什么问题

前 11 天做的是"把数据弄进来"（导入）和"把数据算出来"（统计）。
今天做最后一段：**把数据交出去**。

看起来只是"查出来写进 Excel"，但真实项目里导出恰恰是最容易出事的接口，原因有三个：

| 问题 | 具体表现 | 后果 |
|---|---|---|
| 数据量大 | 48 万行 → 几百万个对象 | 内存爆，整个进程挂 |
| 耗时长 | 一次导出 10 秒以上 | 占住数据库 IO，拖慢所有人 |
| 无法回退 | HTTP 一旦开始输出就不能改 | 用户拿到打不开的文件 |

所以今天真正要验证的是三件事：

```
① 48 万行能不能导出来            → 游标分页 + 流式写，内存恒定
② 导出的时候大屏还能不能用        → 导出通道独立限流
③ 导出来的文件用户能不能直接用    → 列顺序、文本格式、分 sheet、中文文件名
```

一句话总结今天的成果：

> **189 万行导出总量、单次最大 48.96 万行、256MB 堆下稳定完成、
> 并发第 3 人被 65ms 内拒绝、导出时统计接口不受影响。**

## 三、接口清单

| 接口 | 用途 | 参数 |
|---|---|---|
| `GET /api/export/fact` | 指标值明细 | `regionCodePrefix` / `indicatorCode` / `periodType` / `periodFrom` / `periodTo` |
| `GET /api/export/stat` | 统计结果 | `kind=category\|trend\|top\|yoy` + 各统计自己的参数 |
| `GET /api/export/dict` | 维表 | `type=region\|indicator\|period` |

### 3.1 明细导出：`regionCodePrefix` 为什么是"前缀"

区域编码是层级编码：

```
43 0000  湖南省
  └ 43 01 00  长沙市
       └ 43 01 02  芙蓉区
```

上级编码天然是下级编码的前缀，所以：

| 传什么 | 含义 | 实际行数（实测） |
|---|---|---|
| 不传 | 全省全部 | 489,600 |
| `regionCodePrefix=43` | 湖南省 | 489,600（本库数据全是湖南） |
| `regionCodePrefix=4301` | 长沙市及下辖 | 35,904 |
| `regionCodePrefix=430102` | 芙蓉区 | 更少 |

一个参数覆盖三种粒度，比"传 regionCode + 传 level"简洁。

**顺便一个技术点**：`LIKE '43%'` 能用索引（B+ 树范围扫描），
`LIKE '%43%'` 用不上（必须全表扫）。这条区别面试常问：

> **左模糊（`%xx`）废掉索引，右模糊（`xx%`）不会。**

### 3.2 统计导出：四个合并成一个接口

因为四个统计的参数几乎同构（`category + periodType + periodCodes`），
只有 `yoy` 用 `basePeriod/currentPeriod`、`top` 用 `topN`。

合并的好处：前端只维护一个下载地址；后端的限流、日志、异常处理复用一份。
合并的前提是**参数同构** —— 如果四个统计参数结构完全不同，就该拆成四个接口。

### 3.3 维表导出：为什么这里故意不做分页

| type | 行数 | 大小 | 耗时 |
|---|---|---|---|
| `region` | 150 | 7,606 B | 0.051 s |
| `indicator` | 18 | 4,605 B | 0.037 s |
| `period` | 272 | 11,150 B | 0.055 s |

**150 行给它套一套游标分页 + 切 sheet，属于用大炮打蚊子** ——
代码更复杂，性能一点不提升。
同一个项目里两种写法并存不是"不统一"，而是**按数据量级选择**。

## 四、核心一：深翻页，OFFSET 是 O(n²)

### 4.1 两种写法，一个字的差别

```sql
-- ✗ 传统分页（OFFSET）
SELECT ... FROM fact_indicator_value
WHERE deleted = 0
ORDER BY id
LIMIT 400000, 2000;

-- ✓ 游标分页（keyset / cursor）
SELECT ... FROM fact_indicator_value
WHERE deleted = 0
  AND id > 427031        -- 上一页最后一条的 id
ORDER BY id
LIMIT 2000;
```

看起来只差一个 `WHERE id > ?`，但执行方式完全不同。

### 4.2 为什么 OFFSET 是 O(n²)

`LIMIT 400000, 2000` 的中文含义是：

> **先按顺序数出 40 万行，把它们全部丢掉，再取接下来的 2000 行。**

它**不是**"跳到第 40 万行" —— B+ 树没有"第 N 个"这个概念，只能从头走。

所以：

```
第 1 页    扫 2,000 行
第 2 页    扫 4,000 行
...
第 245 页  扫 490,000 行
────────────────────────
合计约 6,000 万行次    ← 48 万行的 122 倍
```

而游标分页每一页都只在 B+ 树上"定位 → 往后取 2000 行"，**每页成本恒定**：

```
每一页都扫 2,000 行 → 245 页合计 49 万行次
```

这就是 O(n²) 和 O(n) 的区别。

### 4.3 实测：完整跑一遍全表（245 页 / 489,600 行）

用存储过程在**服务端**跑（排除 mysql 客户端启动开销），脚本见 `sql/08-导出翻页对比实验.sql`：

| 方式 | 页数 | 行数 | 总耗时 |
|---|---|---|---|
| 游标分页 | 245 | 489,600 | **138.81 ms** |
| OFFSET 分页 | 245 | 489,600 | **8,977.26 ms** |
| **倍数** | | 两者行数一致 ✔ | **64.7×** |

> 注意：这是**纯 SQL 执行时间**（服务端 `NOW(6)` 计时）。
> 客户端启动一次 mysql.exe 就要 50~100ms，245 次就是 20 秒，
> 会把要测的差异完全淹没。测性能时先把"不是你要测的东西"排除掉。

### 4.4 单页对比：OFFSET 的成本随深度线性增长

同一张表，同样取 2000 行：

| 取的位置 | 写法 | 实际扫描行数 | 实际耗时 |
|---|---|---|---|
| 第 1 万行起 | `LIMIT 10000, 2000` | 12,000 | 2.72 ms |
| 第 40 万行起 | `LIMIT 400000, 2000` | 402,000 | 85.4 ms |
| 第 40 万行起 | `WHERE id > 427031` | **2,000** | **0.528 ms** |

深度从 1 万涨到 40 万（40 倍），OFFSET 耗时涨 31 倍 —— **这就是线性增长**。
同样深度下，游标比 OFFSET 快 **162 倍**（85.4 / 0.528）。

### 4.5 怎么看 EXPLAIN ANALYZE

```sql
EXPLAIN ANALYZE SELECT id, region_code FROM fact_indicator_value
WHERE deleted = 0 ORDER BY id LIMIT 400000, 2000;
```

输出（关键两行）：

```
-> Limit/Offset: 2000/400000 row(s)  (actual time=85..85.4 rows=2000 loops=1)
    -> Index scan on fact_indicator_value using PRIMARY
       (actual time=0.0525..64.6 rows=402000 loops=1)
```

读法：

- `Limit/Offset: 2000/400000` —— 取 2000 行，跳过 400000 行
- `rows=402000` —— **实际扫了 40.2 万行**（这才是真正的成本）
- `actual time=85.4` —— 整个查询实际 85.4 毫秒

游标版：

```
-> Limit: 2000 row(s)  (actual time=0.044..0.528 rows=2000 loops=1)
    -> Index range scan on fact_indicator_value using PRIMARY over (427031 < id)
       (actual time=0.0417..0.382 rows=2000 loops=1)
```

- `Index range scan ... over (427031 < id)` —— 明确告诉你：**范围扫描，不是从头走**
- `rows=2000` —— 只碰了 2000 行

**面试时这两段输出可以直接背**：一个 `rows=402000`，一个 `rows=2000`，
差 200 倍，比任何形容词都有说服力。

### 4.6 游标分页的两个前提（面试常追问）

**前提一：排序键必须唯一且有序。**
这里用主键 `id` —— 自增、唯一、有索引，天然满足。

如果业务要求按 `update_time` 排序，就不能只用它做游标：
同一时刻可能有多条记录，`WHERE update_time > ?` 会**漏掉**同一时间戳里的其他行。

正确做法是联合游标：

```sql
WHERE (update_time > #{lastTime})
   OR (update_time = #{lastTime} AND id > #{lastId})
ORDER BY update_time, id
LIMIT 2000
```

**前提二：不能跳页。**
游标分页只能"下一页"，不能"跳到第 100 页"。
所以它**只适合导出/滚动加载**，不适合后台管理里那种带页码的分页器。
后台分页器该用 OFFSET —— 因为用户不会翻到第 10 万页。

> 一句话：**没有"更好的分页方式"，只有"更匹配场景的分页方式"。**

## 五、核心二：流式写出，内存恒定

### 5.1 反面做法

```java
// 一次把 48.96 万行查进 List
List<FactIndicatorValue> all = mapper.selectList(null);   // ← 这里就爆了
EasyExcel.write(out, FactExportRow.class).sheet().doWrite(all);
```

在本地 4GB 堆的机器上可能"能跑"，但：

- 并发 3 个人同时导出 → 3 × 480MB → 直接 OOM
- OOM 不是"这个请求失败"，是**整个 JVM 的线程被打死**（第五节 5.4 有现场）

### 5.2 正确做法

```java
long lastId = 0;
try (var writer = DataExportExporter.open(out, FactExportRow.class, spec)) {
    while (true) {
        List<FactIndicatorValue> page = mapper.selectForExportByCursor(query, lastId, 2000);
        if (page.isEmpty()) break;

        List<FactExportRow> rows = page.stream().map(this::toRow).toList();
        writer.write(rows);              // 写完 → 这一批对象立刻变成垃圾

        lastId = page.get(page.size() - 1).getId();
        if (page.size() < 2000) break;   // 不足一页 = 最后一页
    }
}
```

内存里的对象数**永远是一页的量（2000 个）**，跟总行数无关。
48 万行和 4800 万行，内存占用一样。

### 5.3 实测：同一份数据，两种取数方式

用 `GET /api/export/_test/memory?mode=list|stream&limit=489600` 测（`-Xmx4g`）：

| 模式 | 取到行数 | 起始堆 | 峰值堆 | 增量 | 耗时 |
|---|---|---|---|---|---|
| `list` 一次性全查 | 489,600 | 27 MB | **508 MB** | **+481 MB** | 4,283 ms |
| `stream` 游标流式 | 489,600 | 26 MB | **121 MB** | **+95 MB** | 4,307 ms |

**注意两件事**：

1. **耗时几乎一样**（4283 vs 4307ms）——
   分页没有让"取数"变慢，因为瓶颈是网络传输和对象构造，不是查询次数。
   所以"流式"不是用时间换内存，是**白赚的内存**。
2. **增量差 5 倍**（481 vs 95 MB）——
   而且 `stream` 的 95MB 大部分是"还没来得及回收的垃圾"（测完 `afterMb=67`），
   真正活着的对象只有一页。

### 5.4 OOM 的现场：不是这个请求失败，是整个服务挂掉

把堆压到 256MB（`-Xmx256m`），做两件事：

**① 流式导出全量 48.96 万行 —— 成功**

```
http=200 大小=22,127,375B 耗时=12.66s
```

**② 一次性全查 —— OutOfMemoryError，整个服务不可用**

```
Exception in thread "http-nio-18080-Poller" java.lang.OutOfMemoryError: Java heap space
jakarta.servlet.ServletException: Handler dispatch failed: java.lang.OutOfMemoryError
Caused by: java.lang.OutOfMemoryError: Java heap space
```

紧接着再访问 `/ping`：

```
http=000        ← 连不上，不是 500，是根本没响应
```

**这就是为什么 OOM 必须当成"最高级别事故"**：
它杀掉的不只是那个请求的线程，`http-nio-*-Poller`（Tomcat 的网络轮询线程）也死了，
之后所有请求都进不来。用户看到的是"网站打不开了"，而不是"导出失败"。

> 补充一个有意思的数字：在 **384MB** 堆下，一次性全查**没有 OOM**（峰值 341MB，delta 315MB）。
> 也就是说"能跑"和"会挂"之间只差 100MB ——
> **靠"我这台机器能跑"来判断内存够不够，是最危险的判断方式。**

### 5.5 为什么日志里要打堆占用

```java
log.info("[导出-明细] 完成 行数={} sheet={} 耗时={}ms 堆占用 {}MB→{}MB", ...);
```

实测输出：

```
[导出-明细] 完成 行数=489600 sheet=1 耗时=9757ms 堆占用 46MB→127MB
```

这个打点的价值：**下次改代码时，如果谁一不小心把整表查进内存了，
堆占用会从 46MB 跳到 500MB，一眼就能看出来。**
不用等线上 OOM 才发现。

> 注意 46→127 是"未 GC 的已用堆"，含垃圾，不代表活对象有 81MB。
> 要看真实活对象得看 5.3 那个 GC 后的数字。

## 六、核心三：Excel 单 sheet 只能装 104 万行

### 6.1 这是个格式限制，不是 POI 的限制

xlsx 是 OOXML 格式，标准写死：

- 单 sheet 最多 **1,048,576 行**（2^20）
- 最多 **16,384 列**（2^14）

超过后 POI 抛：

```
IllegalStateException: Invalid row number (1048576) outside allowable range
```

**这不是"内存不够"或"配置不对"，是文件格式不允许，改不了。**

我们的表已经 48.96 万行，几轮导入就会逼近百万。
所以导出必须自动分 sheet。

### 6.2 实现：写满就换 sheet

```java
public void write(List<T> rows) {
    int from = 0;
    while (from < rows.size()) {
        ensureSheet();                                    // 需要时才建，避免空 sheet
        int remain = spec.rowsPerSheet() - rowsInSheet;
        int to = Math.min(from + remain, rows.size());
        writer.write(rows.subList(from, to), currentSheet);  // 一批可能跨两个 sheet
        rowsInSheet += (to - from);
        totalRows += (to - from);
        from = to;
        if (rowsInSheet >= spec.rowsPerSheet()) {
            currentSheet = null;                          // 标记下次换 sheet
        }
    }
}
```

### 6.3 一个容易漏的坑：一批数据跨过 sheet 边界

假设每 sheet 上限 1000 行，当前 sheet 已写 900 行，这一批有 300 行。

如果直接整批写进去 → 变成 1200 行 → **抛异常**。

所以必须拆：100 行给旧 sheet、200 行给新 sheet。
**这个 bug 只在"每页条数不整除每 sheet 行数"时出现** ——
用 1000 条/页、1000 行/sheet 的整数测试数据永远测不出来。

### 6.4 实测

把 `rows-per-sheet` 调成 200,000（生产默认是 1,000,000），导全量：

```
[导出-明细] 完成 行数=489600 sheet=3 耗时=9751ms
文件大小 = 22,128,621 B
```

解压 xlsx 看每个 sheet 的 `<row>` 数量：

| sheet 名 | 行数（含表头） | 数据行 | dimension |
|---|---|---|---|
| 指标值明细 | 200,001 | 200,000 | A1:I200001 |
| 指标值明细-2 | 200,001 | 200,000 | A1:I200001 |
| 指标值明细-3 | 89,601 | 89,600 | A1:I89601 |
| **合计** | | **489,600** ✔ | |

**一行没丢，也没重复。** 这个校验必须做 ——
"分 sheet"最容易出的问题就是边界上丢一行或重复一行。

## 七、工业级细节（这一节最值钱）

前六节是"怎么导出"，这一节是"怎么导出得像个做过真实项目的人"。

### 7.1 所有校验必须在 setHeader 之前

HTTP 响应是**单向**的。一旦开始输出字节：

- 不能改状态码（200 已经发出去了）
- 不能改响应头
- 不能再写一段 JSON 错误体 —— 会变成"xlsx 文件里混进 JSON"

所以 `ExportServiceImpl` 里严格分两段：

| 阶段 | 允许抛异常 | 做什么 |
|---|---|---|
| **setHeader 之前** | ✅ 安全 | 限流、COUNT、参数校验 |
| **setHeader 之后** | ❌ 危险 | 只写数据；出错只能记日志 |

代码里的处理：

```java
boolean committed = false;
try {
    acquired = acquirePermit(...);        // ① 限流
    long total = factMapper.countForExport(query);  // ② 计数
    if (total > maxRows) throw new BizException(...);
    setExcelHeaders(response, fileName);  // ③ 从这里开始
    committed = true;
    ... 写文件 ...
} catch (Exception e) {
    if (committed) {
        // 已经写出去了，再抛异常会让 Spring 试图往同一个响应里写第二次，
        // 报 "getOutputStream() has already been called"
        log.error("[导出-明细] 已在输出中途失败，客户端会拿到不完整文件", e);
        return;      // ← 安静结束，不再抛
    }
    throw e;
}
```

**这段代码不好看，但它是正确性的核心。**
真实项目里减少这种局面的办法：前置校验做全、行数上限设小、
关键报表改用"先落临时文件、成功后再回传"。

### 7.2 限流用 Semaphore，不是线程池

```java
this.permits = new Semaphore(maxConcurrent, true);   // true = 公平模式
...
if (!permits.tryAcquire()) {
    throw new BizException("当前导出任务较多（并发上限 2 个），请稍后重试。");
}
```

**为什么不用线程池？**
导出的执行线程由 Tomcat 提供（一个请求一个线程），我们不需要自己造线程，
只需要限制"同时进入的请求数"。这是 Semaphore 的语义，不是线程池的语义。

**为什么默认 `tryAcquire()` 不等待？**
导出要跑 10 秒以上。让用户排队等，他前端就是一个转圈的页面，
等到网关超时（通常 60 秒）可能页面都关了 —— 白占一个 Tomcat 线程。
直接拒绝 + "请稍后重试"，用户 3 秒后重试，体验反而更好。

> 这就是**快速失败（fail fast）**：
> 在知道做不成的时候立刻说做不成，比让对方一直等更有价值。

**为什么必须 `finally { permits.release(); }`？**
少释放一次，许可就永久少一个。几次之后所有人都导不出来，
而且现象是"越来越多人被拒绝"，极难联想到是信号量泄漏。

**⚠️ 这是单机限流。** 多实例部署时每个实例各限各的，
集群总并发 = 实例数 × max-concurrent。要全局限流得用
Redis 计数器（INCR + EXPIRE）或网关层限流。

#### 实测：3 个并发，上限 2

```
同时发起 3 个导出请求：/api/export/fact?regionCodePrefix=4301
------------------------------------------------------------------------------
✅ #0  HTTP 200  文件           1623388 B     1514 ms
⛔ #1  HTTP 200  JSON(拒绝)         148 B       65 ms  当前导出任务较多（并发上限 2 个），请稍后重试。
✅ #2  HTTP 200  文件           1623388 B     1507 ms
------------------------------------------------------------------------------
成功 2 个 / 被拒 1 个 / 墙钟总耗时 1516 ms
```

- 成功 2 个：各 1.5 秒（并行，所以墙钟也是 1.5 秒，不是 3 秒）
- 被拒 1 个：**65ms 就返回了**，不占资源、不排队

> 测试脚本用了 `threading.Barrier` 对齐起跑线。
> 不用 Barrier 的话，第 1 个可能已经在下载、第 3 个还没开始，
> 根本不在同一个时间窗口里，测不出并发争抢。

### 7.3 旁路日志不能影响主链路

```java
private void saveLog(ExportLog l) {
    try {
        exportLogMapper.insert(l);
    } catch (Exception e) {
        log.warn("[导出-日志] 写入失败，不影响导出结果 ...");   // 吞掉
    }
}
```

**日志是旁路：它挂了，不该让用户已经下载好的文件作废。**

反过来判断：如果一个操作失败会导致业务状态不一致（比如"导入任务状态"），
那它**必须**和主流程同成败，不能吞异常。

> **「旁路可以吞，记账不能吞」** —— 这条判断标准比记住某个具体写法有用。

实测日志表（`export_log`，9 条记录）：

| id | 类型 | 行数 | sheet | 耗时ms | 状态 |
|---|---|---|---|---|---|
| 1 | FACT | 489,600 | 1 | 12,086 | SUCCESS |
| 2 | FACT | 35,904 | 1 | 1,567 | SUCCESS |
| 4 | FACT | 0 | 0 | 0 | **REJECTED**（并发超限） |
| 7 | FACT | 489,600 | **3** | 12,146 | SUCCESS（分 sheet 那次） |
| … | | | | | |

拒绝也记日志 —— 因为"谁在被拒"同样是需要知道的事。

### 7.4 中文文件名 + 跨域

```java
String encoded = URLEncoder.encode(fileName, StandardCharsets.UTF_8).replace("+", "%20");
response.setHeader("Content-Disposition",
        "attachment; filename=\"" + encoded + "\"; filename*=UTF-8''" + encoded);
response.setHeader("Access-Control-Expose-Headers", "Content-Disposition");
```

三个坑：

1. **HTTP 头只能放 ASCII**，中文直接塞会被 Tomcat 拒绝或变乱码。
   解法是 RFC 5987 双写：`filename=`（老浏览器）+ `filename*=UTF-8''`（现代浏览器）。
2. **`URLEncoder` 把空格编成 `+`**，而 `+` 在文件名里就是字面加号。
   所以必须 `.replace("+", "%20")`，否则"销售 报表.xlsx"会变成"销售+报表.xlsx"。
3. **跨域时前端读不到 `Content-Disposition`**，必须服务端加
   `Access-Control-Expose-Headers`。不加的话 axios 拿到的文件名是 `null`，
   而前端只会说"拿不到文件名"，很难联想到是服务端少了一个头。

### 7.5 不设 Content-Length 的代价

流式导出**刻意不设** `Content-Length`：总字节数要等 Excel 全部生成完才知道，提前设只能是瞎猜。

代价是 Tomcat 用 **chunked** 编码，浏览器**显示不了下载进度百分比**
（只显示"已下载 xx MB"）。

这是流式方案固定的体验代价。要进度条就得换方案：

| 方案 | 代价 |
|---|---|
| 先全部生成到临时文件，再回传 | 多一次全量写盘 + 读盘，48 万行约 22MB |
| 前端轮询"生成进度" | 需要任务表 + 状态机（像 Day 9 的异步导入） |
| 直接接受没有进度条 | 成本最低，用户也能忍 |

> 真实项目里常用第三种。**不是所有体验问题都值得用架构解决。**

### 7.6 维表放内存当字典，而不是 JOIN

导出 48 万行时，每行都要补两个字段：区域名称、指标名称 + 单位。

| 方案 | 成本 |
|---|---|
| SQL 里 `JOIN dim_region / dim_indicator` | 48 万行 × 2 次随机回表 = 约 100 万次随机 IO |
| 启动时把维表读进 `HashMap` | 150 + 18 条记录 ≈ 几十 KB 内存；48 万次哈希查找 |

Day 6 已经证明过 JOIN 的代价（44.3ms → 9.52ms 就是靠去掉 JOIN 换来的），
这里用得是同一个思路。

**但前提必须说清楚**：维表要**小且变化不频繁**。
如果维表有 100 万行，或者每分钟都在变，就不能这么干 ——
得换回 JOIN，或者按页批量查。

### 7.7 维表里查不到的编码怎么办

```java
r.setRegionName(regionNames.getOrDefault(f.getRegionCode(), "（区域已不存在）"));
```

三种选择的对比：

| 选择 | 后果 |
|---|---|
| 抛异常 | 一条脏数据害得整张表导不出来，最差 |
| 名称留空 | 用户看到"430999 \| （空）"，不知道自己少了什么 |
| 填明确提示 | 用户能看到"这里有个区域已经不存在了"，还能自己判断 |

选第三种。
**导出文件的职责是"如实反映数据现状"，不是"只展示漂亮的数据"。**

## 十、踩坑记录

### 坑 1：`writeSmall` 的泛型擦除

`head` 是 `Class<?>` 时，`open(out, head, spec)` 返回 `PagedWriter<capture of ?>`，
不能直接当 `PagedWriter<Object>` 用。

解法：写一个 `cast()` 做一次 `@SuppressWarnings("unchecked")` 转换。
**为什么敢这么写**：`head` 和 `rows` 是同一个 `switch` 分支里一起决定的，两者必然匹配。
这类"局部保证正确"的地方加 `@SuppressWarnings` 是合理的，而不是全局关掉警告。

### 坑 2：`catch (Exception e) { throw e; }` 编不过

编译器做"精确重抛"分析时会算出：try 块里能抛的受检异常只有 `IOException`，
所以 `throw e` 等价于 `throws IOException` —— 而方法没声明。

解法：包成 `IllegalStateException` 抛出去，由全局异常处理器兜底成 500。

### 坑 3：EasyExcel 的 `autoCloseStream` 默认是 true

`writer.finish()` 会顺手把 `OutputStream` 关掉。
所以**不能**在 try 块里提前关流，否则 xlsx 的 zip 尾部写不出去，文件损坏。

### 坑 4：日期列 + 文本格式 = 一串数字

周期维表导出时，如果把 `LocalDate` 直接交给 EasyExcel，写进去的是"日期数值"；
而这一列又被设成文本格式 → 显示出来是 `46023` 这样的序列号。

解法：**先把日期转成字符串再写**，让单元格里从头到尾只有一种类型。

### 坑 5：验证脚本少数了一行

`verify-export.py` 里一开始写成：

```python
if i == 0: header = row
elif i == 1: first = row
else: data_rows += 1
```

结果统计出来 35,903，而 `COUNT(*)` 是 35,904，差 1 行，排查了十几分钟。

> 教训：**"跳过表头"和"跳过首行数据"是两件事，别写在一个 if-else 链里。**

### 坑 6：`rows-per-sheet` 越界

配置项可能被人手改成 200 万（"我想一个 sheet 装完"）。
那不是配置，那是让 POI 抛异常。

解法：在 `record` 的紧凑构造器里夹紧：

```java
public SheetSpec {
    if (rowsPerSheet <= 0 || rowsPerSheet > EXCEL_MAX_DATA_ROWS) {
        rowsPerSheet = EXCEL_MAX_DATA_ROWS;
    }
}
```

**配置的边界值应该在读取时就夹紧，而不是等运行时炸了再回来看配置。**

### 坑 7：拒绝了却返回 HTTP 200

本项目所有业务异常都走 `GlobalExceptionHandler` → `Result.fail()` → **HTTP 200 + body.code=500**。
这是国内项目很常见的约定，但对**下载类接口**不太合适：

- 用 `<a href>` 直接点的用户，被拒时浏览器会把 JSON 显示成一段文字（还好，不是坏文件）
- 更规范的做法是返回 `429 Too Many Requests` / `400 Bad Request`

如果要做，加一个专门的异常 + `@ResponseStatus` 即可。本次保持项目内一致，先不改。

## 十一、自测题（先自己答，再往下看）

**Q1.** `LIMIT 400000, 2000` 和 `WHERE id > 427031 LIMIT 2000`，同样的数据、
同样的排序，为什么一个 85ms 一个 0.5ms？

<details>
<summary>答案</summary>

前者要**先按顺序数出 40 万行再丢掉**（B+ 树没有"第 N 个"的概念，只能从头走），
所以成本跟 offset 成正比；后者直接在 B+ 树上**定位**到 427031，往后再取 2000 行，
成本恒定。实测前者扫 402,000 行、后者扫 2,000 行。
</details>

**Q2.** 游标分页能不能做"跳到第 100 页"？

<details>
<summary>答案</summary>

不能。它只能"下一页"，因为它是靠"上一页最后一个 id"定位的，
没有这个 id 就不知道从哪开始。所以游标分页只适合导出/滚动加载，
后台管理那种带页码的分页器还得用 OFFSET（用户不会翻到第 10 万页）。
</details>

**Q3.** 如果业务要求按 `update_time` 排序，游标怎么写才不漏数据？

<details>
<summary>答案</summary>

不能只用 `WHERE update_time > ?` —— 同一时刻可能有多条记录，会漏掉。
要用联合游标：`WHERE (update_time > ?) OR (update_time = ? AND id > ?)`，
`ORDER BY update_time, id`。（Day 10 里"僵尸任务"也踩过类似的"只看单个时间字段必误杀"的坑。）
</details>

**Q4.** 为什么导出接口要"先 COUNT 一次再开始写"？多查一次不是更慢吗？

<details>
<summary>答案</summary>

因为 HTTP 响应是流式的，**一旦开始写就不能回头**。
如果用户筛出 300 万行，而你不先数一遍就闷头导，最后会撞上 Excel 的 104 万行上限或者 OOM ——
用户拿到一个打不开的文件，还拿不到任何错误提示，会反复重试把服务器再压一遍。
多花几十毫秒 COUNT，换来"永远不会有半截文件"。
</details>

**Q5.** 用 Semaphore 限流导出，为什么默认不等（`tryAcquire()` 而不是 `tryAcquire(timeout)`）？

<details>
<summary>答案</summary>

导出要跑 10 秒以上。让用户排队等，他前端就是一个转圈页面，
等到网关超时（通常 60 秒）可能页面都关了 —— 白占一个 Tomcat 线程。
直接拒绝 + "请稍后重试"，用户 3 秒后重试，体验反而更好。这就是 fail fast。
</details>

**Q6.** `export_log` 写入失败，为什么可以吞掉异常？而导入任务的状态更新失败就不能吞？

<details>
<summary>答案</summary>

判断标准是：**这个数据丢了，会不会导致业务状态不一致？**
导出日志丢了，用户照样拿到了文件，只是少了一条审计记录 → 旁路，可以吞。
导入任务状态丢了，用户会看到"一直在跑"、系统会重复投递、重试机制也失效 → 记账，不能吞。
一句话：**旁路可以吞，记账不能吞。**
</details>

**Q7.** 为什么维表（150 行）导出不做游标分页，而明细（48 万行）必须做？

<details>
<summary>答案</summary>

按数据量级选择。150 行一次查完只要几毫秒、几 KB 内存，
套游标 + 切 sheet 只会让代码更复杂、性能一点不涨。
48 万行一次查完要 480MB，256MB 堆下直接 OOM。
**不是"哪个写法更高级"，而是"哪个更匹配这个量级"。**
</details>

## 十二、面试话术（可以直接背）

**① 你项目里导出是怎么做的？**
> 用游标分页 + 流式写出。每次从库里取 2000 行，转成导出 VO 写进 ExcelWriter，
> 然后丢掉这批对象，内存里永远只有一个页的量。
> 实测 48.96 万行的表，一次性全查要 481MB 堆，流式只用 95MB；
> 在 256MB 堆下流式能完整导出 22MB 的 Excel，一次性全查直接 OOM 把服务打挂。

**② 为什么不用 LIMIT offset？**
> 因为 OFFSET 的成本跟偏移量成正比，它是"数出 N 行再丢掉"，不是"跳到第 N 行"。
> 全表 48.96 万行、每页 2000 条要翻 245 页，总成本是 O(n²)。
> 我实测过：同样 245 页，游标 138.81ms，OFFSET 8977.26ms，差 64.7 倍。
> 单页对比更明显：第 40 万行起取 2000 条，OFFSET 扫 402,000 行要 85ms，
> 游标扫 2,000 行只要 0.5ms。

**③ Excel 行数有上限吗？**
> 有，xlsx 格式写死单 sheet 最多 1,048,576 行 × 16,384 列，超出 POI 抛
> IllegalStateException。我做了自动分 sheet，写满 100 万行就新建一个，
> 而且处理了"一批数据跨过 sheet 边界"的情况 ——
> 这个 bug 只在每页条数不整除每 sheet 行数时才出现，用整数测试数据测不出来。

**④ 导出把数据库拖慢了怎么办？**
> 导出是只读但极贵的操作，48 万行的顺序扫描会把 buffer pool 冲刷掉，
> 让本该 10ms 的统计查询也变慢。所以导出通道要独立限流：
> 用 Semaphore 限制同时导出数，拿不到许可立刻返回"请稍后重试"（实测 65ms 返回，不排队）。
> 单机限流多实例会失效，全局限流得上 Redis 计数器或网关限流。

**⑤ 导出中途失败了怎么办？**
> 关键是"所有校验前置"：HTTP 响应一旦开始写就改不了状态码。
> 所以限流、COUNT、参数校验全部在 setHeader 之前做完，
> 之后如果还失败（磁盘满、连接断），只能记日志 + 安静结束，
> 用户会拿到不完整文件 —— 这个取舍我在手册里写清楚了，
> 要更可靠就得改成"先落临时文件、成功后再回传"。

**⑥ 大文件导出用户看不到下载进度，怎么解决？**
> 因为流式响应不设 Content-Length，Tomcat 用 chunked，浏览器显示不了百分比。
> 三种解法：先落临时文件（多一次全量读写）、做异步任务 + 前端轮询进度（像导入那样）、
> 或者接受没有进度条。我们选了第三种，因为不是所有体验问题都值得用架构解决。

**⑦ 你怎么知道流式导出真的省内存？有数据吗？**
> 有。我专门做了一个实验接口（默认关闭，`@ConditionalOnProperty` 控制），
> 用 `System.gc()` 对齐基线后测堆占用：同样 48.96 万行，
> 一次性全查峰值 508MB（增量 481MB），游标流式峰值 121MB（增量 95MB）。
> 而且耗时几乎一样（4283 vs 4307ms）—— 说明流式是白赚的内存，不是拿时间换的。

**⑧ 这段代码你觉得哪里还能改进？**
> 两个：① 业务异常现在都返回 HTTP 200 + body.code，对下载接口不够规范，
> 被限流应该返回 429；② 限流是单机的，多实例部署要改成 Redis 全局计数。
> 另外导出日志表会无限增长，生产上要按月分区或者定期清理。

## 十四、前端怎么接（这段直接能用）

因为导出接口"成功返回文件、失败返回 JSON"，
前端必须用 `blob` 接，然后按 `Content-Type` 判断：

```javascript
async function download(url, fallbackName = '导出.xlsx') {
  const resp = await fetch(url, { responseType: 'blob' });
  const type = resp.headers.get('Content-Type') || '';

  // 失败：后端返回的是 JSON（我们的约定是 HTTP 200 + body.code）
  if (type.includes('application/json')) {
    const err = await resp.json();
    alert(err.message || '导出失败');
    return;
  }

  // 成功：从 Content-Disposition 里取文件名（服务端已加 Expose-Headers）
  const cd = resp.headers.get('Content-Disposition') || '';
  const m = /filename\*=UTF-8''([^;]+)/.exec(cd);
  const name = m ? decodeURIComponent(m[1]) : fallbackName;

  const blob = await resp.blob();
  const a = document.createElement('a');
  a.href = URL.createObjectURL(blob);
  a.download = name;
  a.click();
  URL.revokeObjectURL(a.href);   // ★ 必须释放，否则 blob 一直占着内存
}
```

三个要点：

1. **必须判断 `Content-Type`** —— 后端两种响应都走 HTTP 200，不看类型会把 JSON 存成 .xlsx。
2. **文件名要从 `filename*=UTF-8''` 里取**，别用 `filename=`（那是 ASCII 兜底，可能是 URL 编码的乱码）。
3. **`URL.revokeObjectURL` 必须调用**，否则每下载一次就泄漏一块内存，
   用户连续导出几次页面就卡了。

```
新增数据导出：游标分页 + 流式写 + 自动分 sheet + 并发限流

导出是"只读但极贵"的操作，本次解决三个问题：

1. 深翻页 O(n²)
   把 LIMIT offset,size 换成 WHERE id > ? 的游标分页。
   实测 245 页 / 48.96 万行：游标 138.81ms，OFFSET 8977.26ms，差 64.7 倍；
   单页第 40 万行起对比：扫 2,000 行 vs 402,000 行。

2. 内存随数据量线性增长
   边查边写，内存里永远只有一页（2000 条）。
   实测 48.96 万行：一次性全查峰值 508MB，流式 121MB；
   在 256MB 堆下流式可完整导出 22MB Excel，一次性全查直接 OOM 导致服务不可用。

3. 导出拖慢在线功能
   Semaphore 限制并发导出数（默认 2），拿不到许可 65ms 内快速失败，
   不排队、不占 Tomcat 线程。同时写 export_log 便于事后排查。

其它细节：
- Excel 单 sheet 上限 1,048,576 行，超限自动分 sheet（含"一批跨边界"处理）
- 所有校验（限流/计数/参数）前置于 setHeader，避免用户拿到半截文件
- 编码列设为文本格式，防止 2027-01 被 Excel 变成日期
- 中文文件名 RFC 5987 双写 + Access-Control-Expose-Headers
- 导出日志写入失败不影响导出结果（旁路可以吞，记账不能吞）
```
