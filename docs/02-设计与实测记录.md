## 1. 索引优化：133 ms → 9.66 ms

### 问题

大屏的趋势图要查"工业类指标在 2024/2025/2026 三年的合计值"：

```sql
SELECT f.period_code, SUM(f.indicator_value)
FROM fact_indicator_value f
JOIN dim_indicator i ON i.indicator_code = f.indicator_code
WHERE f.deleted = 0
  AND f.period_type = 'Y'
  AND f.period_code IN ('2024','2025','2026')
  AND i.category = '工业'
GROUP BY f.period_code;
```

表里 489,600 行，`EXPLAIN` 结果是 `type=ALL`、`key=NULL`、`rows=487354`——**全表扫**。

### 为什么原来的索引用不上

表上原本有一个唯一索引：

```
uk_fact (region_code, indicator_code, period_code)
```

看起来"周期"和"指标"都在里面，为什么还用不上？

**因为 B+ 树只能从最左列开始找入口。** 打个比方：

> 一本电话簿按「姓 → 名」排序。要找所有姓"刘"的人，翻到 L 就行——很快。
> 但如果你的条件是"名字里第二个字是'德'"呢？电话簿帮不上忙，只能从第一页翻到最后一页。

`uk_fact` 的第一列是 `region_code`，而**这条 SQL 从头到尾没有 `region_code` 这个条件**（那个版本是按分类查，不是按区域查）。最左列没给值 → B+ 树没法定位 → 整个索引作废。

这就是**最左前缀原则**：不是"只要条件里包含索引列就能用"，而是"必须从最左列开始连续命中"。

### 做法

新建一个联合索引：

```sql
ALTER TABLE fact_indicator_value
    ADD INDEX idx_tpi (period_type, period_code, indicator_code);
ANALYZE TABLE fact_indicator_value;   -- 更新统计信息，让优化器知道有它
```

**列顺序的三条依据**：

1. `period_type` 是**等值条件**（`= 'Y'`），且每条查询必带 → 放最左。等值列在最左，能把 B+ 树的搜索范围一次收窄到一段连续区间。
2. `period_code` 是 `IN ('2024','2025','2026')`——`IN` 本质上是"多个等值"，也算范围，必须排在等值列后面。
3. `indicator_code` 是 JOIN 带过来的等值条件 → 放最后，让索引尽量"覆盖"到它。

**为什么不能反过来把 `period_code` 放最左？** 因为 `IN` 是多个不连续的区间，后面的列在每个区间里还要再扫一遍；等值列放在最左，后续列在每个等值点内部才是有序的。

### 数字

| | 优化前 | 优化后 |
|---|---|---|
| 平均耗时（50 次稳态均值） | **133.45 ms** | **9.66 ms** |
| 提升 | | **13.8×** |
| 扫描行数 | 489,618 | 5,418 |
| 执行计划 | `type=ALL` `key=NULL` `rows=487354` | `type=range` `key=idx_tpi` `rows=5400` |

### 复现

```bash
# 完整实验（含 A/B/C 三个候选方案的对比）见 sql/04-索引优化实验.sql
mysql -u root -p area_econ

EXPLAIN SELECT ...;                    -- 优化前：type=ALL
ALTER TABLE fact_indicator_value ADD INDEX idx_tpi (period_type, period_code, indicator_code);
ANALYZE TABLE fact_indicator_value;
EXPLAIN SELECT ...;                    -- 优化后：type=range, key=idx_tpi

-- 加完索引一定要校验结果一致（否则可能"变快了但答案错了"）
SELECT COUNT(*) FROM fact_indicator_value WHERE period_type='Y' AND period_code IN ('2024','2025','2026');
```

**⚠️ 加索引之后必须做的一件事**：`SELECT` 的结果和优化前**逐行比对**。索引能加快查询，也能因为统计信息过期让优化器选错执行计划，出现"结果少了几行"。快不等于对。

### 设计取舍

> "这个查询慢的原因不是数据量大，是索引根本没用上。
> 表上有一个 `uk_fact(region_code, indicator_code, period_code)` 唯一索引，
> 看起来什么都有，但这条 SQL 里**没有 `region_code` 条件**。
> B+ 树只能从最左列开始定位，最左列缺失就等于没有索引，只能全表扫 48 万行。
>
> 我建了 `idx_tpi(period_type, period_code, indicator_code)`，顺序是这么定的：
> `period_type` 是等值条件、每条查询必带，放最左；`period_code` 是 IN，算范围，放第二；
> `indicator_code` 是 JOIN 带过来的等值条件，放最后。
> **等值在前、范围在后**，这是联合索引列顺序的基本规则。
>
> 加完之后从 133ms 降到 9.66ms，扫描行数从 48.9 万降到 5,418。
> 加完我还做了一件事：把结果和优化前逐行比对，确认没有因为优化器选错计划导致少返回数据。"

**关于「索引是不是越多越好」**：

> "不是。每个索引在写入时都要维护，`INSERT`/`UPDATE` 都会变慢，还占存储；索引多了优化器也可能选错。
> 所以只给高频查询建，并且定期查 `sys.schema_unused_indexes` 清理没人用的索引。"

## 2. 改 SQL 结构：43 ms → 10.57 ms，一个索引都没加

### 问题

大屏的"分类汇总"要按区域列出每个区域的总值。最早的写法是：

```sql
-- 简化的示意：区域名从维表 JOIN 进来
SELECT r.region_name, SUM(f.indicator_value)
FROM fact_indicator_value f
JOIN dim_region r ON r.region_code = f.region_code
JOIN dim_indicator i ON i.indicator_code = f.indicator_code
WHERE ...
GROUP BY f.region_code;
```

### 为什么慢——原因和上一个完全不一样

慢的不是"扫的行多"，而是：

- `dim_indicator` 是**维表**，只有几百行，用来过滤 `category = '工业'`。为了拿到"哪些 indicator_code 属于工业"，MySQL 要先查一遍维表，把结果（**约 30 个编码**）拿回来，再用 `IN (30 个值)` 去过滤事实表。这叫**半连接（semi-join）**。
- `dim_region` 是为了**取区域名字**。但它是在 `GROUP BY` 之后才需要的东西——每个分组只需要一个名字，却要对**每一行事实数据**都参与一次 JOIN 匹配。

实测的代价：**600 次随机点查 + 1,350 次回表**（`performance_schema` 数出来的）。

### 做法

两件事，都跟"少做无用功"有关：

**① 维表不 JOIN，改成先查一次编码列表，再用 `IN` 塞进去。**

几百行的维表，用一次查询把 30 个 `indicator_code` 拿到 Java 里，再作为参数传进主查询。这比让 MySQL 每次做 semi-join 便宜——**维表是"少量多次"的访问模式，缓存一次比关联一次划算**。

**② 区域名字不在 SQL 里 JOIN，改成查完之后在 Java 里补。**

```java
// 查完 150 条结果后，一次性把所有 region_code 对应的名字捞出来
Map<String, String> nameMap = loadRegionNameMap(codes);
rows.forEach(r -> r.setRegionName(nameMap.get(r.getRegionCode())));
```

这就是典型的**N+1 变 1+1**：原来是"150 个分组各 JOIN 一次维表"，现在变成"1 次主查询 + 1 次批量查名字"。

### 数字（这一组最有意思）

| | 优化前 | 优化后 |
|---|---|---|
| 平均耗时 | **43.38 ms** | **10.57 ms** |
| 提升 | | **4.1×** |
| 扫描行数 | **1,668** | **5,568** |
| 数据库内部动作 | 600 次点查 + 1,350 次回表 | 1 次顺序范围扫描 |

**扫描行数涨了 3.3 倍，耗时反而降到 1/4。**

这就是这一组最该记住的一句话：

> **扫描行数少 ≠ 快。**
>
> 1,668 行如果是**600 次随机 I/O** 凑出来的，比 5,568 行**一次顺序 I/O** 慢得多。
> 机械硬盘上随机读一次的代价约等于顺序读几百行；SSD 上差距小一些，但仍然存在。
> 所以看 `EXPLAIN` 的 `rows` 只能当参考，**真正要优化的是"访问模式"，不是那个数字**。

### 复现

```bash
# sql/05-JOIN结构优化实验.sql 里有三种写法的对照
mysql -u root -p area_econ

-- 用 performance_schema 数"到底查了多少次"，而不是只看耗时
SELECT * FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC LIMIT 5;
```

### 设计取舍

> "这个接口我优化了两次，第一次以为要加索引，后来发现瓶颈不在索引。
>
> 原 SQL 有两个 JOIN：一个关联指标维表用来过滤分类，一个关联区域维表用来取名字。
> 第一个 JOIN 是 semi-join，MySQL 要先查维表拿到 30 个编码再回主表过滤；
> 第二个 JOIN 更亏——区域名字只在 `GROUP BY` 之后需要，每个分组一个名字就够，
> 却要对每一行事实数据都匹配一次。
>
> 我把它拆成三步：先查一次维表拿到编码列表，用 IN 传进主查询；主查询只查事实表；
> 查完在 Java 里批量补区域名。本质是**把 N+1 变成 1+1**。
>
> 结果是 43ms 降到 10.5ms。有意思的是扫描行数从 1,668 涨到了 5,568，反而快了 4 倍——
> 因为原来是 600 次随机点查，现在是一次顺序扫描。**扫描行数少不等于快，访问模式才是关键。**
> 这个反例让我后来看执行计划不再只盯着 rows 那个数字。"

## 3. Redis 读通路：23.3 ms → 5.37 ms

### 问题

大屏首页会同时打 4 个统计接口，参数组合高度重复（同一个区域、同样的周期，几秒内被刷新多次）。每次都要跑一次聚合查询。

### 做法

标准的 Cache-Aside：

```
请求 → 拼 key → 查 Redis
                 ├ 命中 → 直接返回（不碰数据库）
                 └ 未命中 → 查库 → 写回 Redis（带 TTL）→ 返回
```

几个具体决定：

| 决定 | 选择 | 为什么 |
|---|---|---|
| 序列化 | `StringRedisTemplate` + Jackson，**不用 JDK 序列化** | JDK 序列化体积大、跨语言不可读，而且反序列化有安全风险 |
| 更新策略 | **删除**缓存，不更新缓存 | 两个并发写可能因执行顺序把旧值后写进去，删除更安全 |
| TTL | 600 s + **随机抖动** | 防止大量 key 同时过期（雪崩） |
| 空值 | 存一个哨兵值（短 TTL） | 防止查不存在的数据每次都穿到库（穿透） |

### 数字

| | 优化前（MISS） | 优化后（HIT） |
|---|---|---|
| 接口耗时 | **23.3 ms** | **5.37 ms** |
| 其中缓存层自身 | —— | **0.68 ms** |
| 50 次请求期间执行的 SQL 条数 | 50 | **0** |
| 命中率 | —— | **93.4%**（hit=240 / miss=17） |

**"SQL 条数 = 0"这个数字比耗时更有说服力。** 因为耗时会被 JIT 预热、GC、机器负载影响，而 `performance_schema` 的语句计数是账面事实。

这也解释了一个常见误区：**"加了缓存但没变快"**，很可能是 key 拼错了（每次都 miss）。所以要数命中率，不能只看耗时。

### 复现

```bash
curl -s -H "X-User-Id: 1" "http://localhost:18080/api/stat/cache-stats"
# → hit=240 miss=17 命中率=93.4% 防击穿=开启

# 数数据库真正执行了几条 SQL（比看耗时可靠）
mysql -u root -p -e "
SELECT COUNT_STAR, LEFT(DIGEST_TEXT,60)
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT LIKE '%fact_indicator_value%' ORDER BY COUNT_STAR DESC LIMIT 5;"
```

### 设计取舍

> "大屏是典型的读多写少，同一个参数组合几秒内会被反复请求。
> 我加了 Cache-Aside 模式的 Redis 缓存，命中时接口从 23ms 降到 5.4ms。
>
> 但我不太喜欢用耗时证明缓存生效，因为 JIT 预热和 GC 会让耗时抖动。
> 我改用 `performance_schema` 数 SQL 条数——缓存命中的 50 次请求期间，
> 数据库执行的相关 SQL 是 **0 条**。这是账面事实。
>
> 序列化我用的 `StringRedisTemplate` 加 Jackson，不用 JDK 序列化：体积小、可读、
> 而且 JDK 反序列化有安全风险。
> 更新策略是**删除**不是更新——两个并发写请求如果更新缓存，可能因为执行顺序把旧值后写进去。"

## 4. 缓存写通路 + 防击穿：50 并发 → 1 次查库

### 问题

加完缓存之后，出现了两个新问题：

**问题一：数据改了，缓存还是旧的。**
改一个区域的名字，大屏上要等到 TTL 到期（10 分钟）才变。

**问题二：热点 key 过期的瞬间，大量请求同时打到数据库。**
这就是"缓存击穿"。实测：50 个并发同时打一个刚过期的 key，数据库执行了 **50 次**同样的聚合查询。

### 做法

**① 删除缓存必须在事务提交之后（`afterCommit`）。**

```java
// 错误写法：在方法内直接删
@Transactional
public void updateRegion(...) {
    regionMapper.updateById(r);
    redis.delete(key);        // ← 事务还没提交，别的线程可能立刻读库拿到旧值，又把旧值写回缓存
}

// 正确写法：注册事务同步回调
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override public void afterCommit() { evictCache(...); }
    });
```

如果提前删，会出现这个经典时序：

```
T1: 改数据库，删缓存
T2: 读请求 → 缓存空 → 读数据库（此时 T1 事务还没提交，读到旧值）
T1: 事务提交
T2: 把旧值写回缓存  ← 缓存从此一直是脏的，直到 TTL 到期
```

**② 批量删除用 `SCAN`，不用 `KEYS`。**

`KEYS pattern` 会遍历全部 key 并**阻塞 Redis 单线程**，生产环境上是事故。`SCAN` 是游标式渐进遍历，每次返回一小批，删完一批再拿下一批游标。

**③ 击穿用 `SETNX` + TTL + Lua 释放。**

```
请求 → 缓存 miss → SETNX lock:key（带 TTL）成功？
                       ├ 成功 → 查库 → 写缓存 → Lua 比对 token 后删锁
                       └ 失败 → 等 1 秒，重试读缓存；还拿不到就**直接降级查库**
```

**关键细节：抢不到锁的请求不能无限等。** 等 1 秒还拿不到就直接查库——这看起来违背了"只让一个人查"的初衷，但对比"让用户等 10 秒"或者"报错"，这是更好的选择。

**删除锁必须用 Lua 比对 token**：如果只是 `DEL lock`，会出现

```
T1 拿到锁，但执行超过 TTL，锁自动释放
T2 拿到新锁
T1 执行完，DEL lock  ← 把 T2 的锁删了
T3 又能拿到锁 → 两个请求同时查库
```

### 数字

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 50 并发打冷 key | 数据库执行 **50 次** | **1 次** |
| 改区域名后前端可见 | 最慢等到 TTL 到期（600 s） | **下一次请求即返回新值** |
| 精准失效（只改排序字段） | —— | 缓存 key 数 **1 → 1 不变**（判定为不影响统计，不删） |
| Redis 不可用时 `/trend` | 约 **1,000 ms**（白等锁） | **23 ms**（跳过抢锁直接查库） |

最后一行特别值得说：把 Redis 指向一个不存在的端口（模拟故障），接口从白等 1 秒变成 23ms。**缓存是锦上添花，不能因为缓存挂了把整个服务拖死。**

### 复现

```bash
# A/B 三轮：关掉防击穿 vs 打开
python tools/cache-stampede-test.py

# 模拟 Redis 故障（改端口，不要停服务）
# 然后把 spring.data.redis.port 改成 6399 重启，打 /api/stat/trend
```

### 设计取舍

> "缓存加完反而带来两个新问题：数据一致性，和击穿。
>
> 一致性上，删缓存必须放在事务提交之后。如果在事务里删，会出现这个时序：
> 我删了缓存，另一个线程读不到缓存就去读库——但我的事务还没提交，它读到旧值，
> 然后把这个旧值写回缓存。缓存从此一直是脏的。
> 所以我用 `TransactionSynchronizationManager` 注册 `afterCommit` 回调。
>
> 批量失效我用 SCAN 不用 KEYS，因为 KEYS 会阻塞 Redis 的单线程。
>
> 击穿我用 SETNX 加 TTL 做互斥，抢到锁的去查库，抢不到的等。
> 但有个细节：**抢不到锁的不能无限等**，等 1 秒拿不到就直接降级查库。
> 还有删锁必须用 Lua 比对 token——如果只是 DEL，第一个请求执行超时后锁自动释放，
> 第二个请求拿到新锁，第一个请求执行完把第二个的锁删了，第三个请求又能进来，等于没锁。
>
> 实测 50 个并发同时打一个冷 key，加锁前数据库执行 50 次，加锁后 1 次。
> 另外我把 Redis 指向一个不存在的端口模拟故障，接口从白等 1 秒变成 23 毫秒——
> 缓存应该是锦上添花，不能因为缓存挂了把服务拖死。"

## 5. Excel 异步导入：5,090 ms → 56 ms

### 问题

同步导入 1 万行 Excel：

```
用户点上传 → 接口阻塞 → 逐行 INSERT 10,800 次 → 5,090 ms → 才返回
```

前端转圈 5 秒，用户不知道进度，网络差一点就超时重传，然后数据重复。

### 做法（两层，分开算账）

**第一层：批量插入代替逐行插入。**

```
逐行 INSERT：10,800 次网络往返 + 10,800 次事务
每 500 行一批：22 次 INSERT
```

实测 **5,090 ms → 651 ms（7.8×）**。这一层是数据库层面的优化。

**第二层：异步接单。**

```
上传 → 算文件 MD5 → 查任务表（幂等）→ 落任务记录 → 提交线程池 → 立刻返回 taskId
                                                        ↓
                                              前端轮询 /task/{id}
```

实测 **接单 56 ms（91× 快）**，后台实际跑 1,082 ms。

**注意这两个数字的口径不同**：5,090 → 651 是"数据真的写完了"的耗时；56 ms 是"接口返回了"的耗时，数据还没写完。**这里必须说清口径，否则看起来像在玩数字游戏。**

### 任务表的三个设计决定

| 决定 | 做法 | 为什么 |
|---|---|---|
| 顺序 | **先落库，再提交线程池** | 反过来的话，提交成功但落库失败，任务永远消失；现在的顺序最坏是"库里有一条 PENDING 没执行"，可以被补偿扫描捡回来 |
| 记账 | **线程池只干活，任务表才记账** | 线程池的队列长度、活跃线程数是运行时状态，重启就没了；用户要查的是"我那次导入成功了吗" |
| 拒绝策略 | **`AbortPolicy`**，不用 `CallerRunsPolicy` | 见下 |

**为什么不用 `CallerRunsPolicy`：**

看起来它很优雅——"队列满了就让提交任务的线程自己跑，形成自然背压"。但这里的提交方是 **Tomcat 的 Web 线程**。它一跑导入，接口就重新变成同步阻塞了，你辛辛苦苦做的异步全废。而且拒绝时**必须把任务标记为 FAILED**，否则用户永远看到 PENDING。

### 数字

| 指标 | 数值 |
|---|---|
| 逐行插入 10,800 行 | **5,090 ms** |
| 每 500 行批量 | **651 ms**（7.8×） |
| 异步接单返回 | **56 ms**（91×） |
| 后台实际处理 | 1,082 ms |
| 10 线程并发上传同一文件 | 只建 **1 个**任务（9 个撞唯一键） |
| 服务重启后查任务 | 仍返回 SUCCESS / 10800（状态在库里，不在内存） |

### 复现

```bash
# 造一份 1 万行的 Excel
python tools/gen-import-excel.py

# 上传（异步）
curl -F "file=@data/import/test-10000.xlsx" \
     -H "X-User-Id: 1" http://localhost:18080/api/import/async

# 盯任务状态
python tools/watch-task.py 1
```

### 设计取舍

> "原来同步导入 1 万行要 5 秒，用户一直等着，还会超时重传导致重复数据。
> 我做了两层：先把逐行 INSERT 改成每 500 行一批，5,090ms 降到 651ms；
> 再改成异步，接口只负责落任务、提交线程池、返回 taskId，接单只要 56ms。
>
> 这里我要说清楚口径：**651ms 是数据真写完了，56ms 只是接口返回了**。
> 这两个不能混着说。
>
> 任务表这里有两个设计我比较在意。第一是**先落库再提交线程池**——
> 反过来如果先提交成功、落库失败，这个任务就永远消失了；
> 现在的顺序最坏情况是库里有一条 PENDING 但没执行，可以被补偿扫描捡回来。
> 第二是**拒绝策略用 AbortPolicy 不用 CallerRunsPolicy**。
> CallerRuns 看起来是优雅背压，但提交方是 Tomcat 线程，它一跑导入接口就又变同步了。
> 拒绝的时候必须把任务标成 FAILED，不然用户一直看到 PENDING。"

## 6. 失败重试与幂等：可重试的前提是可重入

### 问题

做完异步导入之后，我加了一个"失败重试"。第一次实现直接重放失败批次，结果是：

```
ERROR 1062 (23000): Duplicate entry '430102-1-1-2024' for key 'uk_fact'
```

因为**纯 `INSERT` 不能重放**。第一次执行已经把数据写进去了，重试时再插同样的行就撞唯一键，整批回滚。

### 关键认识

> **"可重试"的前提是"可重入"。**
>
> 一个操作如果执行两次的结果和执行一次不一样，它就不能被重试。
> 所以在写重试逻辑之前，先问：**这个操作重复执行安全吗？**
> 如果不安全，先把操作本身改成幂等的，再谈重试。

### 做法

**① 把 `INSERT` 改成 `INSERT ... ON DUPLICATE KEY UPDATE`（upsert）。**

```sql
INSERT INTO fact_indicator_value (region_code, indicator_code, period_code, indicator_value, deleted)
VALUES
  <foreach ...>
ON DUPLICATE KEY UPDATE
  indicator_value = VALUES(indicator_value),
  deleted = 0;                        -- ← 这一行是关键，见下
```

**`deleted = 0` 是踩出来的。** `uk_fact` 这个唯一索引**不包含 `deleted` 字段**，所以逻辑删除的行**仍然占着唯一键**。如果 upsert 不显式把 `deleted` 置回 0，重试时那行永远是 `deleted=1`，看起来"导进去了"但查不出来。

**② 指数退避，但绝不 `sleep`。**

```
第 1 次失败 → 等 1s  → next_retry_time = now + 1s
第 2 次失败 → 等 2s  → next_retry_time = now + 2s
第 3 次失败 → 等 4s  → next_retry_time = now + 4s
第 4 次失败 → 标 FAILED，retry_count = 3
```

`sleep` 会把线程占死。正确做法是**把"什么时候再试"写进数据库**（状态 `RETRY_WAIT` + `next_retry_time`），由一个定时任务（500ms 扫一次）去捞到期的任务。这样线程可以立刻去干别的，服务重启也不丢。

**③ 僵尸任务回收。**

服务在任务执行到一半时被 kill，那条记录会永远停在 `RUNNING`。启动时（以及之后每 500ms）扫一遍：

```sql
UPDATE async_task
SET status = 'PENDING', retry_count = retry_count + 1
WHERE status = 'RUNNING' AND update_time < NOW() - INTERVAL 5 MINUTE;
```

**阈值必须远大于单个任务的最大耗时**，否则会把正在正常执行的长任务误杀。如果任务可能跑很久，要**打心跳**（定期更新 `update_time`），不能只看 `update_time`。

**④ 异常分类：先判子类，再判父类。**

```java
if (e instanceof RetryableImportException) {     // 可重试：网络抖动、锁等待超时
    scheduleRetry();
} else if (e instanceof IllegalArgumentException) {  // 不可重试：数据格式错，重试一万次也一样
    markFailed();
}
```

顺序反了会出事：如果先判 `Exception`，所有异常都被当成可重试，一个格式错误的数据会被重试 3 次、白等 7 秒才报错。

### 数字

| 实验 | 结果 |
|---|---|
| 纯 INSERT 重放 | `ERROR 1062 Duplicate entry ... uk_fact` |
| 3 行批量，第 1 行冲突 | **整批回滚**，另外 2 行一行未进（批量 INSERT 的原子性） |
| upsert 重放 | 行数不变，`affected_rows = 2`（更新算 2 行） |
| 退避实测间隔 | **1.705 s / 2.669 s / 4.288 s**（含调度开销，比理论的 1/2/4 略长） |
| 三次耗尽 | 10.777 s 后标 FAILED，`retry_count = 3` |
| 手动重试后 | SUCCESS，总行数 **500,400**（不是 505,900，重试没有重复插入） |
| 僵尸回收 | 服务启动后 **249 ms** 发现并恢复 |
| 非法数据 | **0.005 s** 直接 FAILED，不进重试队列 |

`affected_rows` 那个细节值得记：MySQL 的 `ON DUPLICATE KEY UPDATE` 返回值——**插入记 1，更新记 2，值没变化记 0**。所以批量 upsert 的返回值**不能当行数用**，混在一起算会得出荒谬的数字（这就是为什么上面"总行数 500,400"要用 `COUNT(*)` 验证，而不是看返回值）。

### 设计取舍

> "重试这块我踩了一个大坑。第一次做完重试，一跑就报 `Duplicate entry` 撞唯一键。
> 因为我原来用的是纯 INSERT，第一次已经写进去了，重试再插就冲突。
>
> 这件事让我记住一句话：**可重试的前提是可重入**。一个操作如果执行两次跟执行一次结果不一样，
> 它就不该被重试。所以我先把它改成 `INSERT ... ON DUPLICATE KEY UPDATE`，
> 重放就变成幂等覆盖了。
>
> 改的时候还踩了个更细的：唯一索引不含 `deleted` 字段，所以逻辑删除的行仍然占着唯一键。
> upsert 必须显式 `SET deleted = 0` 才能把删掉的行复活，否则重试完看着成功、其实查不出来。
>
> 退避我没用 `Thread.sleep`，因为那会把线程占死。我是把状态改成 `RETRY_WAIT`，
> 把 `next_retry_time` 写进数据库，让定时任务去捞到期的。好处是线程立刻能去干别的，
> 而且服务重启也不丢。
>
> 实测间隔是 1.7、2.7、4.3 秒，比理论的 1/2/4 长一点，是调度开销造成的。
> 三次耗尽之后标 FAILED，手动重试成功，总行数 500,400，没有产生重复数据。"

**关于「事务边界」**：

> "这里有个容易被忽略的点：**事务边界由调用方决定**。
> 如果内层方法自己标了 `@Transactional`，但它是被外层事务调用的，那它其实在同一个事务里，
> 自己的提交根本不生效。还有同类内部自调用会绕过 AOP，`@Transactional` 直接失效。
> 所以我在需要独立事务的地方用 `TransactionTemplate` 显式控制，不靠注解。"

## 7. 导入闭环：错误明细必须独立事务

### 问题

最初导入失败，只在任务表上记一行：

```
async_task.error_msg = "导入失败：3 条数据不合法"
```

用户拿到这句话完全没法行动——**哪 3 条？哪一列？我改哪个单元格？**

### 做法

**① 把错误结构化地存下来，一条错误一行记录。**

```sql
CREATE TABLE import_error_row (
    id           BIGINT PRIMARY KEY AUTO_INCREMENT,
    task_id      BIGINT      NOT NULL,
    row_index    INT         NOT NULL,   -- Excel 第几行
    error_type   VARCHAR(32) NOT NULL,   -- BAD_PERIOD_TYPE / NEGATIVE_VALUE / ...
    column_name  VARCHAR(64),
    raw_value    VARCHAR(512),           -- ⚠️ 用 VARCHAR 不用 DECIMAL
    error_message VARCHAR(512)
);
```

**`raw_value` 用 `VARCHAR` 而不是数值类型，是踩出来的。** 因为要存的是"用户填错的原始值"，比如 `"2027-01"`、`"abc"`、`"－12"`（全角减号）。如果用 `DECIMAL`，**记录这个错误动作本身就会失败**——你用数值类型去存一个不是数字的东西。

> **描述错误的表，不能假设数据是合法的。**

**② 错误明细必须用独立事务写。**

这是这一节最重要的一条。看这个错误写法：

```java
@Transactional
public void importFile(...) {
    for (row : rows) {
        try { save(row); }
        catch (Exception e) {
            errorRowMapper.insert(new ImportErrorRow(...));   // ← 和业务在同一个事务
            throw e;
        }
    }
}
```

问题：业务异常一抛，**整个事务回滚，连你刚写的错误明细也一起回滚了**。用户下载错误报告，拿到一张空表。

正确做法：错误明细用 `TransactionTemplate` 在**独立事务**里先提交，再抛异常。

```java
transactionTemplate.executeWithoutResult(status -> errorRowMapper.insert(errorRow));
throw new ImportValidationException(...);   // 此时错误明细已经落库了
```

**③ 提供两种导出：只导错误行 / 全量带标注。**

用户改完错误后要重新上传，导哪一份？——**必须是全量**。这里有个危险的陷阱：

> 如果只给他"错误行"那份，他改完重传，**正确的行就永久丢失了**。
> 更糟的是任务状态会显示 SUCCESS，因为在他上传的那份文件里，每一行都是合法的。

实测（E1）：只改错误行重传 → 任务 SUCCESS，2989 行，但库里只有 2928 行，**丢了 7,072 行**。
全量带标注重传（E2）→ SUCCESS 10000 行，总数正确。

**④ Excel 日期化：`2027-01` 变 `2027/1/1`，发生在用户输入的那一刻。**

Excel 会把看起来像日期的字符串自动转成日期格式。这个转换**发生在用户敲回车的时候，程序无法挽回**。

对策是在模板里把那一列设成**文本格式**（`@`），并且要作用在**整列**上：

```java
WriteCellStyle textStyle = new WriteCellStyle();
textStyle.setDataFormat((short) 49);        // 49 = 文本
sheet.setDefaultColumnStyle(colIndex, textStyle);   // 列级默认样式，对新增行生效
```

用 `setDefaultColumnStyle` 而不是逐格设样式——逐格设对后续新增的行无效。

### 数字

| 实验 | 结果 |
|---|---|
| 改造前错误信息 | 只有一句总数，**5 条**示例 |
| 改造后错误明细 | **2,989 条全量**，落库 6 批共 **412 ms** |
| 错误类型分布 | `BAD_PERIOD_TYPE` 2,629 行（87.96%）/ 负值 224 行（7.49%）/ 必填空 106 行（3.55%）/ `BAD_NUMBER` 30 行（1.00%） |
| 导出错误行 | 142 KB / **154~308 ms** |
| 导出全量 10,000 行 | 413 KB / **278~415 ms** |
| 截断到 100 条时 | 真实 2,989 / 明细 100 / `truncated=true` / 百分比之和 **100%** |
| **E1：只改错误行重传** | SUCCESS 2,989 行，库里仅 **2,928 行，丢 7,072 行** |
| **E2：全量带标注重传** | SUCCESS 10,000 行，总数 **499,600** |

**截断时百分比的分母要用 `recordedRows` 而不是真实总数。** 如果真实 2,989 条、只记了 100 条，用 2,989 做分母，四类占比加起来只有 3.34%，看起来像算错了。

### 设计取舍

> "这块是我觉得最贴近真实业务的部分。原来导入失败只记一句『3 条数据不合法』，
> 用户根本不知道改哪里。我把它改成一条错误一行记录：行号、列名、错误类型、原始值。
>
> 有两个细节是踩出来的。第一个是**原始值必须用 VARCHAR 存**。
> 因为你存的是用户填错的东西，可能根本不是数字。用 DECIMAL 的话，
> **『记录这个错误』的动作本身就会失败**——描述错误的表不能假设数据是合法的。
>
> 第二个是**错误明细必须独立事务**。如果和业务数据在同一个事务里，
> 业务一抛异常回滚，你刚写的错误明细也一起回滚了，用户下载到一张空表。
> 我用 `TransactionTemplate` 单独提交再抛异常。
>
> 还有一件事我觉得挺重要：用户改完错误要重传，我一开始只提供『只导错误行』。
> 后来意识到这是个陷阱——他重传的只有那 2989 行，剩下 7000 多正确的行就永久丢了，
> 而且任务还会显示 SUCCESS，因为上传的文件里每一行都是合法的。
> 实测丢了 7,072 行。后来改成提供全量带标注的导出，改完直接传。"

## 8. 游标导出：8,977 ms → 138.81 ms

### 问题

全量导出 48.96 万行。第一版用 `LIMIT offset, size` 翻页，每页 2,000 行，共 245 页。

实测：**8,977 ms**。

### 为什么慢 —— 这是全篇最重要的一个原理

很多人以为 `LIMIT 400000, 2000` 的意思是"跳到第 40 万行，取 2000 行"。

**不是。它的真实语义是"先数出前 400,000 行，把它们全部丢掉，再取 2,000 行"。**

所以翻页的代价是这样的：

```
第 1 页    ：数 2,000 行      → 取 2,000 行
第 2 页    ：数 4,000 行      → 取 2,000 行
第 3 页    ：数 6,000 行      → 取 2,000 行
...
第 245 页  ：数 490,000 行    → 取 2,000 行
```

总扫描量 ≈ 2000 × (1+2+...+245) ≈ **6,000 万行**。这是 O(n²)。

实测单页对比最能说明问题：

| | 取第 40 万行附近的一页 |
|---|---|
| `LIMIT 400000, 2000` | **85.4 ms**，扫 **402,000** 行 |
| 游标 `WHERE id > 400000 LIMIT 2000` | **0.528 ms**，扫 **2,000** 行 |
| | **162×** |

翻到后面越慢，前面很快——**这就是 O(n²) 的典型特征**。

### 做法：游标分页（keyset pagination）

```sql
SELECT ... FROM fact_indicator_value
WHERE id > #{lastId}          -- ← 上一页最后一行的 id
ORDER BY id
LIMIT #{size}
```

每页都从"上一页结束的位置"开始，**扫描量恒定**，不管翻到第几页都是扫 2,000 行。

### 三个必须知道的限制

| 限制 | 说明 |
|---|---|
| 排序键必须**唯一且有序** | `id` 满足。如果按 `update_time` 排，**同一时间戳的多行会丢**——必须用联合游标 `(update_time, id)` |
| **不能跳页** | 它只能顺序往下翻。后台管理页面的页码器（用户点"第 87 页"）仍然只能用 OFFSET |
| 数据在导出期间变化会有偏差 | 导出不是快照。严格一致要靠事务隔离级别或读快照 |

**所以游标分页不是"OFFSET 的升级版"，它是另一种访问模式**——只适合导出、滚动加载这类"一路往下走"的场景。这个区分很容易混淆。

### 数字

| | OFFSET 翻页 | 游标分页 |
|---|---|---|
| 245 页 / 48.96 万行总耗时 | **8,977.26 ms** | **138.81 ms** |
| 提升 | | **64.7×** |
| 单页扫描量 | 随页码线性增长 | 恒定 2,000 行 |
| 第 40 万行处的单页 | 85.4 ms | 0.528 ms |

### 复现

```bash
# sql/08-导出翻页对比实验.sql 里有两种写法的对照表
# 服务里对应 FactIndicatorValueMapper.xml 的 selectForExportByCursor
python tools/verify-export.py --file data/export/fact-xxx.xlsx
```

### 设计取舍

> "全量导出 49 万行，第一版用 `LIMIT offset, size` 翻页，245 页要 9 秒。
>
> 慢的原因是 `LIMIT 400000, 2000` 的语义不是『跳到第 40 万行』，
> 而是『**先数出 40 万行丢掉，再取 2000 行**』。翻到后面，前面全白扫了，
> 总扫描量是 O(n²)。
>
> 我改成游标分页，用 `WHERE id > 上一页最后的id ORDER BY id LIMIT 2000`，
> 每页扫描量恒定。245 页从 8,977ms 降到 138.81ms。
> 单页对比更明显：取第 40 万行附近的数据，OFFSET 要 85ms 扫 40 万行，游标 0.5ms 扫 2,000 行。
>
> 但游标分页有代价，我一般会主动说：**它不能跳页**。
> 所以它只适合导出和滚动加载，后台那种可以点『第 87 页』的分页器还是得用 OFFSET。
> 另外排序键必须唯一有序，按非唯一列排要用联合游标，否则同一时间戳的行会丢。"

## 9. 行级数据权限：5 个用户，150 / 11 / 1 / 11 / 0

### 问题

之前所有接口都是"谁能调，谁就能看全部 48.96 万行"。政企系统里这是不可能的——长沙的用户只能看长沙的数据。

### 做法：过滤条件下推到数据库

**核心决定：不在 Java 里过滤。** 原因有三个，缺一不可：

1. **性能**：Java 里过滤，数据库照样把全量数据传回来，网络和内存都白花。
2. **内存**：48 万行结果集要装进堆。
3. **分页正确性**：这是最隐蔽的——数据库给你 20 行，你滤掉 17 行，前端看到 3 行，**而且不报错**。用户以为"只有 3 条数据"。

实现方式是 MyBatis-Plus 的 `InnerInterceptor` + JSqlParser 改写 SQL：

```java
@DataScope(alias = "f")     // 声明这条查询的事实表别名
List<RegionMetricStatVO> selectCategorySummary(...);
```

```sql
-- 改写前
WHERE f.deleted = 0 AND i.category = ? AND f.period_code IN (?,?)
-- 长沙市用户（region_code = 4301）请求，改写后
WHERE f.deleted = 0 AND i.category = ? AND f.period_code IN (?,?) AND f.region_code LIKE '4301%'
```

业务代码一行 `if` 都没加。7 个 Mapper 方法加个注解就够了。

### 六个必须讲对的技术点

**① 必须用 AST 改写，不能用字符串拼接。**

```java
// 危险写法
String newSql = sql + " AND f.region_code LIKE '4301%'";
```

如果原 SQL 是 `WHERE a = 1 OR b = 2`，拼完变成：

```sql
WHERE a = 1 OR b = 2 AND f.region_code LIKE '4301%'
```

`AND` 的优先级高于 `OR`，实际等价于 `a=1 OR (b=2 AND 权限)`——**权限被 OR 短路了，越权且不报错**。

JSqlParser 的 `AndExpression` 构造出来**天然带括号**，从语法树上就避免了这个问题。

**② 插件顺序 = 执行顺序，权限必须在分页之前。**

```java
interceptor.addInnerInterceptor(dataScopeInnerInterceptor);              // ① 先加权限
interceptor.addInnerInterceptor(new PaginationInnerInterceptor(MYSQL));  // ② 再加分页
```

顺序反了会怎样？分页插件先执行，它的 COUNT 语句数的是**全量**，然后再套权限条件。结果：

| | 正确顺序 | 顺序反转 |
|---|---|---|
| changsha 的 `total` | **35,904** | **489,600** |
| `pages` | 1,796 | 97,920 |
| 实际返回的数据 | 正确 | **也正确** |

**数据是对的，只有总数错。** 这种 bug 前端不会报错，只能靠跟基线对账发现。

**③ 子查询要按别名递归找层级。**

`TOP N` 那条 SQL 长这样：

```sql
SELECT * FROM (
    SELECT ..., RANK() OVER (PARTITION BY ...) rn FROM fact_indicator_value f ...
) t WHERE t.rn <= 3
```

条件加在**外层**会报 `Unknown column 'f.region_code'`——外层根本没有 `f` 这个别名。必须递归找到子查询内部，把条件加在 `f` 所在的那一层。

**④ 辖区为空必须 fail-closed。**

```java
// 危险写法：少写一个 else
if (user.getRegionCode() != null) {
    conditions.add(regionLike(user.getRegionCode()));
}
// 没有 else → regionCode 为 null 时，一个条件都不加 → 等于全量
```

实测后果：`data_scope = REGION` 但辖区为 NULL 的用户，从应该看到 0 个区域，变成看到 **150 个（全省）**。接口 200、日志无异常、前端正常显示。

正确写法是显式加 `1 = 0`：

```java
if (regionCode == null || regionCode.isBlank()) {
    conditions.add("1 = 0");     // 明确"什么都看不到"
}
```

> **安全代码里，"跳过"就是"放行"。** 业务代码里跳过一条数据是容错，安全代码里跳过一条规则是漏洞。
> 所以默认值永远往"更严格"的方向选：配置缺失 → 拒绝，枚举不认识 → 拒绝，找不到别名 → 抛异常。

**⑤ 缓存 key 必须带权限指纹。**

这是全篇最隐蔽的一个坑。加了缓存之后，流程变成：

```
请求 → 拼 key → 命中 Redis → 直接返回
                    ↑
              SQL 根本没执行
```

**而数据权限是靠"改写 SQL"实现的。SQL 不执行，权限就不生效。**

实测后果：admin 先查了一次，结果写进缓存；changsha 用同样的参数请求，**命中同一个 key**，直接拿到 150 个区域，**越权 139 个**。耗时 1.12 ms，SQL 改写次数 0——拦截器工作得完美无缺，是缓存把权限整个绕过去了。

修法是 key 里加"权限指纹"：`stat:category-summary:工业:Y:2024,2025,2026:R4301`，最后一段由 `scopeKey()` 收敛成三种值：

| 用户 | `data_scope` | `region_code` | `scopeKey()` |
|---|---|---|---|
| admin | ALL | 430000 | `ALL` |
| changsha | REGION | 4301 | `R4301` |
| viewer | REGION | **NULL** | `NONE` |

**为什么不能直接拼 `regionCode`**：`ALL` 用户的 regionCode 可能是 `430000`，也可能是 `null`；`REGION + null` 一定是 `null`。直接拼的话两者会撞成同一个 key——而它们一个能看 48.9 万行，一个一行都看不到。

**⑥ 改写结果的缓存，key 里不能带参数值。**

JSqlParser 解析 + 拼回，一条 SQL 约 **0.92 ms**。一个导出请求 245 条 SQL，就是 225ms 纯花在"拆字符串再拼回去"上。

但这件事的结果**每次都一样**：只取决于 (哪条 SQL, 谁的权限范围)，参数值完全不影响——我们只是往 WHERE 里 AND 一个常量前缀，`?` 占位符一个都不动。

所以加一层缓存，key = `msId | scopeKey | SQL文本`：

| | 优化前 | 优化后 |
|---|---|---|
| 每条 SQL 改写开销 | **0.92 ms** | **0.057 ms**（稳态 0.02 ms） |
| 缓存命中率 | —— | **99.9%** |

**为什么 key 里不能带参数值**：如果带了，用户随便传什么参数都能造一个新 key，key 空间被用户输入撑爆——这是缓存最经典的事故之一。

## 10. 我是怎么让这些数字可信的

性能数字很容易停留在"我感觉快了"。这里刻意做了四件事：

### ① 不只看耗时，看"账面"

耗时会被 JIT 预热、GC、机器负载影响。所以关键结论用**数据库自己的账本**：

```sql
-- 这条 SQL 到底执行了几次
SELECT COUNT_STAR, SUM_ROWS_EXAMINED, SUM_ROWS_SENT
FROM performance_schema.events_statements_summary_by_digest
WHERE DIGEST_TEXT LIKE '%fact_indicator_value%';
```

"缓存命中时 SQL 条数为 0"、"50 并发只查库 1 次"——这些是**账面事实**，不是耗时推断。

### ② 先跑对照组

测优化效果之前，先把优化**临时关掉**跑一遍。第 4 组（防击穿）、第 11 组（改写开销）都是 A/B 各三轮。

很多"优化了 80%"的结论，其实是两次测量的误差。**没有对照组的优化数据不可信。**

### ③ 承认反直觉的结果

第 2 组优化后扫描行数从 1,668 涨到 5,568，耗时反而降到 1/4。我把这个反例写进了文档，而不是把 1,668 那个数字藏起来。

**行数少 ≠ 快**，这个结论比"我加了个索引变快了"有价值得多。

### ④ 把错误也测一遍

第 9 节里那三种"故意改错"的实验——fail-open、插件顺序反转、去掉缓存权限指纹——都是我把代码真的改错后跑出来的。

**知道自己哪里会错，比知道自己哪里对了更难，也更值钱。**

### 关于测量误差，两条实话说在前面

1. **Windows 上 `curl` 命令每次起进程 + 建连接要 50~70 ms**，会把接口耗时完全淹掉。所以耗时测量一律用复用了 keep-alive 连接的 Python 脚本（`http.client`），不用 `curl` 循环。
2. **新启动的 JVM 前几十次请求不准**（JIT 还没编译热点代码）。所有耗时数据都是预热后取稳态均值，样本量在 25~100 次之间。

## 11. 已知限制

| # | 限制 | 生产该怎么做 |
|---|---|---|
| 1 | 身份用 `X-User-Id` 请求头，**谁都能伪造** | 换 JWT / Session / SSO，身份从令牌解析 |
| 2 | `async_task` / `import_error_row` **没有 `user_id`**，知道 taskId 就能下载别人的错误明细 | 加 `create_user_id` + 辖区**快照**（人会调辖区，历史任务该按当时的算）。这个漏洞是我写的扫描工具自己扫出来的 |
| 3 | SQL 改写结果缓存在**单机内存** | 多实例各存一份也无害；要共享的话 key 必须含 `msId + scopeKey + SQL 文本` |
| 4 | 导出限流 `Semaphore` **只限单机** | 多实例要换成网关限流或 Redis 计数器 |
| 5 | 测试以**端到端脚本**为主，没有 JUnit 单测 | 退避计算、key 构造、错误分类这些纯逻辑应该补单测——端到端覆盖不到分支 |
| 6 | 单机线程池，没有 MQ | 任务量再大一个量级换 MQ + 独立消费者 |
| 7 | 权限只做了**读** | 写操作要在执行前校验"这条数据归属谁" |

**为什么要把这些写出来**：一个说不出自己边界的项目，比一个有边界的项目更可疑。
能立刻列出三条具体的、带修法的限制，比一句"还需要继续优化"有意义得多。

## 12. 延伸问题

这些问题不在上面九组里，但排查时经常遇到。

| 问题 | 一句话答案 | 详细 |
|---|---|---|
| MP 3.5.9 的分页为什么要单独引依赖？ | 3.5.9 起把 JSqlParser 拆成独立包 `mybatis-plus-jsqlparser`，不引就没有分页 | §1 索引优化 |
| 手写 SQL 会不会自动加 `deleted = 0`？ | **不会**。`@TableLogic` 只管框架生成的 SQL，手写 XML 必须自己写 | §1 索引优化 |
| `BigDecimal` 有什么坑？ | `divide` 必须给 scale + RoundingMode，比大小用 `compareTo`，0 和 null 要区分 | §2 改 SQL 结构 |
| 缓存 key 怎么拼才不出错？ | 三铁律：入参不漏 / 集合排序去重 / **角色参数绝不排序**（判据：交换两个值结果会不会变） | §3 Redis 读通路 |
| 线程池拒绝策略选哪个？ | `AbortPolicy`。`CallerRunsPolicy` 会让 Web 线程变同步 | §5 Excel 异步导入 |
| 多实例怎么防止重复投递？ | 抢占式 `UPDATE ... WHERE id=? AND status=?`，比分布式锁轻 | §6 失败重试 |
| Excel 中文文件名乱码怎么解决？ | `URLEncoder` + `replace("+","%20")` + `filename*=UTF-8''` + `Access-Control-Expose-Headers` | §8 游标导出 |
| 流式导出的响应还能改吗？ | **不能**。`setHeader` 之后所有失败只能记日志静默结束，再抛会让 Spring 二次写响应 | §8 游标导出 |
| EasyExcel 的 Listener 能单例吗？ | **不能**，它是有状态的 | §5 Excel 异步导入 |
| 为什么不用 `KEYS` 删缓存？ | 阻塞 Redis 单线程 | §4 缓存写通路 |
