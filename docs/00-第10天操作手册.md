## 0. 先看这张图（今天所有代码都围着它转）

```
                        ┌──────────────────────────────────┐
                        │                                  │
   ① 用户上传           │   ② 后台执行                     │
   ─────────→ PENDING ──┼──→ RUNNING ──③ 成功──→ SUCCESS  │
                 ↑      │        │                         │
                 │      │        │ ④ 失败                  │
                 │      │        ↓                         │
                 │      │  ┌───────────────────────────┐   │
                 │      │  │ 是临时故障？ 还有次数吗？ │   │
                 │      │  └────────┬──────────────────┘   │
                 │      │    有 ────┴──── 没有 / 确定性失败│
                 │      │     ↓                    ↓      │
                 │      │  RETRY_WAIT            FAILED    │
                 │      │     │                    │      │
                 │      └─────┼────────────────────┼──────┘
                 │            │                    │
                 │   ⑤ 调度器扫到 next_retry_time  │
                 │      到点，抢占式改成 PENDING    │ ⑥ 人工点"重试"
                 └────────────┘                    └──────→ PENDING

  ⑦ RUNNING 超过 5 分钟没动静（服务重启/线程被杀）
     └──→ 调度器判定为"僵尸" ──→ RETRY_WAIT（或次数用完 → FAILED）
```

**记住五个状态和一句话**：

| 状态 | 含义 | 谁写的 |
|---|---|---|
| `PENDING` | 刚建好 / 排队中 | 上传接口、调度器、手动重试 |
| `RUNNING` | 正在跑 | 抢占成功的那个工作线程 |
| `RETRY_WAIT` | 失败过一次，等退避时间到 | 失败处理逻辑、僵尸回收 |
| `SUCCESS` | 成功 | 工作线程 |
| `FAILED` | 彻底失败（不可重试 or 次数用完） | 失败处理逻辑、僵尸回收 |

## 1. 昨天留了个什么坑

### 1.1 先说现象

昨天的导入是这么跑的（1 万行，每 500 行一批，共 20 批）：

```
第 1 批  → 提交成功 ✅ 500 行落库
第 2 批  → 提交成功 ✅ 累计 1000 行
...
第 10 批 → 提交成功 ✅ 累计 5000 行
第 11 批 → 数据库连接断了 ❌ 抛异常
```

任务变成 `FAILED`，`success_rows = 5000`。

**但数据库里已经躺了 5000 行。**

### 1.2 你现在点"重试"会发生什么

Day 9 的 `insertBatch` 是纯 `INSERT`。重试会从文件第 1 行重新开始写：

```
第 1 批  → INSERT 第 1~500 行
        → 这 500 行里，有一部分（或全部）已经存在于表里了
        → 撞唯一索引 uk_fact(region_code, indicator_code, period_code)
        → 整批 500 行全部回滚 ❌
第 1 批（重试第 2 次）→ 同样的结果 ❌
第 1 批（重试第 3 次）→ 同样的结果 ❌
→ 放弃，永久 FAILED
```

**这个文件永远导不进去了。** 而且用户看到的是"重试了 3 次还是失败"，
完全不知道问题在于"上次已经成功了一半"。

### 1.3 所以今天的第一句话

> **"可重试"的前提是"可重入"。**

- **可重试** = 失败了可以再执行一遍
- **可重入**（幂等）= 执行一遍和执行一百遍，结果完全一样

一个不可重入的操作套上重试框架，只会把"失败一次"变成"失败四次"，
还把数据库多压三遍。**先保证可重入，再谈重试。**

## 3. 核心概念（用大白话讲）

### 3.1 幂等 / 可重入 —— 电梯按钮的比喻

电梯的"1 楼"按钮，你按一次它亮，按十次它还是亮，电梯该来还是来。
**按十次的效果和按一次一样，这就叫幂等。**

反过来，如果每按一次电梯就来一趟，你连按十次就会来十趟 —— 那不幂等。

数据库里的对应关系：

| 操作 | 幂等吗 | 为什么 |
|---|---|---|
| `UPDATE ... SET x = 5` | ✅ 幂等 | 执行几次都是 5 |
| `UPDATE ... SET x = x + 1` | ❌ 不幂等 | 执行几次就加几次 |
| `INSERT` | ❌ 不幂等 | 执行几次就多几行（有唯一索引时是"报错"） |
| `INSERT ... ON DUPLICATE KEY UPDATE` | ✅ 幂等 | 撞了就改成更新，行数不变 |
| `DELETE WHERE id = 1` | ✅ 幂等 | 删几次结果都是"没了" |

我们的导入是**批量 INSERT**，所以天然不幂等。必须改成 upsert。

### 3.2 指数退避 —— 为什么要等 1 秒、2 秒、4 秒，而不是每秒都试

假设数据库挂了 5 秒正在重启。三种策略：

**策略一：不等，立刻重试**
```
失败 → 立刻重试 → 失败 → 立刻重试 → 失败 → ...
1 秒内试了 1000 次，全部无效，还把刚起来的数据库又打了一遍
```

**策略二：固定等 1 秒**
```
失败 → 等 1s → 试 → 失败 → 等 1s → 试 → ...
好一点，但如果数据库要 10 秒才恢复，前 9 次全是白费
```

**策略三：指数退避（我们今天用的）**
```
失败 → 等 1s → 试（失败）
     → 等 2s → 试（失败）
     → 等 4s → 试（成功）
累计等 7 秒，只在必要的时候打扰对方
```

直觉是：**越失败说明对方越没好，就越该少打扰它。**

工业上还常见"指数退避 + 随机抖动"：等 `2^n + random(0,1)` 秒。
加随机是为了防"惊群"—— 如果 1000 个任务同时失败，它们会在同一毫秒一起重试，
把刚恢复的系统瞬间再打死一次。

### 3.3 ★ 为什么绝对不能在 catch 里 sleep 然后重试

这是今天最需要记住的一条。先看错误写法：

```java
catch (Exception e) {
    for (int i = 0; i < 3; i++) {
        Thread.sleep(1000);          // ❌ 在这里睡
        try { doImport(); return; } catch (Exception ignore) {}
    }
}
```

在单线程脚本里这段代码是对的。在我们的线程池里是三重灾难：

**灾难一：白占线程**

线程池 `core=4`。也就是说全系统最多同时跑 4 个导入。
如果 4 个任务都在 `sleep`，等于 **4 个线程全部瘫痪**，
第 5 个用户上传的文件连"接单"都排不上。

> `sleep` 的线程和干活的线程是**同一种资源**，睡 1 秒就少 1 秒的并发能力。

**灾难二：服务一重启，重试计划全丢**

重试的"计划"只存在于方法的栈帧（内存）里。
发版、OOM、断电 —— 全丢。用户还在轮询 taskId，永远等不到结果。
Day 9 我们特意把任务落库就是为了防这个，结果重试又把它丢回内存里了。

**灾难三：没法观测、没法干预**

运营想知道"现在有几个任务在等重试"，答案是"在某个线程的 for 循环里"。
你查不出来，也没法让它"立刻重试"或者"别重试了"。

**正确做法（今天实现的）**：

```
失败 → 把"什么时候重试"写进数据库（status=RETRY_WAIT + next_retry_time）
     → 线程立刻释放，去干别的活
     → 到点了，调度器扫出来重新投递
```

一句话：

> **重试的"记忆"必须落库，不能留在内存里。**

这和 Day 9 的"线程池只干活、任务表才记账"是同一条原则的延伸。

### 3.4 异常要分两类 —— 不是所有失败都值得重试

很多人写重试是 `catch (Exception e) { retry(); }`，一行搞定。
但 `Exception` 是个大箩筐，里面装着**性质完全相反**的两类失败：

| 类型 | 例子 | 重试有用吗 |
|---|---|---|
| **临时故障** | 连接池空了、连接被服务端掐断、死锁被回滚、查询超时、网络抖动 | ✅ 过一会儿自己就好了 |
| **确定性失败** | Excel 表头写错、第 800 行是空值、文件被删了、超过 5 万行、SQL 语法错 | ❌ 试一万次结果一样 |

如果无脑重试第二类，用户要白等 7 秒（1+2+4），最后看到一条一模一样的错误。

今天的实测对比（见第五节实验 E）：

| 处理方式 | 用户多久看到结果 |
|---|---|
| 无脑重试 | 10.777 秒（跑了 4 遍才放弃） |
| 分类后 | **0.005 秒** |

判断标准只有一句话：

> **换个时间点重试，结果会不会变？**
> 会变 → 可重试；不会变 → 不可重试。

具体到代码里，判断顺序很关键 —— **必须先判"不可重试"，再判"可重试"**。
因为 Spring 的异常有继承关系：

```
DataAccessException                 ← 父类（连接、超时、死锁）
 ├─ DataIntegrityViolationException ← 子类（唯一索引冲突、字段超长）
 │   └─ DuplicateKeyException       ← 孙类
 └─ BadSqlGrammarException          ← 子类（SQL 写错了）
```

如果先写 `if (e instanceof DataAccessException) return true;`，
那么"唯一索引冲突"也会被误判成可重试 —— 然后重试 3 次全撞同一批，纯浪费时间。

### 3.5 僵尸任务 —— 一个最难查的线上问题

任务被标成 `RUNNING` 之后，如果发生这些事：

- 发版重启（哪怕只重启 5 秒）
- 线程池被 `shutdownNow` 强杀
- OOM 被操作系统干掉
- 进程被 `kill -9`

这条任务就会**永远停在 RUNNING**。用户轮询到天荒地老，
看到的是"任务执行中，请稍候"。

**这为什么最难查？** 因为数据库里看着一切正常：状态是 RUNNING，行数也有，
就是不动。你甚至怀疑是前端没刷新。

**对策：用 `update_time` 当"心跳"。**

```
RUNNING 且 update_time 已经 5 分钟没变过  →  判定为僵尸 → 收回来重新排队
```

⚠️ 这里有个必须想清楚的边界：**怎么区分"卡死的僵尸"和"正在跑的大任务"？**

如果阈值设成 30 秒，而某个 5 万行的导入要跑 60 秒，就会被**误杀** ——
调度器以为它死了，重新投递一份，于是两个线程同时导同一个文件。
虽然 upsert 能兜住数据不重复，但白白浪费一倍资源，而且日志会非常乱。

我们的取值：**300 秒**。理由：
- 实测 1 万行约 1 秒，5 万行（上限）约 5 秒
- 300 秒有 60 倍余量，几乎不可能误杀

真实项目里如果任务能跑几十分钟（比如导出百万行报表），
就必须让任务**定期更新心跳**（每 10 秒 touch 一次 update_time），
不能只靠"最后一次状态变更时间"，否则一定会误杀。

## 5. 五个实验和实测数字

> 环境：MySQL 8.0.46 / Redis 5.0 / JDK 21 / 1.0.0 jar / 端口 18080
> 基线：`fact_indicator_value` = 489,600 行，`async_task` = 0 条
> 测试文件：`data/import/indicator-import-10000.xlsx`（10,800 行 = 150 区域 × 12 指标 × 2027 年 1~6 月）

### 实验 A：证明纯 INSERT 不可重入（对照组）

**A-1 重放一条已存在的记录**

```sql
INSERT INTO fact_indicator_value (region_code, indicator_code, period_code, period_type, indicator_value, data_source)
SELECT region_code, indicator_code, period_code, period_type, indicator_value, data_source
FROM fact_indicator_value WHERE period_code='2027-01' LIMIT 1;
```

结果：

```
ERROR 1062 (23000) at line 1: Duplicate entry '430000-1-1-1-2027-01'
                              for key 'fact_indicator_value.uk_fact'
```

**A-2 一行冲突会不会导致整批失败？**

一条 SQL 插 3 行，第 1 行故意撞唯一索引：

```sql
INSERT INTO fact_indicator_value (region_code, indicator_code, period_code, period_type, indicator_value, data_source) VALUES
('430000','1-1-1','2027-01','M', 1.0, '测试-冲突行'),
('999998','TEST-1','2027-06','M', 1.0, '测试-新行A'),
('999999','TEST-2','2027-06','M', 1.0, '测试-新行B');
```

结果：

```
ERROR 1062 (23000) at line 2: Duplicate entry '430000-1-1-1-2027-01' ...

查那 2 行新数据有没有进去：
should_be_zero
0          ← 一行都没进去
```

**这两条一起证明了**：批量 INSERT 是**整批原子**的，
只要 500 行里有 1 行撞索引，其余 499 行也全部作废。

所以"半截数据 + 纯 INSERT + 重试" = 永远失败，逻辑闭环。

**A-3 换成 upsert 之后（实验组）**

```sql
INSERT INTO fact_indicator_value (...)
SELECT ..., f.indicator_value + 1, ...
FROM fact_indicator_value f WHERE f.period_code='2027-01' ORDER BY f.id LIMIT 1
ON DUPLICATE KEY UPDATE indicator_value = f.indicator_value + 1;
```

结果：

| 指标 | 值 |
|---|---|
| 执行前总行数 | 495,100 |
| 执行后总行数 | **495,100（没变）** |
| `affected_rows` | **2** |
| 那条记录的值 | 25,369.2496 → **25,370.2496（被覆盖了）** |

两点值得注意：

1. **行数不变**，说明重复写入没有产生新行 → 幂等成立
2. **`affected_rows = 2`** 而不是 1 —— 这是 MySQL 的规定：
   `ON DUPLICATE KEY UPDATE` 走 UPDATE 分支时按"删旧行 + 插新行"算两次。
   **所以这个返回值绝对不能当"写入行数"用**（见第六节坑 2）。

### 实验 B + C：指数退避 + 重试救回任务

**怎么造出"写到一半断了"**

用今天新增的故障注入开关（默认关闭）：

```bash
java -jar target/area-econ-metrics-1.0.0.jar \
     --server.port=18080 \
     --stat.import.test.fail-at-batch=12
```

含义：写到第 12 批时强制抛 `RetryableImportException`。
此时前 11 批（11 × 500 = 5,500 行）**已经提交落库**，正是我们要的"半截数据"。

**观察到的完整时间线（200ms 轮询精度）**

```
  0.005s  PENDING     successRows=-      totalRows=-
  0.233s  RUNNING
  1.070s  RETRY_WAIT  successRows=5500   totalRows=10800   ← 第 1 次失败
  2.732s  RUNNING                                        ← 退避后重跑
  3.142s  RETRY_WAIT  successRows=5500
  5.815s  RUNNING
  6.223s  RETRY_WAIT  successRows=5500
 10.573s  RUNNING
 10.777s  FAILED      successRows=5500   ← 4 次尝试后放弃
```

**后台日志里的退避间隔**

```
20:11:37.636  第 1 次执行失败，1 秒后重试
20:11:39.341  调度器重新投递         ← 实测间隔 1.705 秒
20:11:39.756  第 2 次执行失败，2 秒后重试
20:11:42.425  调度器重新投递         ← 实测间隔 2.669 秒
20:11:42.768  第 3 次执行失败，4 秒后重试
20:11:47.056  调度器重新投递         ← 实测间隔 4.288 秒
20:11:47.430  重试次数用尽（3 次）→ FAILED
```

**为什么实测间隔比配置的 1/2/4 秒多出 0.3~0.7 秒？**

这是必须讲清楚的**测量误差**，不是 bug：

```
配置的退避 1.0 秒
+ 调度器扫描间隔 0~0.5 秒（每 500ms 扫一次，什么时候扫到看运气）
+ 一次导入执行耗时 0.1~0.4 秒（5500 行写库）
= 实测 1.7 / 2.7 / 4.3 秒
```

**结论**：退避的**绝对值**受扫描间隔影响，
但**增长趋势 1 : 2 : 4 是准确的**（1.705 : 2.669 : 4.288 ≈ 1 : 1.57 : 2.51，
扣掉固定的扫描/执行开销后接近 1 : 2 : 4）。

> 做性能实验一定要区分"被测的量"和"测量工具带来的开销"。
> Day 8 压测踩过同样的坑（`xargs -P` 假并发、urllib 代理多 70ms）。

**失败后的数据库状态**

```sql
SELECT id,status,retry_count,success_rows,total_rows,next_retry_time FROM async_task;
```

```
id: 1  status: FAILED  retry_count: 3  success_rows: 5500
total_rows: 10800  next_retry_time: NULL
```

`fact_indicator_value` = **495,100 行**（489,600 + 5,500）。

**然后关掉故障注入，手动重试**

重启（不带 `--stat.import.test.fail-at-batch` 参数），然后：

```bash
curl -X POST http://127.0.0.1:18080/api/import/task/1/retry
```

**结果**

| 指标 | 值 |
|---|---|
| 最终状态 | `SUCCESS` |
| `retry_count` | **0**（手动重试归零） |
| `success_rows` | 10,800 |
| `next_retry_time` | `NULL` |
| `error_msg` | `NULL` |
| `fact_indicator_value` 总行数 | **500,400** |
| 2027 年数据行数 | **10,800** |

**这几个数字为什么是"决定性证据"**

```
如果有 upsert（实际情况）：  489,600 + 10,800 = 500,400  ✅ 对上了
如果没有 upsert（假设）：    489,600 + 5,500 + 10,800 = 505,900  ← 会多出 5,500 行重复
```

而且我们之前用 SQL 故意把某一行 `+1`（25,369.2496 → 25,370.2496），
重试之后它又变回了 **25,369.2496** —— 说明 upsert 的覆盖**确实生效了**。

### 实验 D：僵尸任务自动回收

## 6. 今天踩到的 5 个坑

### 坑 1：MyBatis-Plus 的 `updateById` 会**静默忽略 null 字段**

Day 9 的代码里有这么一段：

```java
AsyncTask running = new AsyncTask();
running.setStatus(RUNNING);
running.setNextRetryTime(null);              // 我以为能清空
asyncTaskMapper.update(running, wrapper);    // ← 实际上这行没进 SQL
```

MyBatis-Plus 的默认字段策略是 `NOT_NULL`：**实体里为 null 的字段不会出现在 SET 子句里**。
所以 `next_retry_time` 根本没被清空，旧值一直挂着。

**为什么这个 bug 特别坏？**
不报错、不抛异常、接口正常返回、日志一切正常。
表现是"重试成功的任务，`next_retry_time` 还留在过去某个时刻"，
运维查表时会误判"它还在等重试"，白查半天。

**修法**：想写 null 就必须显式声明。

```java
asyncTaskMapper.update(null, new LambdaUpdateWrapper<AsyncTask>()
        .eq(AsyncTask::getId, taskId)
        .set(AsyncTask::getStatus, RUNNING)
        .set(AsyncTask::getNextRetryTime, null));   // ← 这样才能真正清空
```

> **铁律**：在 MyBatis-Plus 里，`updateById` 适合"只改非空字段"的场景；
> 只要涉及"把字段改成 null"，一律用 `UpdateWrapper`。
> 这个坑在 yudao / 若依这类框架里同样存在，面试也很爱问。

**证据**：今天实验 B 和 D 之后查库，`next_retry_time` 和 `error_msg` 都是 `NULL`。
换成 Day 9 的写法，这两个字段会残留旧值。

### 坑 2：upsert 的 `affected rows` 语义变了，不能当行数用

| SQL | 返回值含义 |
|---|---|
| 纯 `INSERT` 500 行 | 500 = 插了 500 行 |
| upsert 插 500 行 | 500 |
| upsert 更新 500 行 | **1000**（每行算 2 次） |
| upsert 命中但值没变 | **0** |

批量执行时这些数字会混在一起累加，**根本没法反推真实行数**。

所以 `ImportServiceImpl` 里的 `written` 是自己按"提交成功的批次数 × 批大小"手数的，
**不信 SQL 返回值**。这一点在实验 A-3 里也看到了：单行更新返回 2。

### 坑 3：`deleted = 0` 必须显式写进 SET 子句

唯一索引 `uk_fact` **不包含** `deleted` 字段：

```sql
UNIQUE KEY uk_fact (region_code, indicator_code, period_code)
```

所以一条被逻辑删除的记录（`deleted=1`），它的唯一键**还占着位置**。
再导入同一组 (区域, 指标, 周期) 会撞索引 → 走 UPDATE 分支。

如果 SET 里不写 `deleted = 0`，这行就**永远保持 deleted=1**：

- SQL 不报错
- 接口返回"导入成功"
- 用户查询结果里看不到这条数据

典型的"静默错误"。所以我们的 upsert 最后一行是：

```sql
ON DUPLICATE KEY UPDATE
    period_type     = VALUES(period_type),
    indicator_value = VALUES(indicator_value),
    data_source     = VALUES(data_source),
    deleted         = 0                    -- ← 这一行不能省
```

> 延伸：为什么 `period_type` 也更新？因为 `uk_fact` 里没有它，说明它是"冗余描述字段"，
> 语义上以最后一次导入为准。如果业务要求"历史值不许改"，那 `indicator_value` 也得去掉。

### 坑 4：退避的实测值一定比配置值大

配置 1/2/4 秒，实测 1.705 / 2.669 / 4.288 秒。差值是：
- 调度器扫描间隔 0~500ms
- 一次导入执行耗时 100~400ms

**这不是 bug，是所有"轮询式延迟任务"的固有精度损失。**

想更准只有两条路：
1. 扫描间隔调小（比如 100ms）→ 数据库压力上升
2. 换成延迟队列（RabbitMQ 死信队列 / Redis ZSET / RocketMQ 延迟消息）→ 精度到毫秒，但不省事

对一个"导入"场景来说，几百毫秒的误差完全无所谓。**够用就好。**

### 坑 5：僵尸阈值设小了会误杀正在跑的任务

如果阈值是 30 秒，而某个导入要跑 60 秒：调度器以为它死了 → 重新投递 →
**两个线程同时导同一个文件**。

虽然 upsert 能保证数据不重复，但：
- 白烧一倍 CPU 和数据库连接
- 日志里两条 `runTask` 交叉打印，排查时极其混乱

我们取 300 秒（1 万行实测 1 秒，5 万行上限约 5 秒，60 倍余量）。

**真实项目的解法是"心跳"**：长任务每 10 秒更新一次 `update_time`，
调度器只看心跳而非"最后一次状态变更时间"。这样阈值可以放心设小。

## 7. 面试话术（照着说就行）

### Q：为什么要做失败重试？

> "异步导入是分批提交的，1 万行分成 20 批，每批一个独立事务。
> 这解决了长事务问题，但代价是失去全局原子性 —— 如果第 11 批失败，
> 前 10 批 5500 行已经落库了，撤不回来。
>
> 那时候任务状态是 FAILED，用户看到的是'导了一半'。
> 我要么让用户自己想办法补，要么让系统能自动把剩下的一半补齐。
> 我选了后者，但做之前先解决了一个前提问题：**重入。**

### Q：为什么"可重试"的前提是"可重入"？

> "因为重试的语义是'从头再执行一遍'，而不是'从断点继续'。
> 我的导入是批量 INSERT，如果直接重试，第 1 批就会撞唯一索引，
> 而且批量 INSERT 是整批原子的 —— 500 行里只要有 1 行冲突，整批 500 行全部回滚。
>
> 我实测过：一条 SQL 插 3 行，第 1 行故意撞索引，结果另外 2 行新数据一行都没进去。
> 所以纯 INSERT 的重试**永远不可能成功**，只会把'失败一次'变成'失败四次'。
>
> 解决办法是把 INSERT 改成 `INSERT ... ON DUPLICATE KEY UPDATE`。
> 实测同一份数据重放，行数不变、值被覆盖，跑一遍和跑一百遍结果一样。"

### Q：为什么不在 catch 里 sleep 然后重试？

> "三个原因。
> 第一，线程池是稀缺资源。我的导入线程池 core=4，4 个任务都在 sleep 就等于 0 并发。
> sleep 的线程和干活的线程是同一种资源。
> 第二，重试计划只存在内存里，服务一重启全丢，用户拿到 taskId 却永远等不到结果。
> 第三，无法观测 —— 运营问'现在几个任务在等重试'，答案在某个 for 循环里，查不出来。
>
> 所以我把重试计划写进数据库：status=RETRY_WAIT + next_retry_time，
> 线程立刻释放，由定时调度器到点捞出来重新投递。
> **重试的记忆必须落库，不能留在内存里。**"

### Q：为什么要区分异常类型？

> "因为 Exception 是个大箩筐，里面装着两类性质相反的失败。
> 临时故障（连接断了、死锁、超时）过一会儿自己就好了，重试有意义；
> 确定性失败（数据非法、文件不存在、SQL 写错）重试一万次结果一样。
>
> 无脑重试第二类，用户要白等 1+2+4=7 秒，最后看到一条一模一样的错误。
> 我实测过：一个数据格式错误的文件，无脑重试要 10.777 秒才报错；
> 分类之后 5 毫秒就返回了准确原因。
>
> 判断标准只有一句话：**换个时间点重试，结果会不会变？**
> 另外判断顺序很重要，必须先判子类（唯一索引冲突）再判父类（DataAccessException），
> 否则唯一索引冲突会被误判成可重试。"

### Q：服务重启后卡在 RUNNING 的任务怎么办？

> "用 update_time 当心跳。RUNNING 且超过 300 秒没有更新，就判定为僵尸任务，
> 由调度器收回来重新排队。
>
> 实测：我手动把一条任务改成 RUNNING 并把 update_time 调到 6 分钟前，
> 服务启动后 **249 毫秒**就发现了它，自动回收重跑，最后数据还是正好 10800 行。
>
> 这里有个边界要注意：阈值必须明显大于最大任务的正常耗时，否则会误杀。
> 我 5 万行的上限大约 5 秒，阈值设 300 秒，60 倍余量。
> 如果任务能跑几十分钟，就必须做定期心跳，不能只看最后一次状态变更时间。"

### Q：多实例部署时调度器会不会重复投递？

> "会，所以每个投递动作前都做**抢占式 UPDATE**：
>
> ```sql
> UPDATE async_task SET status='PENDING', next_retry_time=NULL
>  WHERE id=? AND status='RETRY_WAIT' AND next_retry_time <= NOW()
> ```
>
> MySQL 的 UPDATE 会对命中行加排他锁，'判断 + 修改'在一条语句里原子完成。
> 两台机器同时执行，只有一台拿到 affected=1，另一台拿到 0，自动去重。
>
> 这比 Redis 分布式锁好在：不需要额外组件、不用考虑锁超时和续期、
> 状态和锁在同一个事务边界内，不会出现'锁住了但状态没改'的中间态。
> **能用一条带条件的 UPDATE 解决的并发，就别上分布式锁。**"

### Q：这个功能有什么不足？

> "三个。
> 一，退避的实测精度受扫描间隔影响，实测 1.7 秒而配置是 1 秒。想更准得换延迟队列。
> 二，僵尸判定靠 update_time，长任务必须自己打心跳，否则会误杀。
> 三，手动重试没有权限控制，真实项目里应该只允许运维或任务创建者调用，并且要记审计日志。"

## 10. 今天的代码里，最值得记住的五句话

1. **"可重试"的前提是"可重入"。** 不可重入的操作套重试，只会把失败放大 N 倍。
2. **重试的记忆必须落库，不能留在内存里。** `sleep` 重试三重灾难：占线程、重启丢、不可观测。
3. **不是所有失败都该重试。** 判据：换个时间点重试，结果会不会变？
4. **能靠一条带条件的 UPDATE 解决的并发，就别上分布式锁。** 数据库本身就是强一致协调者。
5. **静默错误最贵。** `deleted=0` 不写、null 字段不设、affected rows 当行数用 —— 都不报错，但全是错的。
