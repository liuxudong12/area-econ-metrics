# 第 9 天 · Excel 异步导入（不重复、不丢失、可重试、可查状态）

> 今天把"上传 1 万行 Excel"这件事从**同步阻塞**改造成**异步接单**，
> 并用 MD5 + 唯一索引做双保险，保证同一个文件传 10 次也只导 1 遍。
>
> 这是三条简历亮点里最值钱的一条 —— 它同时考并发、幂等、状态机、容错四件事。

---

## 一、今天的核心矛盾：用户等不了

先说同步版是怎么工作的：

```
用户点"上传" → 请求到达服务器 → 解析 Excel → 逐行/批量写库 → 返回"成功"
              └──────────── 用户一直盯着转圈 ────────────┘
```

在本地测出来的数字是 **5.24 秒**（10,800 行）。看起来还行？

但真实环境不是本地：

| 环节 | 本地 | 真实生产 |
|---|---|---|
| 应用 ↔ MySQL 网络往返 | 0.05 ms | 0.5 ~ 2 ms |
| 并发导入人数 | 1 | 10 ~ 30 |
| 网关超时 | 无 | Nginx 默认 60s，公司网关常配 10~30s |

**1 万行 5 秒，10 万行就是 50 秒。** 用户会先看到浏览器转圈，然后：

1. 觉得卡了，**再点一次上传** → 重复导入（如果没有幂等，数据翻倍）
2. 网关超时，返回 504 → 用户不知道到底成没成功
3. 如果 30 个人同时导入，Tomcat 的线程池会被占满 → **整个服务无法响应其他请求**

第 3 条最致命。Tomcat 默认 200 个线程，看起来很多，但每个线程被一个长请求占住 50 秒，
200 / 30 ≈ 6 轮就排满了。这就是"一个慢接口拖垮整个服务"的典型场景。

## 二、实测：三种方案的数字

同一台机器、同一份文件（10,800 行 / 286.8 KB）、同一个数据库。

| # | 方案 | 接口耗时 | 端到端 | 说明 |
|---|---|---|---|---|
| ① | 同步 · 逐行插入（batchSize=1） | **5,090 ms** | 5.24 s | 1 万次单独的 INSERT |
| ② | 同步 · 批量插入（batchSize=500） | **651 ms** | 0.66 s | 20 次 INSERT，每次 500 行 |
| ③ | **异步 · 接单** | **56 ms** | 0.06 s | 只做：存文件 + 算 MD5 + 插一条记录 + 投递 |

几个结论：

- **① → ②：7.8 倍。** 只改了一个参数（每批写多少行），代码逻辑没变。
  这就是"批量插入"的威力，原因见第八节"坑 4"。
- **① → ③：91 倍。** 因为异步接口根本不干活，它只"接单"。
- **③ 的背景任务实际耗时约 1,082 ms**，和 ② 差不多（同样的分批写入）。
  **异步不是让导入变快了，而是让用户不用等。**

> 这句话是面试的核心表述，值得背下来：
> **"异步没有让任务变快，它只是把'等待'从请求线程挪到了后台线程。"**

## 三、异步是怎么"把等待挪走"的

### 打比方

> **同步**：你去银行办业务，柜台说"您稍等，我给您数 1 万张钞票"。你只能站着等 5 分钟，
> 后面排队的人全堵着。
>
> **异步**：柜台给你一张**取号单**（taskId），说"好了我叫你"。
> 你去旁边坐着刷手机（用户可以去干别的），办完了凭号来取。

关键不在"数钱变快了"，而在**"柜台被释放了"** —— 后面的人可以继续办业务。

### 代码上的流程

```
POST /api/import/async
  │
  ├─ 1. 校验文件（后缀、非空）                  ~0.2ms
  ├─ 2. 读一遍文件算 MD5                        ~20ms
  ├─ 3. 查 async_task.biz_key = MD5
  │      ├─ 有且 SUCCESS  → 直接返回那个 taskId（幂等）      ← 实测 2~3ms
  │      ├─ 有且 RUNNING  → 返回"执行中"
  │      └─ 没有     → 继续
  ├─ 4. 把文件存到 data/import/{md5}.xlsx        ~15ms
  ├─ 5. INSERT async_task (status=PENDING)
  └─ 6. importExecutor.execute(() -> runTask(taskId))
  │
  └─ 立即返回 { taskId, status: "PENDING" }      ← 总计 56ms
```

```
后台线程（import-task-1）：
  runTask(taskId)
    ├─ UPDATE async_task SET status='RUNNING' WHERE id=? AND status='PENDING'
    ├─ 读文件 → EasyExcel 解析 → 校验全部行
    ├─ 校验通过 → 每 500 行一个事务写入
    └─ UPDATE async_task SET status='SUCCESS', total_rows=?, success_rows=?
```

### 状态机

```
                      提交线程池
   PENDING ──────────────────────→ RUNNING ──── 全部成功 ────→ SUCCESS
      ▲                                │
      │                                │
      │                          校验或写库失败
      │                                │
      │                                ↓
      │                          还有重试次数？（Day 10 实现）
      │                                ├── 有 → 算 next_retry_time，回到 PENDING
      └────────────────────────────────┘
                                       └── 没有 → FAILED
```

> ⚠️ 注意 `RUNNING` 那次更新用的是 `UPDATE ... WHERE status='PENDING'`，不是简单的 `updateById`。
> 这是**抢占式更新**：只有把状态从 PENDING 改成 RUNNING 成功的那个线程才继续执行。
> 万一同一任务被投递了两次，只有一个线程能"抢到"，另一个直接退出 —— 避免重复导入。

## 四、关键设计一：任务必须落库，不能只在内存里跑

这是整个异步方案里**最该讲清楚的一点**。

### 反面写法（很多人第一版都这么写）

```java
// ❌ 只丢进线程池，不落库
importExecutor.execute(() -> doImport(file));
return "提交成功";
```

看起来没问题，但服务一重启（发版、OOM、断电）：

- 线程池队列里还没跑的任务 **全没了**
- 用户手里已经拿到"提交成功"的提示 —— 他以为在导，其实什么都没发生
- 他下次再传，又会新建一个任务，**永远不知道上一次丢了**

### 落库之后能得到什么

| 能力 | 靠什么 |
|---|---|
| 用户随时查进度 | `GET /api/import/task/{id}` |
| 服务重启后任务不丢 | 记录在 MySQL 里 |
| 能扫"僵尸任务"重新投递 | `WHERE status IN ('PENDING','RUNNING')`（Day 10） |
| 出问题能追溯 | `total_rows` / `success_rows` / `error_msg` / 时间戳 |

**一句话：线程池只是"干活的"，任务表才是"记账的"。记账必须在数据库里。**

### 实测验证：重启服务后任务还在

```
重启前：taskId=1  status=SUCCESS  totalRows=10800
（停掉进程 —— 内存里的线程池、计数器、缓存全部消失）
重启后：taskId=1  status=SUCCESS  totalRows=10800   ← 完全一样
```

## 五、关键设计二：幂等的两道防线

### 为什么需要幂等

用户会很自然地重复提交：

- 网卡了，点两次"上传"
- 传完没看清结果，刷新页面再传一次
- 同事之间互相转发了同一个文件
- 网关超时，前端自动重试

**如果没有幂等，1 万行数据会变成 2 万行**（如果有唯一索引就会报错，用户看到一堆红色错误）。

### 第一道：业务查询（biz_key = 文件 MD5）

```java
String md5 = DigestUtils.md5DigestAsHex(file.getInputStream());
AsyncTask exist = findByBizKey(md5);
if (exist != null) return buildResult(exist);   // 直接返回已有的，不新建
```

**为什么用 MD5 而不是文件名？**

| 场景 | 用文件名 | 用 MD5 |
|---|---|---|
| 同一文件改个名字再传 | 拦不住 ❌ | 拦住 ✓ |
| 两个不同的文件同名 | 误拦 ❌ | 正常区分 ✓ |
| 文件名带路径（`../../etc/passwd`） | 有安全风险 ❌ | 无影响 ✓ |

实测：把文件复制一份、改名成 `改了名字的副本.xlsx` 再传 —— **仍然返回 taskId=1**，任务表还是 1 条。

### 第二道：唯一索引（`uk_biz_key`）

**光查一次是不够的。** 看这个时序：

```
线程 A: 查 biz_key → 不存在
线程 B: 查 biz_key → 不存在        ← 两个都查到了"没有"
线程 A: INSERT ✓
线程 B: INSERT                    ← 如果不拦，就是两条任务！
```

"查完到插入"之间有窗口，并发下必然重复。真正的闸门是数据库的 `uk_biz_key` 唯一索引（`sql/schema.sql:127`）。

```java
try {
    asyncTaskMapper.insert(task);
} catch (DuplicateKeyException e) {
    // 不是异常情况，是正常并发。返回先插入的那一条
    AsyncTask again = findByBizKey(md5);
    return buildResult(again);
}
```

### 实测：10 个线程同时上传同一个文件

```
墙钟总耗时：365 ms
HTTP 状态码分布：{200: 10}          ← 全部成功，没有报错
返回的 taskId 集合：[1]              ← 10 个请求拿到同一个 taskId
✓ 幂等生效
```

日志里的真相（这是最有力的证据）：

```
[导入-异步] 已受理。taskId=1                                    ← 只有 1 个建任务成功
[导入-异步] 并发插入撞唯一索引，返回已存在的任务。md5=2a179ddf...   ← 9 个被唯一索引拦住
[导入-异步] 并发插入撞唯一索引，返回已存在的任务。md5=2a179ddf...
（...共 9 条）
```

数据库侧：

```
任务表：1 条（不是 10 条）
数据行数：10,800（不是 108,000）
唯一组合数：10,800（没有任何重复）
```

> **面试可以直接说这段**：
> "我先用业务查询做第一道幂等，再用唯一索引做第二道兜底。
> 只靠查是不够的 —— 查和插之间有窗口，高并发下必然会重复。
> 我用 10 个线程压过，结果是 1 个建任务成功、9 个撞唯一索引被拦住，最终只导入了 1 遍。"

## 六、关键设计三：线程池的 7 个参数

```java
new ThreadPoolExecutor(
    4,                                    // corePoolSize   常驻线程
    8,                                    // maximumPoolSize 峰值线程
    60L, TimeUnit.SECONDS,                // keepAliveTime  非核心线程空闲多久回收
    new LinkedBlockingQueue<>(100),       // workQueue      ★ 必须有界
    threadFactory,                        // 给线程起名字
    new ThreadPoolExecutor.AbortPolicy()  // ★ 拒绝策略
);
```

### 为什么核心是 4、最大是 8

导入是 **IO 密集**（等数据库）**+ 中等 CPU**（解析 Excel）的任务。4 个并发已经能吃满 MySQL 的写能力，
再多只会让数据库更慢，还会把连接池（默认 10 个）抢光，拖累正常的查询接口。

### JDK 线程池的"反直觉"行为

很多人以为：核心满了就立刻扩容到 max。**错。**

JDK 的真实顺序是：

```
任务来了
  ├─ 线程数 < corePoolSize？  → 新建线程
  ├─ 否则队列没满？           → 丢进队列排队
  └─ 否则线程数 < max？       → 新建线程
     否则                     → 交给拒绝策略
```

所以 **4 个线程忙、队列 100 个还没满的时候，线程数会一直是 4**，永远不会涨到 8。
这个顺序是面试常考点。

### 为什么队列必须有界（100 而不是 `Integer.MAX_VALUE`）

无界队列不会拒绝任务，而是**无限塞**。内存慢慢涨，最后 **OOM**。
OOM 是整个服务一起死，比"拒绝一个请求"严重得多。

**拒绝你能立刻看到错误，OOM 你只能看到进程消失。**

### ★ 为什么用 AbortPolicy，不用 CallerRunsPolicy

`CallerRunsPolicy` 的语义是：队列满了，让**提交任务的线程**自己去跑。

在后台批处理程序里这很好（自动限流，不丢任务）。但在 **Web 场景**里是陷阱：

```
提交任务的线程 = Tomcat 处理 HTTP 请求的那个线程
队列一满 → 这个请求亲自去跑一个 10 秒的导入
→ 异步接口又变成了同步接口，而且比同步还糟
→ 同时 Tomcat 线程被占住，其他请求也没人处理
```

**接口"秒回"的承诺被悄悄打破**，前端还在轮询 taskId，但任务其实没跑起来。体验比直接报错还差。

所以我们用 `AbortPolicy`：队列满就抛 `RejectedExecutionException`，
上层捕获后返回"系统繁忙，请稍后再试"，**并且把刚建的任务标成 FAILED**：

```java
} catch (RejectedExecutionException e) {
    markFailed(task.getId(), "系统繁忙：导入队列已满，请稍后重试");
    throw new BizException("系统繁忙，导入任务较多，请稍后重试");
}
```

为什么必须标 FAILED？否则会留下一条永远 PENDING 的"**僵尸任务**"，
用户轮询到天荒地老。**这类状态卡死的 bug 最难查。**

> 一句话总结：
> **CallerRunsPolicy 保护的是"任务不丢"，AbortPolicy 保护的是"请求不变慢"。**
> Web 场景优先保后者 —— 任务丢了可以让用户重试，而且我们有幂等，重试是安全的。

## 七、关键设计四：事务边界（今天最精妙的一段）

### 同步版：一个大事务

```java
@Transactional(rollbackFor = Exception.class)
public ImportResultVO importSync(...) { ... }
```

从"解析第一行"到"插入最后一行"全包在一个事务里。好处是原子性，代价是**长事务**：

| 危害 | 具体表现 |
|---|---|
| undo log 膨胀 | 1 万行的回滚信息全留着，MySQL 的 purge 线程追不上 |
| 锁持有时间长 | 其他会话读到的是旧快照（MVCC），写操作可能被阻塞 |
| 连接被独占 | 一个连接被占几十秒，并发 20 个人就能打满连接池 |

### 异步版：分批提交

```java
for (int from = 0; from < size; from += batchSize) {
    transactionTemplate.executeWithoutResult(status -> writeBatch(batch));
}
```

每 500 行一个独立事务，提交完就释放锁和 undo log。代价是**失去全局原子性**：
第 10 批失败时，前 9 批（4,500 行）已经落库了。

### 同一个方法，两种事务语义

`writeAllInBatches` 和 `writeBatchInNewTx` 被同步版和异步版**共用**，但行为完全不同：

| 调用方 | 外层有事务吗 | `TransactionTemplate` 的行为 | 结果 |
|---|---|---|---|
| 同步版 | 有（`@Transactional`） | 默认传播级别 `REQUIRED`，**加入**外层 | 还是一个大事务 |
| 异步版 | 没有 | 自己开一个新事务并提交 | 每批独立 |

**事务边界是由调用方决定的，不是被调方。**
理解了这一点，就不会再问"我给这个方法加了 `@Transactional` 怎么不生效" ——
注解只对"从代理外部调用进来"的那一次生效，同类内部 `this.method()` 会绕过代理。

### 为什么 `runTask` 上不能加 `@Transactional`

```java
private void runTask(Long taskId) {          // ← 故意没有 @Transactional
    ...
    asyncTaskMapper.updateById(success);      // 状态 SUCCESS
}
```

如果整个 `runTask` 在一个事务里，那么导入失败回滚时，**状态更新也会被一起回滚**。
从 `RUNNING` 回滚成 `RUNNING` —— 看起来"没变"，实际上是那条 update 被撤销了，
任务永远卡在 `RUNNING`。**这是最难查的一类 bug。**

所以：**状态更新必须和业务数据分开事务。**

## 八、今天踩的 5 个坑

### 坑 1：Listener 被注册成单例 Bean

`FactImportListener` 是有状态的（`buffer` 攒行、`totalRows` / `errors` 计数）。
如果写成 `@Component` 单例：

```
用户 A 上传 → 读到第 300 行（buffer 里攒着）
用户 B 同时上传 → 拿到同一个 Listener 实例 → B 的行被塞进 A 的篮子
```

两份文件的数据混在一起，计数互相覆盖。偶发、难复现、日志看起来完全正常。

**正确做法：每次导入 `new` 一个。**
判断标准：**这个对象的状态，是不是"只属于一次请求"？是，就不能做单例。**

### 坑 2：并发写同一个文件

第一版直接 `Files.copy(in, dest)`。10 个并发请求同时写 `data/import/{md5}.xlsx`，
Windows 上第二个就报 `另一个程序正在使用此文件`。

修法是**先写临时文件，再改名**：

```java
Path tmp = dir.resolve(md5 + ".tmp." + UUID.randomUUID());
Files.copy(in, tmp);                 // 每个请求写自己的临时文件
try {
    Files.move(tmp, dest);           // 谁先 move 成功算谁的
} catch (FileAlreadyExistsException e) {
    Files.deleteIfExists(tmp);       // 别人写好了，内容一样，直接用他的
}
```

无锁、性能好。**加锁也能解决，但没必要。**

### 坑 3：`successRows` 统计口径错了

第一版失败时写的是 `listener.getHandledRows()`（解析出多少行）。
结果：一个**校验失败、一行都没写进去**的任务，`success_rows` 显示 **1**。

用户看到"失败 / 成功 1 行"会彻底懵。

正确做法：用 `AtomicInteger written` 精确记账，**每批事务提交成功后才累加**：

```java
writeBatchInNewTx(batch);
written.addAndGet(batch.size());   // 提交成功才加
```

失败时 `success_rows` = `written.get()`。校验失败时它就是 0。

> 这类 bug 不会让程序崩，只会让**用户看到错的数字**。而"数字错了"往往比"报错了"更麻烦。

### 坑 4：逐行插入 vs 批量插入，差 7.8 倍

| 方式 | SQL 次数 | 耗时 |
|---|---|---|
| 逐行 `INSERT`（batchSize=1） | 10,800 次 | 5,090 ms |
| 批量 `INSERT ... VALUES (...),(...)`（每批 500） | 22 次 | 651 ms |

不只是"网络往返次数"的问题，还有：

- 每次 INSERT 都要**单独解析 SQL**（虽然 MySQL 有执行计划缓存，但仍有开销）
- 每次 INSERT 都要**单独维护索引**（`uk_fact` + `idx_tpi` 两棵 B+ 树）
- 每次 INSERT 都是**一个隐式事务**（关闭 binlog 同步、写 redo/undo）

为什么不是"一次插 1 万行"？三个限制：

1. `max_allowed_packet` 默认 64MB，一条 SQL 太大会被拒
2. 单条 SQL 太长，解析和事务日志都变大，回滚成本高
3. 一整批失败时，500 行的重试代价远小于 1 万行

**500 是工程经验值，不是理论最优。**

### 坑 5：表头写错一个字，字段全变成 null（而且不报错）

EasyExcel 靠 `@ExcelProperty("区域编码")` 做表头匹配。如果 Excel 里写的是"区域代码"：

- **不报错**
- 所有行的 `regionCode` 都是 `null`
- 如果不做校验，1 万条 `region_code = NULL` 的数据会被插进去（然后被数据库的非空约束拒绝，报一堆看不懂的错）

**这就是为什么 Listener 里必须逐行校验**，而不是信任 Excel。

实测（`bad-header.xlsx`）：

```
status=FAILED  total_rows=2  success_rows=0
失败原因：共 2 行数据不合法，本次一行都未写入：
         第 2 行：区域编码不能为空；第 3 行：区域编码不能为空
```

### 补充：为什么"校验失败一行都不写"

第一版是"边解析边写"，结果是"第 8000 行错了"的时候，前 7999 行已经插进去了。
虽然同步版能靠大事务回滚，但异步版是分批提交，**事务兜不住**。

所以改成：**解析阶段只收集、不写库；零错误才开始写。**

```java
List<FactImportRow> allRows = new ArrayList<>();
FactImportListener listener = new FactImportListener(COLLECT_BATCH, allRows::addAll);
// ... 解析完 ...
if (listener.getErrorRows() > 0) throw new BizException("...本次一行都未写入...");
writeAllInBatches(allRows, batchSize, written);   // 校验全过了才写
```

实测三种非法文件，全部 `success_rows=0`，库里查 `2027-07` 的行数是 **0** —— 一行脏数据都没留。

代价：1 万行对象暂存在内存里（约 3~5MB）。用 `stat.import.max-rows=50000` 给内存设上限。
**这是"原子性"和"内存"的交换。** 要导 100 万行，就得改成"两遍扫描"（第一遍只校验，第二遍才写）。

## 十二、自测题（8 道）

### Q1. 异步任务的记录为什么必须落在数据库里？只丢进线程池不行吗？

<details>
<summary>点开看答案</summary>

**不行。** 线程池是**进程内**的，服务一重启（发版、OOM、断电），队列里没跑完的任务全部消失。

而用户手里已经拿到了"提交成功" —— 他会以为在导，实际什么都没发生。更糟的是他下次再传，
又会新建任务，永远不知道上一次丢了。

落库之后才有：可查进度、重启不丢、能扫僵尸任务重投递、出问题能追溯。

**一句话：线程池是干活的，任务表是记账的。记账必须在数据库里。**

</details>

### Q2. 为什么用文件 MD5 当幂等键？用文件名不行吗？

<details>
<summary>点开看答案</summary>

三个原因：

1. **文件名可以改。** 用户把 `data.xlsx` 另存为 `data-副本.xlsx` 再传，文件名变了、MD5 没变 ——
   MD5 能拦住，文件名拦不住（实测验证过）。
2. **不同内容可能同名。** 两个不同部门各有一个 `2026数据.xlsx`，用文件名会把第二个误判成重复。
3. **文件名是用户可控的。** 保存文件时如果直接拼原始文件名，`../../../etc/passwd` 这种
   可以造成**路径穿越**。用 MD5 当文件名，用户完全无法影响路径。

MD5 的本质是**内容指纹**：内容一样 → 指纹一样；改一个字节 → 指纹完全不同。

</details>

### Q3. 已经查过 `biz_key` 了，为什么还需要唯一索引？

<details>
<summary>点开看答案</summary>

因为**"查"和"插"是两步，中间有窗口**：

```
线程 A: 查 → 不存在
线程 B: 查 → 不存在       ← 两个都查到了"没有"
线程 A: INSERT ✓
线程 B: INSERT           ← 没有唯一索引就是两条任务
```

加锁也能解决，但那会把整个上传接口串行化，性能很差。
唯一索引是数据库层的原子保证，**零成本、无锁、天然安全**。

实测：10 线程并发上传同一文件 →
日志是 `1 条已受理 + 9 条并发插入撞唯一索引`，最终任务表只有 1 条记录。

**面试表述："业务查询是第一道防线（拦住大部分），唯一索引是第二道（兜住并发的那一小部分）。缺一不可。"**

</details>

### Q4. 线程池为什么用 `AbortPolicy`，不用 `CallerRunsPolicy`？

<details>
<summary>点开看答案</summary>

`CallerRunsPolicy` 会让**提交任务的线程**自己执行任务。在 Web 里，提交任务的就是 Tomcat 的
HTTP 工作线程 —— 于是：

- 异步接口又变成了同步（用户被卡 10 秒）
- Tomcat 线程被占住，其他请求没人处理
- 前端还在轮询 taskId，但任务根本没跑

`AbortPolicy` 直接抛 `RejectedExecutionException`，我们捕获后：

1. 把任务标成 FAILED（避免留"僵尸 PENDING"）
2. 返回"系统繁忙，请稍后重试"

用户明确知道要重试，而且有幂等兜底，重试是安全的。

**CallerRunsPolicy 保"任务不丢"，AbortPolicy 保"请求不变慢"。Web 场景优先保后者。**

</details>

### Q5. 1 万行逐行 insert 和每 500 行批量 insert，差多少？为什么？

<details>
<summary>点开看答案</summary>

实测（同一台机器）：**5,090 ms → 651 ms，快 7.8 倍。**

原因有四层：

1. **网络往返**：10,800 次 vs 22 次。每次往返即使只有 0.3ms，也是 3 秒的差距。
2. **SQL 解析**：每条 INSERT 都要解析一次语法、生成执行计划。
3. **索引维护**：这张表上有 `uk_fact` 和 `idx_tpi` 两棵 B+ 树，每条 INSERT 都要更新两棵树。
4. **事务开销**：每条 INSERT 是一个隐式事务，要写 redo log、刷 binlog。

**为什么不是一次插 1 万行？** 因为 `max_allowed_packet`（默认 64MB）、
单条 SQL 解析开销、失败重试代价三个限制。500 是经验值。

</details>

### Q6. 为什么 `runTask` 上不能加 `@Transactional`？

<details>
<summary>点开看答案</summary>

因为**状态更新会和业务数据一起回滚**。

假设加了 `@Transactional`，导入到第 10 批失败：

1. 业务数据回滚（正确）
2. **`UPDATE async_task SET status='SUCCESS'` 也被回滚**
3. 但之前那次 `UPDATE ... SET status='RUNNING'` 也在同一个事务里 → 也回滚
4. 结果：状态还是 `PENDING`？不 —— 实际上要看 update 是在事务内还是外

更准确的说法是：一旦状态更新和业务数据共享事务，任何一次回滚都会让**状态和实际数据脱节**。
最典型的表现是任务永远卡在 `RUNNING`，谁也看不出它失败了。

正确做法：**状态更新用独立的、自动提交的 SQL**（本项目里 `runTask` 没有 `@Transactional`，
每次 `updateById` 就是独立提交）。业务数据用 `TransactionTemplate` 分批管理。

</details>

### Q7. `FactImportListener` 为什么不能注册成 Spring 单例 Bean？

<details>
<summary>点开看答案</summary>

因为它**有状态**：`buffer`（攒行的篮子）、`totalRows`、`errors` 都是"本次导入"的私有数据。

单例的话，两个用户同时导入 → 共用同一个 Listener → B 的行被塞进 A 的篮子，
计数互相覆盖。数据混在一起，还查不出来。

**判断标准：这个对象的状态是不是"只属于一次请求"？是，就不能做单例。**
Spring 单例适合无状态的 Service / Mapper / 工具类。

（顺带：`@Component` 的 Service 也应该是无状态的 —— 如果你在 Service 里写了
`private List<Xxx> cache`，那基本就是 bug。）

</details>

### Q8. 校验失败时为什么"一行都不写"？怎么实现的？

<details>
<summary>点开看答案</summary>

因为**"部分成功"是最糟糕的状态**：用户看到"失败 + 成功 8000 行"，根本不知道哪些进去了。
再传一次又会产生重复。

实现方式是**把"解析"和"写入"彻底分开**：

```java
FactImportListener listener = new FactImportListener(COLLECT_BATCH, allRows::addAll);
EasyExcel.read(in, FactImportRow.class, listener).sheet().doRead();  // 只收集，不写库

if (listener.getErrorRows() > 0) {
    throw new BizException("...本次一行都未写入...");   // 到这里还一行没写
}
writeAllInBatches(allRows, batchSize, written);        // 校验全过了才写
```

代价是 1 万行对象要暂存在内存（3~5MB），用 `max-rows` 限制上限。
如果数据量特别大，改成"两遍扫描"（第一遍只校验，第二遍才写）。

</details>

## 十三、明天（Day 10）

今天完成了"接单 + 执行 + 幂等"，还差**失败之后怎么办**：

1. **指数退避重试**：失败后 1s / 2s / 4s 再试，用 `async_task.next_retry_time` 记账
2. **定时补偿扫描**：`@Scheduled` 扫 `status IN ('PENDING','RUNNING')` 或 `next_retry_time <= now()` 的任务重新投递
3. **`insertBatch` 改成 upsert**（`ON DUPLICATE KEY UPDATE`）
   —— 这是重试能成功的**前提**：普通 INSERT 重试会撞唯一索引，永远失败
4. **人为造一次失败**，把重试链路跑通、把日志和状态变化录下来

> 记住这句话：**"可重试"的前提是"可重入"。**
> 一个操作如果重复执行会出错，那它就不该被重试 —— 要么让它幂等，要么别重试。
