# 区域经济运行指标服务 · area-econ-metrics

> 一个从零实现的指标数据服务：49 万行事实数据、4 个统计接口、Excel 异步导入导出、行级数据权限。
> 每个技术选择都配了可复现的对照实验，数字全部来自本机实测。

```
Java 21 · Spring Boot 3.3.5 · MyBatis-Plus 3.5.9 · MySQL 8.0 · Redis 5.0 · EasyExcel 3.3.4
14 次提交 · 79 个 Java 文件 · 10,970 行 Java · 建表与实验 SQL 8 份 · 验证脚本 10 个
```

## 为什么做这个项目

起因是实习时接触到「指标编码体系」——用一套编码统一管理几百个业务指标，不同业务域、不同周期、不同区域的数据都能落到同一张事实表里。这套建模思路值得单独实现一遍。

于是在本地从零写了一个：先定模型，再让接口跑起来，然后逐项处理性能、导入导出和数据权限。每个技术选择都做成可对照的实验，而不是凭感觉下结论：

1. **联合索引到底能把查询快多少？** 先不建索引，测出慢查询，再加索引重测。
2. **缓存命中真的等于快吗？** 只看耗时会受 JIT 波动干扰，改用 `performance_schema` 查"SQL 到底执行了几条"。
3. **用「改写 SQL」做行级数据权限，代价有多大？** 先测出开销，再决定怎么优化。

**结论都在下面这张表里，测量方法一并附上。**

| 改错什么 | 后果 | 有多难发现 |

## 核心设计决策

### 1. 为什么过滤条件下推到数据库，而不是在 Java 里筛？

Java 里过滤会同时牺牲三件事：**性能**（数据库照样回传全量）、**内存**（全量结果集要装进堆）、**分页正确性**（数据库给你 20 行，滤完剩 3 行，而且不报错）。所以权限必须在 SQL 层。

实现方式是给 Mapper 方法打注解，由拦截器用 JSqlParser 往 AST 里插条件：

```java
@DataScope(alias = "f")   // alias 是这个查询里事实表的别名
List<RegionMetricStatVO> selectCategorySummary(...);
```

```sql
-- 改写前
WHERE f.deleted = 0 AND i.category = ? AND f.period_code IN (?,?)
-- 长沙用户（region_code = 4301）请求，改写后
WHERE f.deleted = 0 AND i.category = ? AND f.period_code IN (?,?) AND f.region_code LIKE '4301%'
```

业务代码一行 `if` 都没加。**必须用 AST 而不是字符串拼接**——`sql + " AND cond"` 遇到 `WHERE a=1 OR b=2` 会被 OR 短路，越权且不报错。

### 2. 为什么 `LIKE '4301%'` 就够了？

因为 `region_code` 用的是 GB/T 2260 行政区划编码，天然是前缀结构：`430000`（湖南）→ `4301`（长沙）→ `430102`（芙蓉区）。**一个参数覆盖"省/市/区"三档**，不需要维护"用户-区域"关联表。

### 3. 为什么缓存 key 里要有权限指纹？

因为**缓存命中的时候 SQL 不执行**，拦截器根本没机会改写。key 里不带权限，就会出现"admin 查完，全省数据躺在缓存里，长沙用户直接拿走"。

key 的形态是 `stat:category-summary:工业:Y:2024,2025,2026:R4301`，最后一段 `R4301` 由 `LoginUser.scopeKey()` 收敛成三种值：`ALL` / `R4301` / `NONE`。**不能直接拼 `regionCode`**，因为 `data_scope=ALL` 和 `data_scope=REGION + regionCode=null` 都可能是 `null`，会被拼成同一个 key——而它们一个能看 48 万行，一个一行都看不到。

### 4. 为什么"可重试"的前提是"可重入"？

第一次实现重试时，重放失败批次直接撞 `ERROR 1062 Duplicate entry ... uk_fact`——因为纯 `INSERT` 不能重放。改成 `INSERT ... ON DUPLICATE KEY UPDATE` 之后，重放变成幂等覆盖。

还有一个更隐蔽的：`uk_fact` 不含 `deleted` 字段，**逻辑删除的行仍然占着唯一键**，所以 upsert 必须显式 `SET deleted = 0` 才能把删掉的行"复活"。

### 5. 为什么导出必须用游标分页？

`LIMIT offset, size` 的语义不是"跳到第 N 行"，而是"**数出 N 行再丢掉**"，代价是 O(n²)。实测全量导出 245 页：OFFSET 累计 8,977 ms，游标（`WHERE id > ? ORDER BY id LIMIT ?`）138.81 ms。

游标的前提是排序键**唯一且有序**；按非唯一列排序要联合游标 `(update_time, id)`，否则同时间戳会丢行；代价是**不能跳页**——它只适合导出和滚动加载，后台页码器仍然得用 OFFSET。

### 6. 为什么线程池拒绝策略用 `AbortPolicy` 而不是 `CallerRunsPolicy`？

`CallerRunsPolicy` 看起来"优雅背压"，实际上会让**提交任务的 Web 线程自己去跑导入**，接口重新变成同步阻塞。改成 `AbortPolicy` 之后，拒绝时明确标记任务 FAILED，用户能立刻知道"队列满了，稍后再试"。

## 已知限制

写在这里不是为了自曝短板，而是**一个不知道边界的项目，比一个有边界的项目更可疑**。

| # | 限制 | 生产环境该怎么做 |
|---|---|---|
| 1 | 身份用 `X-User-Id` 请求头，谁都能伪造 | 换 JWT / Session / SSO，身份从令牌解析，不再信客户端 |
| 2 | `async_task` 和 `import_error_row` **没有 `user_id`**，任何人知道 `taskId` 就能下载别人的错误明细 | 加 `create_user_id` + **辖区快照**字段（不是关联查询——人会调辖区，历史任务该按当时的算） |
| 3 | SQL 改写结果缓存在**单机内存**里 | 多实例无共享，但每个实例各存一份也无害；要跨实例共享时，key 里必须含 `msId + scopeKey + SQL 文本` |
| 4 | 导出限流用 `Semaphore`，**只限单机** | 多实例部署要换成网关限流或 Redis 计数器 |
| 5 | 测试以**端到端脚本**为主（10 个 Python 脚本），没有 JUnit 单测 | 核心纯逻辑（退避计算、key 构造、错误分类）应该补单测；端到端脚本覆盖不到分支 |
| 6 | 单机线程池，没有 MQ | 任务量再大一个量级就该换 MQ + 独立消费者，好处是削峰、解耦、可靠投递 |
| 7 | 权限只做了**读**（查询/导出） | 写操作（改/删）要在执行前校验"这条数据归属谁"，本项目未实现 |

## 这些数字是怎么保证可信的

性能数字很容易停留在"我感觉快了"。这里刻意做了四件事：

1. **不只看耗时**。JIT 预热、GC、机器负载都会让耗时抖动，所以关键结论用 `performance_schema` 查"这条 SQL 真正扫了多少行、执行了几次"。比如"缓存命中时 SQL 条数为 0"——这是账面事实，不是耗时推断。
2. **先跑对照组**。测优化后的效果之前，先把优化临时关掉跑一遍。第 5 组（击穿防护）、第 11 组（改写开销）都是 A/B 各三轮。
3. **承认反直觉的结果**。第 2 组优化后扫描行数从 1,668 涨到 5,568，耗时反而降到 1/4——因为从"600 次随机点查"变成了"1 次顺序扫描"。行数少 ≠ 快，这个反例比"我加了个索引变快了"有价值得多。
4. **把错误也测一遍**。上面「反向验证」那三行，是把代码故意改错后跑出来的。**知道哪里会错，比知道哪里对了更难。**
